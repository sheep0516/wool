# 工具调用的产品设计判断

本节讨论工具调用中的风险分级、人工确认、权限校验与失败降级。核心原则：模型提议，程序校验，人确认，系统执行。

## 4.1 操作风险分级

工具的风险由三个因素决定：是否产生副作用、是否可撤销、涉及范围与金额。据此分四级。

| 等级 | 特征 | 例子 | 设计要求 |
|---|---|---|---|
| 一级 只读 | 无副作用，仅本人数据 | 查订单、查物流、查余额 | 权限过滤即可，无需确认 |
| 二级 可撤销写 | 有副作用，可回滚 | 创建工单、保存草稿、发站内提醒 | 记录操作日志，允许撤销 |
| 三级 高影响写 | 影响他人或有一定损失 | 修改收货地址、取消订单、批量通知 | 执行前用户确认参数 |
| 四级 不可逆或涉及资金 | 无法回滚或涉及金额、权限 | 退款、转账、删除数据、授权访问 | 强确认加二次鉴权，必要时人工审核 |

分级的意义在于把确认成本用在高风险操作上。对所有操作都加确认会让产品难用，对所有操作都不加则必然出事。

## 4.2 人工确认的设计

需要确认的场景：

1. 操作不可逆。
2. 涉及金额，且超过设定阈值。
3. 影响他人数据或批量数据。
4. 参数由模型推断且存在歧义，例如“那个订单”指代不明。

确认界面要满足三个条件：

第一，参数可见可改。用户需要看到将要执行的具体参数，例如订单号、新地址、金额，并能在确认前修改。

第二，后果明确。说明操作结果与不可逆性，例如“地址修改后立即生效，已发货订单无法修改”。

第三，范围清晰。批量操作要显示影响条数与对象列表，避免用户以为只操作了一条。

一个反例：弹窗只写“是否确认执行”，不给参数，用户只能盲点。这种确认等于没有确认。

## 4.3 权限校验

四条基本要求：

1. 以用户身份执行，不以系统身份执行。模型看到的是当前用户可访问的数据，工具调用使用当前用户的凭证。
2. 敏感操作二次鉴权。例如退款、授权他人访问，需要二次验证或审批流。
3. 最小权限。工具只授予完成任务所需的最小范围，例如只能读取本人订单，不能读取全部订单。
4. 参数白名单。对可写字段做白名单限制，禁止模型传入用户无权修改的字段，例如状态、金额、内部标记。

有一类错误很常见：把系统的服务账号交给模型使用。这样模型可以访问所有用户数据，权限控制完全失效。正确做法是把用户身份透传到工具层，由业务系统按该身份鉴权。

## 4.4 失败与降级

工具调用必然失败，产品设计要预先规定每种失败的走向。

| 失败类型 | 处理 | 用户看到什么 |
|---|---|---|
| 超时或临时故障 | 有限次重试，指数退避 | 稍等后重试或转人工 |
| 限流 | 排队或提示稍后再试 | 明确的时间预期 |
| 参数缺失 | 向用户追问，不重试 | 需要补充的具体信息 |
| 参数错误 | 修正一次后重试 | 若仍失败则转人工 |
| 业务拒绝 | 解释原因并给替代路径 | 为什么不行，可以怎么办 |
| 权限拒绝 | 停止调用，不暴露细节 | 无权限操作的提示 |
| 结果为空 | 明确说明未查到，不编造 | 未找到记录，建议核对信息 |

三条降级原则：

第一，失败不编造。模型在无结果时必须说明未查到，不能凭自身知识补一个看起来合理的答案。

第二，失败有出口。每条失败路径都要有下一步，至少能转人工或给出自助入口。

第三，失败可观测。记录错误码与频率，错误率上升时需要告警，而不是等用户投诉。

## 4.5 写操作的幂等与重试

写操作的重试风险远高于读操作：网络超时可能已经执行成功，重试会造成重复下单、重复退款。

处理方式：

1. 为每次写操作生成幂等键，服务端按幂等键去重。
2. 重试前先查询操作状态，确认未成功再重试。
3. 明确哪些错误可以重试。超时可重试但需幂等保护，业务拒绝不可重试。
4. 记录调用链路，便于事后核对是否重复执行。

## 4.6 一条可执行的设计原则

把工具调用拆成四段职责：

| 阶段 | 负责方 | 要求 |
|---|---|---|
| 提议 | 模型 | 输出工具名与参数，可包含不确定表达 |
| 校验 | 程序 | 参数格式、业务规则、权限、幂等 |
| 确认 | 人 | 高风险操作的显式同意，参数可见可改 |
| 执行 | 系统 | 真实的副作用，可审计、可回滚 |

只要这四段不合并，误操作的影响就能被限制在可控范围。把校验交给模型、把执行交给模型、或把确认省略，都会让风险直接落到用户身上。

## 4.7 常见误解

一、模型已经理解用户意图，可以直接执行。不成立。理解不等于授权，执行前必须校验与确认。

二、加一句“操作前请确认”就能防误操作。不成立。确认需要界面承载，需要参数可见，需要用户真实操作。

三、工具失败时让模型自行处理更自然。不成立。模型可能编造结果或重复调用，失败路径应由程序定义。

四、幂等只对支付类接口重要。不成立。任何写操作在超时重试时都可能重复执行。

五、只读工具不需要审计。不成立。只读调用也会泄露数据，需要记录谁在何时查询了什么。

## 4.8 判断练习

为下列工具设计风险等级与处理方式。

1. 查询本人最近三笔订单。
2. 取消一个未发货订单。
3. 给全部客户发送促销短信。
4. 修改订单收货地址。
5. 为本人账户申请退款。

参考答案：

1. 一级只读。按用户身份过滤，记录查询日志，无需确认。
2. 三级高影响写。需展示订单号与取消后果，用户确认后执行；可撤销性差，需记录。
3. 四级。批量影响他人，必须显示影响人数与内容预览，走审批，限制频率与总量。
4. 三级。确认界面需展示新旧地址对比，说明已发货不可修改；写操作加幂等键。
5. 四级。涉及资金，需强确认、二次鉴权，并记录完整调用链路。

## 4.9 小结

- 工具按副作用、可撤销性、影响范围分四级，确认成本应集中投在高风险操作上。
- 人工确认必须做到参数可见可改、后果明确、范围清晰。
- 权限以用户身份执行，敏感操作二次鉴权，工具遵循最小权限与参数白名单。
- 失败按类型分流，原则是不编造、有出口、可观测；写操作必须幂等。
- 设计原则是模型提议、程序校验、人确认、系统执行，四段职责不可合并。
