# Function Call 解决什么问题

本节说明工具调用解决的问题、模型的职责边界，以及它与 RAG 的区别。核心结论：模型只负责提出调用意图，实际执行由程序完成。

## 1.1 模型的三类能力边界

语言模型能理解、能表达、能推理，但不能直接与外部世界交互。具体表现为三条边界。

| 边界 | 表现 | 例子 |
|---|---|---|
| 无法访问实时系统 | 不知道订单状态、库存、账户余额 | 用户问“我的快递到哪了”，模型只能猜 |
| 无法保证精确计算 | 多位数运算、金额合计容易出错 | 运费与折扣叠加计算 |
| 无法执行写操作 | 不能改地址、发通知、发起退款 | 用户说“帮我改一下收货地址”，模型只能说“请自行操作” |

这三条边界不因模型变强而消失。模型本质上处理的是文本，访问数据库与执行业务动作必须由外部系统完成。

## 1.2 工具调用的机制

工具调用把一次交互拆成两个角色：

1. 模型接收用户请求与工具清单，输出一个结构化的调用请求，包含工具名与参数。
2. 程序解析该请求，校验权限与参数，调用真实系统，把结果回传给模型。
3. 模型基于结果继续生成回答，或发起下一次调用。

职责划分如下：

| 环节 | 负责方 | 说明 |
|---|---|---|
| 判断是否需要调用、调用哪个 | 模型 | 属于理解与决策 |
| 生成参数 | 模型，但需校验 | 模型可能填错、编造或漏填 |
| 权限校验 | 程序 | 与用户身份绑定，模型无权决定 |
| 执行 | 程序 | 真实副作用发生在这里 |
| 结果解释与回复 | 模型 | 把结构化结果转成用户能懂的话 |

需要明确的一点：模型输出的调用请求只是一份“提议”，不是执行。是否执行、以什么参数执行，由程序决定。这一层隔离是后面所有安全设计的基础。

## 1.3 与 RAG 的区别

| 维度 | RAG | 工具调用 |
|---|---|---|
| 访问对象 | 文档与知识库 | 业务系统、外部 API、计算器 |
| 数据形态 | 非结构化文本为主 | 结构化数据与动作 |
| 是否产生副作用 | 只读 | 可读可写，可能不可逆 |
| 时效性 | 取决于文档更新 | 实时 |
| 主要风险 | 答错、答不全 | 误操作、越权、重复执行 |
| 适合的问题 | “规定是什么” | “我的订单现在什么状态”“帮我改地址” |

两者互补而非替代。退货判定既需要政策文档（RAG），也需要订单状态（工具）。只上 RAG，系统会在需要实时数据时编造；只上工具，系统会在需要解释规则时说不清。

## 1.4 典型场景

| 场景 | 工具做什么 | 风险等级 |
|---|---|---|
| 订单与物流查询 | 按订单号读取状态 | 低，只读 |
| 商品与库存查询 | 读取库存、价格 | 低，只读 |
| 费用与折扣计算 | 调用计价接口 | 低到中，影响用户决策 |
| 创建工单、发通知 | 写入系统 | 中，可撤销但有打扰 |
| 修改收货地址 | 更新订单字段 | 中高，可能发错货 |
| 退款、转账、审批 | 资金或权限操作 | 高，不可逆 |

工具带来的价值是从“会说”变成“会做”，能力边界显著扩大。同时风险等级也随之上移：读操作出错只是信息不准，写操作出错会产生真实损失。第4节会专门讨论分级与确认机制。

## 1.5 工具设计的三个基本判断

第一，这个能力是否真的需要模型参与。如果调用条件完全确定，例如“点击按钮查订单”，不需要模型，直接调接口即可。工具调用适合的是“需要理解自然语言才能确定调用对象与参数”的场景。

第二，工具是否应该暴露给模型。工具越多，模型选错的概率越高。只暴露当前任务需要的子集，比暴露全量工具更可靠。

第三，副作用是否可撤销。不可撤销的操作必须配人工确认，不能依赖模型判断。

## 1.6 常见误解

一、模型能直接执行操作。不成立。模型只输出调用请求，执行发生在你的服务端，必须在服务端做校验。

二、工具越多，能力越强。不成立。工具数量增加会降低选择准确率，并扩大攻击面。

三、有了工具就不需要 RAG。不成立。工具解决实时数据与动作，规则与解释仍需要文档依据。

四、工具调用一定比 RAG 准。不成立。工具返回的是数据，解释数据仍可能出错；参数填错会导致查错对象。

五、只读工具不需要权限控制。不成立。只读也可能泄露他人数据，权限必须按用户身份过滤。

## 1.7 判断练习

判断下列需求应使用 RAG、工具调用，还是两者都不用。

1. 查询“七天无理由退货的具体条件”。
2. 查询“订单 A123 当前是否已签收”。
3. 用户说“帮我把这个订单的地址改到公司”。
4. 解释“为什么我的退款还没到账”。
5. 根据用户描述推荐一款适合的耳机。

参考答案：

1. RAG。属于制度文档，需要引用原文。
2. 工具调用。属于实时结构化数据。
3. 工具调用加人工确认。属于写操作，参数需核对，执行前需用户确认。
4. 两者结合。退款进度需要查系统（工具），到账周期需要查规则（RAG）。
5. 两者结合。商品参数与库存需要工具，推荐理由与对比可以基于资料生成；若推荐依据是商品知识库，则用 RAG。

## 1.8 小结

- 模型有三条边界：无法访问实时系统、无法保证精确计算、无法执行写操作。
- 工具调用中，模型负责提出调用意图与参数，程序负责校验与执行，权限不交给模型。
- 工具调用与 RAG 互补：RAG 提供规则与解释，工具提供实时数据与动作。
- 工具会显著扩大能力边界，也会把风险从“答错”升级为“误操作”。
- 只暴露必要工具、按副作用可撤销性分级，是三条基本设计判断。
