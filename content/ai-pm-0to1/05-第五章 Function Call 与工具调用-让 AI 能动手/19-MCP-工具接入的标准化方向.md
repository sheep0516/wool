# MCP-工具接入的标准化方向

本节说明 MCP 解决的接入问题、它的基本结构，以及对产品架构的影响。MCP 是协议层的标准化，不改变工具调用的基本原理。

## 3.1 MCP 是什么

MCP（Model Context Protocol）是一套用于连接模型应用与外部工具、数据源的协议。它规定工具如何描述、如何被发现、如何被调用、如何鉴权，使工具实现方与应用方不必为每个组合单独开发对接。

一句话概括：把“每个应用对接每个工具”的点对点开发，改为“工具实现一次，多个应用复用”。

## 3.2 它解决的接入问题

在没有统一协议时，接入 N 个工具与 M 个应用，需要 N × M 套对接实现。每套实现各自定义参数格式、错误码、鉴权方式，维护成本随规模非线性增长。

| 维度 | 点对点对接 | 通过 MCP 接入 |
|---|---|---|
| 对接工作量 | N × M | N + M |
| 工具描述格式 | 各应用自定义 | 协议统一 |
| 鉴权方式 | 各实现自行处理 | 协议层统一约定 |
| 新增应用 | 需为每个工具重新对接 | 连接已有服务器即可 |
| 新增工具 | 需为每个应用改造 | 一次实现，多处可用 |

除工作量之外，还有两个隐性收益：工具能力可被应用自动发现，而不是写死在代码里；权限与审计可以集中在接入层，而不是散落在各处。

## 3.3 基本结构

MCP 采用客户端与服务器的结构：

| 角色 | 职责 |
|---|---|
| 服务器 | 暴露能力，包括可调用的工具、可读取的资源、可复用的提示模板 |
| 客户端 | 运行在宿主应用中，发现并调用服务器提供的能力 |
| 宿主应用 | 最终的产品界面与业务逻辑，决定哪些能力暴露给模型 |

连接方式通常分两类：本地进程通过标准输入输出通信，远程服务通过 HTTP 传输。协议包含能力协商与初始化流程，客户端在连接后才知道服务器提供哪些工具及其参数结构。

三类能力的作用不同：

1. 工具：可执行的动作，可能产生副作用。
2. 资源：可读取的数据，通常只读，例如文件、记录、文档。
3. 提示模板：可复用的指令片段，由服务器提供，应用按需引用。

## 3.4 对产品架构的影响

| 影响 | 说明 |
|---|---|
| 工具层可插拔 | 工具实现与模型、应用解耦，更换模型或新增入口不需要重写工具 |
| 能力复用 | 同一工具服务器可被多个产品接入，减少重复开发 |
| 权限集中 | 鉴权、审计、限流可统一在接入层实现 |
| 生态接入变快 | 现成的第三方服务器可以直接接入，缩短从需求到可用的周期 |

同时引入新的风险，需要在产品设计中明确处理：

| 风险 | 说明 | 应对 |
|---|---|---|
| 供应链可信度 | 第三方服务器可能读取数据、执行未声明的操作 | 只接入可信来源，限制其可访问的数据范围 |
| 工具描述注入 | 服务器返回的描述文本可能包含诱导性指令 | 对描述做审查与白名单，不盲信动态描述 |
| 权限过大 | 一个服务器聚合过多能力，或被授予过宽权限 | 按最小权限配置，高风险能力单独授权 |
| 可用性依赖 | 服务器故障会直接导致产品功能不可用 | 准备降级路径与备用实现 |

## 3.5 与 Function Call 的关系

两者不在同一层：

| 概念 | 层级 | 作用 |
|---|---|---|
| Function Call | 模型能力 | 模型输出结构化的调用请求 |
| MCP | 接入协议 | 规定工具如何被发现、描述、调用、鉴权 |

Function Call 回答“模型怎么提出调用”，MCP 回答“工具怎么接进来”。没有 MCP 也能实现工具调用，只是每个工具都要自行对接；有了 MCP，接入过程标准化，但模型侧的调用逻辑不变。

## 3.6 什么时候用，什么时候不用

适合使用的情况：

1. 需要接入多个工具或多个数据源，且未来可能增加。
2. 同一批工具要被多个产品、多个入口复用。
3. 希望把权限与审计收敛到一个接入层。
4. 需要快速接入外部生态提供的现成能力。

不必使用的情况：

1. 只有一两个内部接口，且不会扩展。直接实现调用更简单。
2. 工具逻辑与业务强耦合，需要大量定制化处理。
3. 团队缺少维护接入层的运维能力，引入协议反而增加负担。

判断的核心是规模与复用：工具少、只服务一个产品时，标准化的收益抵不过复杂度。

## 3.7 常见误解

一、MCP 是模型的能力。不成立。它是接入协议，模型本身并不知道 MCP，能力仍通过 Function Call 表达。

二、接入 MCP 后工具就安全了。不成立。协议统一了格式，不保证工具可信、权限合理、操作可控。

三、第三方 MCP 服务器可以直接上生产。不成立。需要审查其能力范围、数据访问与错误处理，并限制权限。

四、用了 MCP 就不需要自己设计工具描述。不成立。描述质量仍决定调用准确率，协议只规定格式。

五、MCP 只适合大公司。不成立。是否使用取决于工具数量与复用需求，与小规模场景关系不大。

## 3.8 判断练习

判断下列情况是否适合引入 MCP 接入层。

1. 一个内部客服助手，需要调用订单、物流、退款三个接口。
2. 公司有五个 AI 产品，都需要访问同一批内部系统。
3. 一个演示 Demo，只调用一个天气接口。
4. 需要接入多个外部 SaaS 服务，且希望统一审计调用记录。
5. 工具需要读取大量敏感数据，且要求严格的数据驻留限制。

参考答案：

1. 可选。接口少且稳定，直接实现更简单；若预期继续扩展，可提前标准化。
2. 适合。多个应用复用同一批工具，标准化的收益明显。
3. 不适合。单接口、单场景，引入协议只增加复杂度。
4. 适合。统一接入便于集中审计与权限管理。
5. 谨慎。若必须本地部署且数据不出域，应选择支持本地运行的服务器，并严格限制其可访问范围，不能因为用了协议就放松管控。

## 3.9 小结

- MCP 是连接模型应用与外部工具、数据源的协议，把 N × M 的点对点对接降为 N + M。
- 结构上是服务器暴露能力、客户端发现并调用、宿主应用决定暴露范围，能力分为工具、资源、提示模板。
- 收益是可插拔、可复用、权限集中；风险是供应链可信度、描述注入、权限过大与可用性依赖。
- Function Call 是模型能力，MCP 是接入协议，二者不同层。
- 是否引入取决于工具数量与复用需求，工具少且单产品使用时不必引入。
