# 工具定义与调用流程

本节说明如何向模型描述一个工具、调用闭环如何运转，以及工具返回结果与错误的设计方式。

## 2.1 工具定义的四个部分

一个工具的定义包含名称、用途描述、参数结构、返回结构。这四项都是写给模型看的接口文档，写法直接决定调用准确率。

| 部分 | 作用 | 常见问题 |
|---|---|---|
| 名称 | 唯一标识，便于模型选择 | 命名相似，模型无法区分 |
| 用途描述 | 说明做什么、什么时候用、什么时候不用 | 只写功能，不写适用边界 |
| 参数 | 名称、类型、是否必填、取值范围、枚举、默认值 | 参数过多，需要模型自行推算 |
| 返回结构 | 成功与失败时的字段约定 | 结构不统一，模型无法判断成败 |

用途描述最容易写差。有效的描述应包含三句：这个工具做什么、在什么情况下使用、在什么情况下不要使用。

| 差的写法 | 好的写法 |
|---|---|
| 查询订单 | 按订单号查询订单状态与物流信息。用户询问订单进度、签收时间时使用。不用于查询退款进度，退款应使用 query_refund。 |
| 修改地址 | 修改未发货订单的收货地址。仅在订单状态为未发货时可用，已发货订单应引导用户联系快递。 |
| 计算价格 | 根据商品、数量、优惠券计算应付金额。涉及金额时优先使用本工具，不要自行计算。 |

命名方面有三条规则：同一前缀表示同一对象（query_order、update_order），动词在前，不出现同义重复工具（query_order 与 get_order 同时存在会导致调用摇摆）。

## 2.2 参数设计

参数越少、越明确，调用越可靠。

1. 减少需要模型推理的参数。能用枚举就用枚举，能设默认值就设默认值。
2. 必填参数尽量少。必填过多会迫使模型猜测，猜测会导致错误调用。
3. 参数加约束。类型、格式、范围写清楚，例如日期用 YYYY-MM-DD，金额为正数。
4. 提供降级参数。例如查订单时，允许用手机号加时间段代替订单号，避免用户提供不出订单号时无法服务。
5. 不要把业务规则藏进参数名。参数名应描述数据，不描述规则。

## 2.3 调用闭环

一次完整的调用流程包含六步：

1. 模型收到用户请求与可用工具清单。
2. 模型判断是否需要调用，选择工具并生成参数。
3. 服务端校验：参数格式、必填项、取值范围、用户权限、调用频率。
4. 服务端执行真实调用，记录请求与响应。
5. 结果回传模型，必要时裁剪为精简字段。
6. 模型基于结果生成回答，或继续发起下一次调用。

几个实践要点：

第一，模型可能一次返回多个并行调用，服务端应支持并行执行并分别回传结果，避免串行等待。

第二，连续调用需要设上限。例如最多三轮工具调用，超出则转为兜底回答并提示用户，防止无限循环。

第三，结果回传要精简。把整个业务对象原样塞回上下文会占用大量 Token，并引入无关字段干扰判断。应只回传回答所需字段。

第四，每次调用都要可追溯：记录用户会话、工具名、参数、耗时、结果状态。线上排查依赖这些记录。

## 2.4 返回结构设计

成功与失败应使用统一结构，让模型能明确判断结果状态。

```
成功：{"status": "ok", "data": {...}, "summary": "订单已签收，签收时间 2026-10-20"}
失败：{"status": "error", "code": "ORDER_NOT_FOUND", "message": "未找到该订单"}
```

错误码应分类，因为不同类别对应不同处理：

| 错误类型 | 例子 | 处理方式 |
|---|---|---|
| 可重试 | 超时、限流、临时故障 | 有限次重试，指数退避 |
| 需要用户补充 | 缺少订单号、地址不完整 | 向用户追问，不要重试 |
| 业务拒绝 | 订单已发货不可改地址、额度不足 | 解释原因并给替代方案 |
| 权限拒绝 | 无权查看他人订单 | 停止调用，不暴露具体原因 |
| 参数错误 | 日期格式不对 | 修正后重试一次，仍失败则兜底 |

一条设计要求：失败信息要能让模型生成有用回复，而不是只返回技术错误。例如“订单已发货，无法修改地址，建议联系快递改址”，模型才能给出可执行建议。

## 2.5 工具数量与选择

模型选错工具，多数源于工具集过大或描述重叠。实践建议：

1. 单场景暴露的工具控制在十个以内。
2. 按业务域拆分工具集，先用意图识别确定域，再暴露该域工具。
3. 删除长期未使用的工具，减少干扰。
4. 对高风险工具单独分组，配合确认流程。

## 2.6 常见误解

一、工具描述越短越好。不成立。缺少适用边界会让模型在错误场景调用。

二、参数越多越灵活。不成立。参数越多，模型填错与漏填的概率越高。

三、调用失败就让模型自由发挥。不成立。失败应进入明确的降级路径，而不是让模型编造结果。

四、返回完整数据更有利于模型判断。不成立。无关字段会干扰判断并推高成本，应裁剪。

五、工具调用可以无限重试。不成立。必须设次数上限，写操作还需幂等保护。

## 2.7 判断练习

1. 两个工具分别叫 query_order 与 get_order，功能相近。预测线上表现并给出处理。
2. 一个改地址工具要求模型填写“新地址所在仓库编号”。指出问题。
3. 查询接口超时后，模型连续重试五次仍失败，最后编造了物流信息。指出两处设计缺陷。
4. 工具返回报文包含 40 个字段，其中只有 3 个与回答相关。给出处理方式。

参考答案：

1. 模型调用摇摆，同一问题可能调用不同工具，结果不一致。应合并为一个工具或明确删除其中一个。
2. 仓库编号不应由模型推算，属于系统内部逻辑。应由服务端根据地址自动匹配，模型只提供地址文本。
3. 一是未设重试上限与错误分类；二是失败后未进入兜底路径，允许模型在无结果时生成答案。应限制重试次数，并在失败时明确拒答或转人工。
4. 在服务端裁剪返回字段，只回传回答所需内容，并附一句摘要供模型直接使用。

## 2.8 小结

- 工具定义包含名称、用途描述、参数结构、返回结构，用途描述要写清何时用与何时不用。
- 参数设计原则是减少必填、多用枚举与默认值、把业务规则交给服务端。
- 调用闭环是模型提议、服务端校验与执行、结果回传、模型再生成，需设调用次数上限。
- 返回结构统一，错误按可重试、需补充、业务拒绝、权限拒绝、参数错误分类处理。
- 单场景工具数量应受控，工具过多会导致选择错误。
