# 结构化 Prompt 与输出格式控制

本节讨论如何让模型稳定输出 JSON、表格与分类标签，以及 Few-shot 示例的设计原则。目标是让输出可被程序解析，而不只是“看起来整齐”。

## 2.1 为什么必须控制格式

结构化输出的目的是让结果进入下游系统。自然语言输出需要额外解析，解析规则脆弱，一旦模型换了措辞就会失败。格式稳定后，才能做自动校验、批量处理和指标统计。

需要区分两个层次的要求：

- 结构正确：字段齐全、类型正确、可被解析。
- 语义正确：字段取值符合事实与规则。

约束解码只能保证前者，后者必须靠校验规则与评估集。

## 2.2 四种手段，可靠性递进

| 手段 | 做法 | 可靠性 | 成本 | 适用 |
|---|---|---|---|---|
| 自然语言要求 | 在 Prompt 中写“只输出 JSON” | 最低，长输出时易被打破 | 低 | 原型验证 |
| Few-shot 示例 | 给出输入输出样例 | 中等，显著提升格式遵循 | 中，占用上下文 | 字段较少、格式稳定的任务 |
| 结构化输出 | JSON schema、函数调用、约束解码 | 高，服务端约束生成 | 低到中，依赖接口支持 | 生产环境首选 |
| 解析校验加重试 | 程序解析，失败则带错误信息重试 | 最高，作为兜底 | 增加调用次数 | 所有生产场景都应保留 |

实践中不是四选一，而是组合：用结构化输出保证主体格式，用解析校验捕获剩余失败，重试时把解析错误回传给模型。

需要注意的是，即使使用 JSON schema，也只保证结构合法，不保证取值合理。金额为负数、日期在未来、枚举值语义错误，都需要业务校验。

## 2.3 分类标签的设计

分类任务的问题多数出在标签体系，而不是模型。四条设计规则：

第一，互斥。任意一条样本应只属于一个标签。若业务上确实存在多重归属，应明确改为多标签任务，并规定最多可选数量。

第二，完备。必须包含兜底类别，例如“其他”“无法判断”。没有兜底类，模型会把边界样本硬塞进最接近的标签。

第三，粒度一致。不要把“退款”和“售后进度查询”放在同一层级，前者是业务动作，后者是信息查询。粒度混杂会导致边界模糊。

第四，每个标签都要有定义与边界样例。仅给标签名，模型只能凭字面猜测。

一个可用的标签定义表：

| 标签 | 定义 | 边界说明 |
|---|---|---|
| 售前咨询 | 询问商品信息、价格、活动 | 未产生订单 |
| 订单查询 | 查询物流、订单状态 | 已有订单号 |
| 退款申请 | 明确表达退款或退货诉求 | 仅表达不满不算 |
| 投诉建议 | 对服务或商品表达不满 | 可与退款并存，按主诉归类 |
| 其他 | 无法归入以上类别 | 兜底类 |

标签数量也有约束：单次分类给出超过 20 个标签时，准确率通常明显下降。标签过多时应改为两级分类，先分大类再分小类。

## 2.4 Few-shot 示例的设计原则

1. 数量控制在 2 至 5 条。质量比数量重要，十条例题不如三条覆盖边界的例子。
2. 必须包含边界样本与难例，不能只给典型样本。只给典型样本会让模型在边界上过度自信。
3. 示例格式与期望输出完全一致，包括字段顺序、引号、空值写法、单位。
4. 顺序有影响。把与当前输入最相似的例子放在最后，更容易被模型采用。
5. 示例必须真实，不能编造。编造的示例会教模型编造，尤其在事实性任务上。
6. 示例与指令不能矛盾。示例里出现指令禁止的写法，模型会优先模仿示例。
7. 分类任务中要打散标签分布。如果五个例子全是同一类，模型会倾向输出该类。
8. 示例中的输入要去标识化，避免把真实用户信息写进 Prompt 缓存与日志。

## 2.5 表格与长文本输出

表格输出适合给人看，JSON 适合给程序用。若两者都需要，先生成 JSON，再由程序渲染表格，避免模型同时维护两种格式。

表格类输出的常见问题与对策：

| 问题 | 对策 |
|---|---|
| 列数不稳定 | 在 Prompt 与 schema 中固定列名 |
| 单元格内换行破坏表格 | 禁止单元格内换行，长内容截断并标注 |
| 空值写法不统一 | 统一为空字符串或 null，并在说明中定义 |
| 内容过长导致截断 | 规定单行字数上限，超出部分另起续篇或输出到附件 |

长文本输出应规定结构与长度，并把“续写”设计为可控制的分段生成，而不是依赖一次超长输出。

## 2.6 失败处理

结构化输出的失败应分级处理，而不是直接报错给用户：

1. 解析失败。把解析错误原文附在重试请求中，要求只修正格式，不改内容。
2. 字段缺失。必填字段缺失时重试，可选字段缺失则补默认值并标记。
3. 类型错误。按 schema 强转，失败则重试。
4. 语义异常。用业务校验规则拦截，例如金额范围、日期范围、枚举合法性。
5. 多次重试仍失败。降级为宽松格式加人工处理，并记录样本用于改进。

这五级应写进 PRD 的降级章节，而不是留给工程临时处理。

## 2.7 常见误解

一、写了“只输出 JSON”就足够。长输出与复杂字段时遵循率会下降，需要 schema 或示例配合。

二、Few-shot 越多越好。示例占用上下文并推高成本，过多还会让模型过度拟合示例中的表面特征。

三、schema 校验通过就代表结果正确。schema 只保证结构，语义正确需要业务校验。

四、温度设为 0 就能保证格式稳定。温度 0 降低但不消除波动，长输出仍可能出现格式偏差，解析兜底不可省略。

五、分类标签越多越细越好。标签数量与粒度都会降低准确率，超过一定规模应分层。

## 2.8 判断练习

1. 一个抽取任务要求输出 JSON，包含 15 个字段，线上解析失败率约 8%。给出三项改进。
2. 五分类任务中，“投诉建议”与“退款申请”经常混淆。给出诊断方向。
3. Few-shot 中五个示例全部是“售前咨询”。预测线上表现。
4. 表格输出中常有单元格内换行导致渲染错位。给出处理方式。

参考答案：

1. 改用结构化输出或 JSON schema 约束；对解析失败重试并回传错误；把非必填字段设为可选并在程序侧补默认值。
2. 标签定义粒度重叠：退款是动作，投诉是情绪表达，两者可并存。应改为按主诉归类，并给出边界样例。
3. 模型会严重偏向“售前咨询”，其余四类召回显著下降。应打散标签分布并补充边界样本。
4. 禁止单元格内换行，规定单行字数上限，超出内容截断并标注；或改为 JSON 输出由程序渲染。

## 2.9 小结

- 结构化输出分为结构正确与语义正确两层，约束解码只保证前者。
- 可靠性递进的手段是自然语言要求、Few-shot、结构化输出、解析校验加重试，生产环境应组合使用。
- 分类标签需满足互斥、完备、粒度一致，并包含兜底类别与边界样例。
- Few-shot 示例要覆盖边界、格式一致、真实且分布均衡，数量控制在 2 至 5 条。
- 失败处理分五级，应写入 PRD 的降级章节。
