# 进阶模式-Plan、ReAct 与思维链

本节说明三种让模型处理复杂任务的结构化方法，以及各自的适用条件与失败模式。三者解决的是同一个问题：单轮直接作答时，多步任务的误差会累积且无法中途检查。

## 3.1 单轮作答的局限

给出问题，要求模型直接输出答案，在简单任务上足够。任务变复杂后出现三个问题：

1. 中间步骤不可见，出错后无法定位。
2. 无法获取外部信息，只能依赖模型记忆。
3. 无法中途干预，整段重来成本高。

三种进阶模式分别针对不同问题：思维链让中间推理可见，Plan-and-Execute 让整体结构可审查，ReAct 让模型可以中途获取外部信息。

## 3.2 思维链（Chain-of-Thought）

做法是要求模型先写出推理过程，再给结论，例如“先列出判断依据，再给出结论”。

适用条件：任务需要多个中间量，例如多条件判定、简单数学、逻辑排除。此时推理文本可以暴露错误位置，也提升准确率。

不适用条件：单一事实问答、格式转换类任务。这类任务加思维链只会增加 Token 与延迟，还可能生成看似合理但并不必要的推理。

一个需要警惕的现象：模型输出的推理文本不一定反映真实的计算过程。它可能是先得到结论，再补一段看似连贯的解释。因此思维链的价值在于可检查，不在于可信任；高风险场景不能因为“推理看起来对”就放过结论。

产品侧的处理：需要给用户展示推理时，应标注为“参考推理过程”，并提供核对来源的入口。合规场景可能需要隐藏推理文本，只展示结论与依据。

## 3.3 Plan-and-Execute

分两个阶段：第一阶段让模型输出计划，即步骤列表、每步目标与所需工具；第二阶段按步骤逐步执行，每步的输出作为下一步的输入。

| 阶段 | 产出 | 可干预点 |
|---|---|---|
| 计划 | 步骤清单、依赖关系、所需工具 | 可人工审阅、修改、拒绝 |
| 执行 | 每步结果 | 可逐步校验、失败可重试或跳过 |

优点：

1. 计划是结构化文本，可以审查和修改，风险在开始执行前就暴露。
2. 子任务相互独立时可以并行，缩短总耗时。
3. 计划与执行可以分层复用，同类任务只改执行细节。

缺点与风险：

1. 计划本身可能错误，第一步方向错了，后面全错。
2. 执行过程中情况变化，原计划失效，需要重规划机制。
3. 计划粒度过细会导致步骤数量膨胀，成本与延迟上升。

适用场景：步骤在任务开始时就能基本确定，例如报告生成、批量数据整理、多文档对比。这类任务适合先给出大纲再由人确认。

## 3.4 ReAct

ReAct 的结构是循环：思考（Thought）、行动（Action）、观察（Observation），然后根据观察结果进入下一轮思考。

```
Thought: 需要先查询订单状态
Action: query_order(order_id="...")
Observation: 状态为已签收，签收时间 2026-10-20
Thought: 已超过七天，需确认是否属于例外商品
Action: query_product_type(...)
Observation: 属于定制品
Thought: 定制品不适用无理由退货，可以给出结论
```

适用条件：信息不全、需要外部数据、需要试探性操作。客服、运维排查、资料检索都属于这类。

代价与风险：

1. 循环次数不可控，可能反复调用同一工具。
2. 每一步都追加到上下文，Token 消耗快速累积。
3. 模型可能忽略观察结果，继续按原假设推进。
4. 缺少明确的终止条件时，会出现空转。

因此 ReAct 必须配套产品约束：最大步数、单步超时、总成本上限、终止条件、失败后的人工接管。这些约束应写进配置，而不是指望模型自觉遵守。

## 3.5 三种模式的对比

| 模式 | 结构 | 适合的任务 | 主要代价 | 主要风险 |
|---|---|---|---|---|
| 思维链 | 单次生成内包含推理 | 多条件判定、简单推理 | Token 与延迟 | 推理文本是事后解释，不可尽信 |
| Plan-and-Execute | 先出计划，再分步执行 | 步骤可预先确定、子任务独立 | 计划与执行两轮成本 | 计划错误导致整体失败 |
| ReAct | 思考与行动交替循环 | 需要外部信息、需要试探 | 上下文膨胀、调用次数多 | 死循环、重复调用、忽略观测 |

组合方式在实践中更常见：外层用 Plan 确定框架与步骤，内层对需要探索的步骤用 ReAct，对需要判断的步骤用思维链。

## 3.6 常见失败模式

| 失败模式 | 表现 | 处理方式 |
|---|---|---|
| 死循环 | 反复调用同一工具或重复同一推理 | 最大步数限制、重复动作检测 |
| 计划漂移 | 执行中偏离原计划且未声明 | 每步校验是否对应计划项，偏离时重新规划 |
| 过早结束 | 未完成所有步骤就给出结论 | 检查完成条件，缺失步骤时要求补齐 |
| 忽略观测 | 工具返回与假设冲突，仍按假设继续 | 要求每步显式引用观测结果 |
| 上下文膨胀 | 步骤多后前文被挤出或注意力分散 | 每步输出结构化摘要，不保留原始全文 |

产品侧的通用做法是：把流程控制放在代码里，把判断交给模型。步骤数量、终止条件、重试策略由程序决定，模型只负责单个节点的判断与生成。

## 3.7 判断练习

判断下列任务最适合哪种模式，并说明理由。

1. 把一份 40 页合同拆成 12 个条款并逐一给出风险提示。
2. 客服判断用户诉求后，查询订单、物流、退款政策，再给出答复。
3. 根据一段产品描述判断是否符合上架规范。
4. 为用户生成一份包含市场分析、竞品对比、建议三部分的报告。

参考答案：

1. Plan-and-Execute。步骤可预先确定，拆分后各条款独立，适合先出计划再并行执行。
2. ReAct。需要多轮查询外部系统，信息逐步获得，适合思考与行动交替。
3. 思维链或单轮结构化输出。条件判定，中间推理需要可见以便复核，但不需要外部工具。
4. Plan-and-Execute 加 ReAct。先确定报告结构与资料需求，再对需要检索的章节使用循环调用。

## 3.8 小结

- 单轮作答在复杂任务上有三个局限：过程不可见、无法取外部信息、无法中途干预。
- 思维链让推理可见，适用于多条件推理，但不能把推理文本当作可信依据。
- Plan-and-Execute 把计划与执行分离，适合步骤可预先确定的任务，风险在计划本身。
- ReAct 通过思考与行动交替获取外部信息，必须配套最大步数、超时、成本上限与终止条件。
- 流程控制应由代码承担，模型只负责节点内的判断与生成。
