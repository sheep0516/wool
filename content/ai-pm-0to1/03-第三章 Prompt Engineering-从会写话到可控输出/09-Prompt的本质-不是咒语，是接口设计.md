# Prompt 的本质-不是咒语，是接口设计

本节说明 Prompt 的结构与写法。核心结论：Prompt 不改变模型能力，它定义的是任务边界、输入规范与输出契约，因此应按接口设计的方式写，而不是按“说好话”的方式写。

## 1.1 四要素

Prompt 由四部分组成，缺任何一项都会出现可预期的失败。

| 要素 | 作用 | 缺失时的典型表现 |
|---|---|---|
| 指令 | 说明要完成什么任务、判断标准是什么 | 答非所问，或按自己的理解自由发挥 |
| 上下文 | 背景、职责范围、可用资料的边界 | 使用通用知识作答，与业务规则不符 |
| 输入数据 | 本次要处理的具体内容 | 处理错对象，或凭空生成内容 |
| 输出格式 | 结构、字段、长度、语言 | 下游无法解析，需要人工二次整理 |

一个完整的例子，以退货资格判定为例：

```
[任务]
判断该订单是否符合七天无理由退货条件。

[规则]
1. 以签收时间为起点计算七天。
2. 定制品、生鲜、已拆封的贴身用品不适用。
3. 需提供购买凭证。

[输入]
订单信息：{{order_json}}
用户描述：{{user_text}}

[要求]
1. 先核对签收时间，再核对商品类型。
2. 仅依据以上规则与输入，不补充外部知识。
3. 信息不足时不做推断。

[输出]
严格输出以下 JSON，不要附加解释：
{"eligible": true | false | null, "reason": "", "missing_info": []}
```

这个例子体现了接口设计的三个特征：输入明确、规则封闭、输出有契约。

## 1.2 角色设定的实际作用

“你是一位有二十年经验的资深专家”这类写法，主要影响语气、术语密度与叙述视角，不提升事实准确率。模型并不会因为被赋予头衔而获得它没有的知识，也不会因此减少幻觉。

有效的角色设定写的是职责与边界，而不是形容词堆叠：

| 有效写法 | 无效写法 |
|---|---|
| 你的职责是核对信息并给出判定，不负责安慰用户 | 你是一位温暖、专业、有同理心的顶级客服 |
| 你只能使用提供的规则与订单信息，不得引用其他来源 | 你学识渊博，无所不知 |
| 无法判断时输出 null 并列出缺失字段 | 你一定要尽力给出答案 |
| 输出使用书面语，不使用感叹号 | 请用最亲切自然的语气回答 |

角色设定的价值在于压缩输出空间：明确职责范围后，模型自由发挥的空间变小，稳定性提高。

## 1.3 约束条件的写法

约束必须可检查。不可检查的约束等于没有约束。

| 类型 | 可检查的写法 | 不可检查的写法 |
|---|---|---|
| 长度 | 回答不超过 120 字 | 回答要简洁 |
| 结构 | 输出三个小节，标题固定为现状、原因、建议 | 结构清晰 |
| 内容 | 必须引用规则编号；禁止出现价格承诺 | 要专业准确 |
| 语言 | 使用书面语；不使用网络用语 | 语气得体 |
| 边界 | 资料未覆盖时输出“无法判断” | 尽量回答用户的问题 |

三条实践规则：

第一，约束数量要受控。核心约束超过七条后，模型对单条约束的遵循率会下降，因为约束之间在争夺注意力。多项要求应分层，把必须遵守的放在开头和结尾。

第二，约束冲突要有优先级。安全与合规高于输出格式，输出格式高于风格。Prompt 中应显式写明冲突时的取舍顺序，否则模型会自行选择。

第三，能用代码判断的规则不要写进 Prompt。金额校验、时间窗口计算、权限判断应由程序完成，模型只负责理解与组织语言。把确定性逻辑交给概率模型，是常见的架构错误。

## 1.4 Prompt 的分层

生产环境中的 Prompt 通常分为三层，权限与可信度不同：

| 层级 | 内容 | 可信度 | 变更频率 |
|---|---|---|---|
| 系统层 | 产品设定、职责、安全规则、输出契约 | 高，由产品维护 | 低，需版本管理 |
| 上下文层 | 检索资料、历史对话、用户画像 | 中，需标注来源 | 每次请求变化 |
| 用户层 | 用户当前输入 | 低，视为不可信 | 每次请求变化 |

分层的意义在于：系统层可以稳定缓存，降低成本；上下文层需要来源标记；用户层必须按不可信输入处理，其中的指令不能被当作系统指令执行（详见第4节）。

Prompt 属于配置，不属于代码，但仍需版本管理：记录版本号与变更原因，每次变更跑一遍评估集，上线采用灰度，保留回滚。没有评估的 Prompt 修改，本质上是在线上做实验。

## 1.5 常见误解

一、Prompt 写得越长越好。不成立。长度增加会稀释关键约束，并推高每次请求的输入成本。

二、加上“请一步一步思考”就能提升准确率。只在多步推理任务上有效，对简单任务会增加成本，也可能引入并不存在的推理步骤。

三、Prompt 可以替代业务逻辑。不成立。确定性规则应由代码实现，Prompt 只处理语言理解与表达。

四、换个更强的模型就不需要认真写 Prompt。不成立。强模型对模糊指令同样会自由发挥，输出契约仍然需要明确。

五、Prompt 改完直接上线，看用户反馈即可。不成立。缺少评估集的变更无法区分“变好”与“碰巧”。

## 1.6 判断练习

指出下列 Prompt 片段的问题并改写。

1. “你是一个专业的 AI 助手，请认真回答用户的问题，要准确、专业、友好。”
2. “根据用户问题判断意图，输出意图名称。”
3. “如果用户问的是退款，就告诉他可以退。”
4. “回答要简洁明了，不要啰嗦。”

参考答案：

1. 全是形容词，没有任务定义与边界。改写：明确可用资料范围、判定职责、无法回答时的行为、输出格式。
2. 缺少标签集合与判定标准，模型会自造标签。改写：列出封闭标签集，每个标签给出定义与一个边界样例，并规定无法归类时的取值。
3. 规则写死且未区分条件，与真实业务可能冲突。改写：给出完整判定规则，把时间窗口与商品类型交给代码校验，模型只输出待判定字段。
4. “简洁”不可度量。改写：回答不超过 120 字；不使用项目符号；先给结论再给理由。

## 1.7 小结

- Prompt 是接口设计，包含指令、上下文、输入数据、输出格式四要素。
- 角色设定影响语气与视角，不提升事实准确率；有效写法是定义职责与边界。
- 约束必须可检查，数量受控，冲突要有优先级，确定性规则交给代码。
- Prompt 分为系统层、上下文层、用户层，可信度不同，需版本管理与评估。
