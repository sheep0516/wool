# 持续跟踪前沿的机制

本节说明如何建立稳定的技术跟踪习惯，把“技术变化”翻译成“产品含义”，以及如何用 Vibe Coding 快速验证想法。

## 4.1 两种常见错误

| 错误 | 表现 | 后果 |
|---|---|---|
| 追热点 | 每个新模型、新框架都试一遍 | 时间碎片化，没有沉淀，判断被厂商宣传左右 |
| 完全不看 | 只用熟悉的一套方案 | 错过成本或能力边界的变化，方案逐渐过时 |

正确的做法介于两者之间：不追单个产品，关注能力边界的变化。

## 4.2 四个翻译问题

看到一条技术更新时，用四个问题把它翻译成产品含义：

| 问题 | 关注点 |
|---|---|
| 能力提升了什么 | 之前做不了的任务现在能做了吗 |
| 成本降了多少 | 哪些原本不划算的场景变得划算 |
| 延迟改善了吗 | 实时交互的可行性是否变化 |
| 边界变了什么 | 上下文长度、多模态、工具调用能力是否变化 |

判断原则：只有当变化影响到成本、能力或延迟中的至少一项，才值得更新自己的判断。仅仅是榜单排名变化，通常不影响产品决策。

可以维护一张表，把变化落到具体场景：

| 变化 | 影响的产品参数 | 需要重估的场景 |
|---|---|---|
| 上下文窗口扩大 | 单次可注入的资料量 | 长文档问答是否还需分块检索 |
| 小模型能力提升 | 路由中可用小模型的比例 | 高频简单任务是否能降本 |
| 推理模型延迟下降 | 实时场景可用性 | 复杂判定的交互是否可同步 |
| 工具调用可靠性提升 | 工具数量与复杂度 | 是否可减少工作流硬编码 |

## 4.3 信息源与筛选

| 类型 | 来源 | 使用方式 |
|---|---|---|
| 一手 | 官方文档、发布说明、模型卡、技术报告 | 确认能力与限制，优先采信 |
| 二手 | 工程博客、评测榜单、社区讨论 | 了解实际表现，注意选择偏差 |
| 实践 | 自己跑样本 | 最终判断依据 |

评测榜单要谨慎使用：榜单题目往往与真实业务分布不同，且存在针对榜单优化的可能。可靠的做法是用自己的评估集做同题测试。

## 4.4 Vibe Coding

定义：以自然语言与 AI 结对，快速搭建可运行的 Demo，用于验证想法。重点在“验证”，不在“交付”。

适用场景：

1. 验证一个交互形态是否成立，例如多轮澄清是否真的减少追问。
2. 验证技术可行性，例如某类文档能否被正确解析。
3. 制作内部工具，降低重复劳动。
4. 快速产出原型，用于需求评审或用户访谈。

不适合的场景：直接交付生产系统。Demo 与产品之间隔着权限、评估、成本、监控与运维五道关口。

| 维度 | Demo | 产品 |
|---|---|---|
| 权限 | 通常没有 | 按用户身份鉴权 |
| 评估 | 靠人工试几个例子 | 固定评估集与阈值 |
| 成本 | 不计 | 有预算与上限 |
| 失败处理 | 出错就重来 | 分类降级与兜底 |
| 运维 | 本地跑 | 监控、告警、回滚 |
| 合规 | 不考虑 | 数据、内容、留痕 |

一个具体的验证流程：

1. 先写验收标准，例如“20 条样本中至少 16 条可用”。
2. 用 AI 生成最小实现，只做核心链路。
3. 跑真实样本，记录失败类型。
4. 判断瓶颈在哪：能力不足、知识不足还是流程设计问题。
5. 得出结论：继续、改方向或放弃。

这个流程的价值是把“讨论可行性”变成“半天内得到结论”。

## 4.5 个人知识管理

建议维护三张表，随版本更新：

| 表 | 内容 | 更新频率 |
|---|---|---|
| 能力表 | 各类任务在当前模型下的表现与失败模式 | 每季度，或重大版本后 |
| 成本表 | 不同模型的单位成本与延迟 | 每季度 |
| 场景表 | 已评估的场景结论：可行、不可行、待验证 | 每个项目结束后 |

三张表合起来，就是个人的选型依据。没有它们，判断会依赖记忆与印象，容易受最近一次体验影响。

## 4.6 常见误解

一、跟踪前沿就是每天看新闻。不成立。新闻量大且重复，应关注边界变化。

二、新模型发布就应该立刻切换。不成立。需要回归评估，版本变化可能带来退化。

三、Vibe Coding 可以替代工程交付。不成立。它解决验证与原型，不解决权限、成本与运维。

四、评测榜单排名高就适合自己。不成立。榜单分布与业务分布不同，必须用自己的样本测。

五、前沿跟踪是个人兴趣，与工作无关。不成立。成本与能力边界的变化会直接改变产品方案的可行性。

## 4.7 判断练习

1. 某模型上下文窗口大幅扩大，产品团队想取消检索。应如何判断。
2. 一个榜单显示新模型全面领先，是否应直接替换线上模型。
3. 用 Vibe Coding 做出了一个可用的客服 Demo，能否直接给客户使用。
4. 团队只关注模型价格，不看能力与延迟变化。指出风险。

参考答案：

1. 先测算成本与延迟，再用评估集对比“全量塞入”与“检索”的效果；窗口扩大通常伴随成本上升与注意力衰减，不能直接取消检索。
2. 不应。需在自有评估集上分场景回归，确认无退化，并通过灰度验证后再切换。
3. 不能。Demo 缺少权限、评估、成本控制、失败兜底与监控，需完成这些再对外。
4. 会错过能力边界变化带来的新场景机会，也可能在延迟或稳定性上做出错误取舍。

## 4.8 小结

- 跟踪前沿既不能追热点，也不能完全不看，应关注能力、成本、延迟与边界的变化。
- 用四个翻译问题把技术更新转成产品含义，只有影响成本、能力或延迟时才更新判断。
- 信息源以一手文档与自测为主，评测榜单需谨慎使用。
- Vibe Coding 用于验证与原型，不用于生产交付；验证流程应先写验收标准再跑样本。
- 维护能力表、成本表、场景表三张表，形成个人的选型依据。
