# 知识库问答、智能客服、生成类产品的设计差异

本节对比三类最常见的 AI 产品，说明它们在核心链路、关键设计与指标上的差异。共同点是概率输出，不同点决定了各自的设计重心。

## 3.1 三类产品对比

| 维度 | 知识库问答 | 智能客服 | 生成类产品 |
|---|---|---|---|
| 目标 | 准确回答事实性问题 | 解决用户诉求、完成服务流程 | 产出可用内容 |
| 核心链路 | 检索、重排、生成、引用 | 意图识别、路由、查询、答复、转接 | 参数收集、生成、筛选、导出 |
| 关键设计 | 引用与权限 | 意图与转人工 | 参数与队列 |
| 主要指标 | 忠实度、引用准确率 | 解决率、满意度、误转率 | 采纳率、生成速度、成本 |
| 主要风险 | 答错、越权泄露 | 错误承诺、漏转人工 | 版权、内容安全、成本失控 |

三类产品的失败后果不同：知识库问答错在“说得不对”，智能客服错在“承诺了不该承诺的”，生成类产品错在“产出了不能用的东西”。因此兜底设计的重心也不同。

## 3.2 知识库问答

核心是两件事：答案有依据，访问有边界。

| 设计项 | 要求 |
|---|---|
| 引用 | 精确到段落或条款，默认折叠、可展开 |
| 无依据时 | 明确说明未找到，不给推测性结论 |
| 权限 | 检索阶段按用户身份过滤，摘要输出同样受限 |
| 冲突资料 | 并列展示不同版本或标注生效时间 |
| 覆盖度 | 明确知识责任人与更新流程 |

一个常被忽略的问题：用户问的问题知识库里有，但表述差异很大。此时不应简单回答“没有”，而应给出相近条目或建议换一种问法。这属于检索层的查询改写能力，也属于产品层的体验设计。

另一个问题：知识库问答不应承担推理任务。用户问“我这种情况能不能退”，需要结合规则与订单状态，属于工具调用或工作流，不是纯知识库能解决的。把这类问题硬塞给知识库问答，会导致模型在资料不足时自由发挥。

## 3.3 智能客服

智能客服的核心不是回答，而是把服务流程走完。

| 环节 | 设计要点 |
|---|---|
| 意图识别 | 覆盖主要诉求，明确兜底意图，不把未知问题硬分到已知类 |
| 参数收集 | 只收集办理所需的最少信息，缺什么问什么 |
| 系统查询 | 以用户身份查询，不做跨用户查询 |
| 答复 | 事实性内容附来源，承诺类内容需规则校验 |
| 转人工 | 明确触发条件，携带完整上下文 |
| 质检 | 抽样复核答复准确性、合规性与服务态度 |

转人工的触发条件应写死，不能交给模型临时判断：

1. 用户明确要求转人工。
2. 连续两轮未解决或意图未识别。
3. 涉及投诉、纠纷、赔付。
4. 涉及权限外的操作或敏感信息。
5. 情绪指标超过阈值。

两个常见指标误区：

第一，把“解决率”定义为“没有转人工”。这会让系统倾向硬扛，短期数据好看，长期满意度下降。解决率应基于事后回访或工单关闭状态。

第二，只考核速度不考核质量。响应快但答复错误率高，成本最终由人工返工承担。

服务指标与质量指标应分开看：

| 类别 | 指标 |
|---|---|
| 服务效率 | 首次响应时长、平均处理时长、并发承载 |
| 解决质量 | 一次解决率、返工率、满意度 |
| 转接质量 | 误转率、漏转率、转接后携带信息完整度 |
| 合规质量 | 承诺准确性、敏感信息泄露、违规话术 |

## 3.4 生成类产品

生成类产品解决的是“产出可用内容”，设计重心在控制与效率。

| 设计项 | 要求 |
|---|---|
| 参数 | 风格、长度、比例、语气、参考素材，提供预设而非空白 |
| 候选 | 一次生成多版，供选择，避免反复重试 |
| 队列 | 长任务异步执行，显示进度，支持取消与重试 |
| 成本 | 按分辨率、时长、候选数量计费，设置单用户额度 |
| 版权 | 明确素材来源与商用范围，提供合规提示 |
| 内容安全 | 输入与输出双向过滤，命中则拦截并说明 |

任务队列的设计要点：

1. 提交后立即返回任务标识，不阻塞界面。
2. 状态可见：排队中、生成中、已完成、失败。
3. 失败可重试，且重试不重复扣费。
4. 批量任务设置总量上限与并发上限。
5. 结果保留期限与存储策略明确。

成本控制的四个抓手：

| 抓手 | 做法 |
|---|---|
| 分辨率与时长 | 默认中等规格，高档位需显式选择 |
| 候选数量 | 默认一版，多版需用户主动选择 |
| 缓存 | 相同参数与提示的请求复用结果 |
| 额度 | 按用户或租户设置日、月上限 |

## 3.5 常见误解

一、三类产品只是界面不同，底层一样。不成立。核心链路、指标与兜底方式差异明显，复用同一套设计会同时踩三类坑。

二、知识库问答可以承担业务判定。不成立。判定需要规则与实时数据，知识库只提供依据。

三、客服的解决率等于未转人工率。不成立。硬扛会掩盖真实解决情况。

四、生成类产品的成本只取决于模型单价。不成立。分辨率、候选数量、重试与批量都会放大成本。

五、转人工越少越好。不成立。该转未转会带来投诉与信任损失。

## 3.6 判断练习

1. 知识库问答中，用户问“我这个订单能不能退”，系统只回答了退货政策。指出问题。
2. 智能客服把“投诉”识别为“售后咨询”，导致用户重复描述。指出改进点。
3. 生成类产品的用户频繁点击重新生成，单次任务成本是预算的三倍。给出三项措施。
4. 客服系统转人工率极低但满意度持续下降。分析原因。

参考答案：

1. 该问题需要订单状态与规则联合判定，属于工作流加工具调用。纯知识库只能回答规则，无法给出结论，应改为引导用户提供订单号后走判定流程。
2. 意图体系缺少投诉类或边界定义不清。应补充投诉意图与兜底意图，并规定投诉类直接进入人工队列。
3. 一是默认只生成一版，多版需显式选择；二是同参数请求缓存复用；三是设置单用户额度并对高频重试做提示。
4. 系统把可转人工的问题自行处理，短期转接率下降，但错误承诺与未解决诉求增加，导致满意度下滑。应放宽转接条件并按解决率而非转接率考核。

## 3.7 小结

- 三类产品在目标、链路、指标与风险上不同，不能用同一套设计。
- 知识库问答的核心是有依据与有边界，不做业务判定。
- 智能客服的核心是把服务流程走完，转人工条件应写死，指标要区分服务效率与解决质量。
- 生成类产品的核心是参数、队列与成本，需在分辨率、候选数量、缓存与额度上做控制。
- 解决率不能等同于未转人工率，该转未转会损害长期满意度。
