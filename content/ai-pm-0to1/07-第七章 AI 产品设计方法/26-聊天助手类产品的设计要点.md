# 聊天助手类产品的设计要点

本节讨论聊天助手在对话体验、上下文管理与异常兜底上的具体设计。聊天助手的难点不在“能不能回答”，而在“多轮之后还能不能保持可用”。

## 2.1 对话体验

| 环节 | 设计要点 |
|---|---|
| 首次进入 | 说明能力边界，给出三到五个真实示例问题 |
| 首轮输入 | 支持一句话表达，允许模糊，由系统追问 |
| 生成过程 | 流式输出，显示可中断按钮 |
| 多轮追问 | 一次只问一个问题，避免同时抛出多个字段 |
| 结果不满意 | 提供重新生成、换一种说法、转人工 |
| 会话结束 | 允许保存、重命名、清空上下文、新建会话 |

两个容易做错的地方：

第一，一次追问多个问题。用户面对“请提供订单号、下单时间、问题描述”时，通常只答一部分，导致二次追问，体验更差。正确做法是每次只问最关键的缺失项。

第二，流式输出不可中断。长回答生成到一半发现跑题，用户无法停止，只能等待。可中断是长输出的基本要求。

## 2.2 Prompt 与上下文策略

聊天助手的 Prompt 通常分三层组装：

| 层级 | 内容 | 变更频率 |
|---|---|---|
| 系统层 | 角色、能力边界、安全规则、输出格式 | 低，需版本管理 |
| 会话层 | 用户画像、当前任务状态、检索到的资料 | 每次请求变化 |
| 当前轮 | 用户本次输入 | 每轮变化 |

三个实践要求：

1. 系统层保持稳定，便于缓存，降低成本。
2. 关键事实（订单号、金额、日期）抽成结构化状态，每轮注入，不依赖历史文本。
3. 检索只在需要时触发，不是每轮都检索；闲聊轮次不检索可显著降本。

## 2.3 上下文管理

多轮对话中，上下文有三种处理动作：

| 动作 | 触发条件 | 做法 |
|---|---|---|
| 保留 | 近期相关轮次 | 完整保留最近若干轮 |
| 压缩 | 轮次超过阈值 | 摘要为结构化要点，丢弃寒暄 |
| 重开 | 话题切换或上下文污染 | 新建会话，保留任务关键事实 |

需要特别处理的是上下文污染。用户给出错误前提，例如“我上周买的那个退款已经批了吧”，模型可能顺着前提继续推演。正确做法是把用户表述当作待核实信息，与系统查询结果比对后再回应；发现冲突时明确纠正，而不是顺着说。

另一个问题是话题漂移。用户从退款问题转到物流问题再转到发票问题，历史越长噪声越多。产品上应允许用户显式开启新话题，系统侧识别到任务目标变更时也应重建任务状态。

## 2.4 异常兜底

| 异常 | 用户看到什么 | 系统行为 |
|---|---|---|
| 无依据可答 | 说明缺少什么信息，给替代路径 | 不调用模型自由生成，直接走兜底 |
| 生成超时 | 提示已超时，可重试或转人工 | 中止请求，记录超时 |
| 回答跑题 | 可重新生成或澄清 | 记录样本，用于后续优化 |
| 格式错误 | 不展示原始错误 | 解析失败则重试，仍失败返回兜底话术 |
| 工具调用失败 | 说明哪一步失败，给替代方案 | 按错误类型重试或降级 |
| 内容风险 | 拒绝并说明原因 | 触发安全审核，记录 |
| 用户情绪激烈 | 提供转人工入口 | 优先转接，不继续自动应答 |

兜底话术的写法有一条原则：说明原因加给出下一步。避免只道歉不解决问题，也避免统一使用“抱歉，我无法回答”这类无信息量的话。

反例与正例：

| 差 | 好 |
|---|---|
| 抱歉，我无法回答这个问题。 | 知识库中没有 2026 年后的保修条款，可以转接人工客服查询，或查看产品页的售后说明。 |
| 系统繁忙，请稍后再试。 | 当前查询排队较多，预计 30 秒后恢复；也可以先查看订单页的物流详情。 |

## 2.5 关键指标

| 指标 | 含义 | 用途 |
|---|---|---|
| 首答可用率 | 第一轮回答即可用的比例 | 衡量开场质量与检索准确度 |
| 平均追问次数 | 每任务需要用户补充信息的次数 | 衡量参数设计是否合理 |
| 会话完成率 | 任务在会话内被解决的比例 | 衡量整体可用性 |
| 转人工率 | 触发人工的比例 | 过高说明能力不足，过低可能存在漏转 |
| 差评率与原因分布 | 用户负反馈占比 | 定位具体失败类型 |
| 单会话成本 | Token 与调用成本 | 判断能否规模化 |

转人工率需要双向看：过高说明自助能力不足，过低则可能把本该转人工的问题硬扛下来，短期指标好看，长期损害信任。

## 2.6 常见误解

一、聊天助手的关键是话术自然。不成立。自然度只影响感受，可用性取决于能否解决任务、失败时能否给出路。

二、多轮对话越长越智能。不成立。轮次增加会放大上下文噪声与成本，多数任务应在三到五轮内完成。

三、把历史全部保留就是有记忆。不成立。关键事实需要结构化，历史文本会被稀释。

四、兜底就是道歉加转人工。不成立。兜底需要说明具体原因与可行替代方案。

五、转人工率越低越好。不成立。该转未转会显著降低信任与解决率。

## 2.7 判断练习

1. 用户第一轮就输入“帮我处理一下”，系统应如何回应。
2. 用户在第三轮说“就那个订单”，系统应如何处理。
3. 会话进行到第 15 轮，模型开始重复已确认的信息。给出两种处理。
4. 用户情绪激动并连续发送三条消息，产品应如何响应。

参考答案：

1. 不直接猜测，先给出两到三个最可能的意图候选并询问；或说明当前可处理的范围，请用户选择。
2. 从结构化任务状态中取最近的订单记录并回显确认，而不是凭对话历史推断；若无记录则追问订单号。
3. 一是压缩历史为结构化要点并保留关键事实；二是提示用户新建会话，同时把任务状态迁移过去。
4. 优先提供人工入口，自动应答降级为安抚加转接，不在情绪化场景继续多轮自动追问。

## 2.8 小结

- 对话体验的关键是空状态引导、单点追问、可中断的流式输出、随时可用的重来与转人工。
- Prompt 分系统层、会话层、当前轮三层组装，关键事实应结构化注入。
- 上下文有三种处理动作：保留、压缩、重开；需专门处理污染与话题漂移。
- 异常兜底遵循“说明原因加给出下一步”，避免无信息量的道歉。
- 指标要看首答可用率、追问次数、完成率、转人工率与单会话成本，转人工率需双向解读。
