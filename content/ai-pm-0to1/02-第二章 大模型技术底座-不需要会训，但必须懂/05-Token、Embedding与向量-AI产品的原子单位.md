# Token、Embedding 与向量-AI 产品的原子单位

本节说明三个基础概念：Token 是模型的计量与处理单位，Embedding 是语义的数值表示，向量库是检索的存储设施。三者的关系决定了产品的成本、上下文上限与检索质量。


## 1.1 Token：模型的输入输出单位

模型不直接处理字符，而是处理 Token。文本先经分词器切分为 Token，再转为编号输入模型。一个 Token 可能是完整单词、词根、单字或字节片段。

常见量级（不同分词器存在差异，只能作估算用）：

| 语言 | 大致对应关系 |
|---|---|
| 中文 | 1 个汉字约 1 至 2 个 Token |
| 英文 | 1 个 Token 约 4 个字符，约 0.75 个单词 |
| 代码与符号 | 缩进、括号、标点各自可能占用 Token |

Token 决定三件事。

第一，计费。主流 API 按输入 Token 与输出 Token 分别计价，输出通常单价更高。缓存命中的输入、批量接口往往有折扣，具体价格随模型版本变化。

第二，上下文上限。模型一次能处理的 Token 总数有上限，输入与输出共享这个额度。超出后必须截断、摘要或改为检索。

第三，延迟。输入越长，首字延迟通常越高；输出越长，总耗时越长。流式输出只改善感知，不减少总计算量。

一个成本估算的例子：日均 1000 次请求，每次输入 1200 Token、输出 300 Token。先算出日总量，再乘以对应单价，得到日成本，乘以 30 得到月成本。这个数字在立项阶段就应算出，而不是上线后再看账单。

| 容易忽略的成本项 | 说明 |
|---|---|
| 历史对话 | 多轮对话每轮都会重发此前内容，成本随轮次累积 |
| 检索片段 | RAG 每次注入若干资料片段，条数与长度直接推高输入量 |
| 系统提示词 | 固定的长提示词会随每次请求重复计费 |
| 重试与自我检查 | 多轮自检、多 Agent 协作属于乘法级放大 |
| 图片与音频 | 多模态输入按分辨率或时长折算 Token |

产品侧可以控制的部分：限制上下文轮数、压缩或摘要历史、控制检索返回条数与片段长度、按任务复杂度选择模型。

## 1.2 Embedding：语义的数值表示

Embedding 是把一段文本映射为一个固定长度的数值向量，例如 1024 维或 1536 维。核心性质是：语义相近的文本，向量在空间中距离更近。

判断相近程度通常用余弦相似度，取值越接近 1 表示方向越一致。

几个必须知道的属性：

1. Embedding 模型与生成模型是两类模型。生成模型负责产出文本，Embedding 模型只负责把文本转成向量，不能互换。
2. 同一个知识库必须使用同一个 Embedding 模型。换模型后向量空间改变，旧向量与新查询不可比，必须全量重建索引。
3. 向量相似不等于答案正确。它衡量的是语义接近程度，不判断内容是否相关、是否过时、是否有权限。
4. 跨语言能力取决于模型。中文查询检索英文资料的效果需要实测，不能假定成立。

产品含义：检索质量的上限由 Embedding 模型、分块方式、查询改写共同决定。更换生成模型通常不影响索引，更换 Embedding 模型则必须重建知识库，这是架构上要提前留出的成本。

## 1.3 向量库与向量检索

向量数据库负责存储向量及其元数据，并提供近似最近邻检索（ANN）。常见实现包括 Milvus、pgvector、Qdrant、FAISS。选型差异主要在规模、过滤能力、运维成本，不在算法原理。

检索不只是“算距离取前几条”，实际链路通常包含：

1. 查询改写：把用户口语补全为可检索的表述，解决指代与省略
2. 召回：向量检索加关键词检索并行
3. 过滤：按租户、权限、时间、文档类型等元数据筛选
4. 重排：用更贵的模型对候选重新排序
5. 截断：按条数与长度组装进上下文

纯向量检索在两类情况下会失准：专有名词与编号（产品型号、法规条款号、订单号），以及精确措辞要求。这两类依靠关键词检索更可靠，所以生产系统普遍采用向量加关键词的混合检索。

元数据设计是产品决策，不是工程细节。至少需要回答：文档属于哪个部门或租户、谁能看到、什么时间生效、来源是什么。如果元数据缺失，后续的权限控制与答案溯源都无法实现。

增量更新同样需要设计：新增文档多久入库、修改文档是否覆盖旧向量、删除文档如何同步清理。知识库不更新，答案就会长期停留在过期信息上。

## 1.4 三个概念的关系

| 概念 | 作用 | 影响的产品指标 |
|---|---|---|
| Token | 计量与处理单位 | 成本、上下文上限、延迟 |
| Embedding | 语义的向量表示 | 检索召回质量 |
| 向量库 | 存储与近邻检索 | 检索速度、权限过滤、可扩展性 |

一句话串联：文本被切成 Token 送进模型计费，同时被 Embedding 转成向量存入向量库；用户提问时，问题同样转为向量，从库中取回相近片段，再与问题一起作为 Token 送进模型生成答案。

## 1.5 常见误解

一、Token 等于字或词。不成立。Token 是分词器切出的片段，中英文对应关系不同，不同模型的切法也不同。

二、Token 数可以直接用字符数乘以固定系数换算。只能粗略估算。涉及预算时应以实际分词结果或接口返回的用量为准。

三、向量检索可以替代关键词搜索。不成立。精确编号、专有名词、条款号等场景，关键词更可靠，生产环境通常两者并用。

四、更换更好的生成模型就能提升检索效果。不成立。检索效果由 Embedding 模型、分块、查询改写、重排决定，与生成模型无关。

五、知识库越大越好。不成立。无关内容会稀释召回精度，并推高上下文成本。覆盖度与精度需要平衡。

## 1.6 判断练习

1. 一个客服系统每天 2000 次会话，平均 8 轮，每轮携带全部历史。指出最可能的成本问题及两种改法。
2. 团队把 Embedding 模型从 A 换成 B，检索结果明显变差。给出原因判断。
3. 用户搜索“GB/T 12345 标准第 4.2 条”，纯向量检索命中率低。给出改进方向。
4. 知识库中同一制度的三个版本同时存在。指出会产生什么现象。

参考答案：

1. 历史全量重发导致输入 Token 随轮次线性累积。改法：滑动窗口限制轮数、对早期对话做摘要后再注入、把事实性信息改存为结构化状态。
2. 旧索引与旧向量由模型 A 生成，新查询由模型 B 生成，向量空间不一致。需要全量重建索引，不能只替换查询侧。
3. 编号与条款号属于精确匹配需求，应加入关键词检索或混合检索，并对编号字段做结构化过滤。
4. 检索可能返回相互冲突的多个版本，模型会择一作答或混合表述。需要在入库时标注版本与生效时间，并在检索侧按时间过滤。

## 1.7 小结

- Token 是计费、上下文上限与延迟的计量单位，成本估算要计入历史对话、检索片段、系统提示词与重试。
- Embedding 把语义转为向量，衡量相似而非正确；换 Embedding 模型必须重建索引。
- 向量库负责存储与近邻检索，生产环境通常采用向量加关键词的混合检索，并依赖元数据实现过滤与权限。
- 检索链路的完整形态是查询改写、召回、过滤、重排、截断，任一环节缺失都会降低答案质量。
