# 对话大模型的生成原理-极简版

本节用最小必要的技术细节，解释模型为什么会产生不确定输出、为什么会被上下文影响、以及温度与上下文窗口这类参数如何改变产品行为。


## 2.1 自回归生成：逐个预测下一个 Token

对话模型的工作方式是自回归：给定已有文本，预测下一个 Token 的概率分布，从中取出一个，追加到文本末尾，再重复这一过程。

由此可以直接推出几个产品现象：

1. 输出是逐个 Token 生成的，所以流式输出能让人看到文字逐步出现。
2. 每次只做一步概率选择，没有全局规划。长链条任务中前一步的小偏差会累积，表现为中途跑偏或前后矛盾。
3. 模型不执行计算，它是在预测“看起来正确的算式结果”。多位数算术、精确计数、日期推演容易出错。
4. 同一个问题问两次得到不同答案，来源是采样环节，不是故障。

## 2.2 Transformer 与注意力：上下文如何影响输出

Transformer 的核心是注意力机制：生成每个 Token 时，模型会根据当前上下文决定重点关注哪些位置。多层堆叠后，模型能够利用长距离依赖，把前文的设定、术语、约束带到后文。

产品侧需要记住三点，不需要理解公式。

第一，上下文里的内容会实际影响输出。系统提示词、检索片段、历史对话、用户当前输入，都在同一上下文中竞争注意力。

第二，注意力存在衰减与位置偏差。关键信息放在极长的上下文中部时，被使用的概率会下降，常被称为“中间遗忘”。实践含义是：最重要的约束与资料应放在开头或结尾，检索片段不宜过多。

第三，上下文是共享且有限的。输入与输出共用窗口额度，塞入更多资料必然挤压历史与输出的空间。

## 2.3 预训练、微调与对齐

模型的训练分三个阶段，每个阶段解决的问题不同。

| 阶段 | 做法 | 解决的问题 | 产品含义 |
|---|---|---|---|
| 预训练 | 在海量文本上做下一个 Token 预测 | 获得语言能力与世界知识的统计规律 | 决定了基础能力上限，产品侧无法改变 |
| 监督微调（SFT） | 用指令与回答样本继续训练 | 学会按指令形式作答 | 可定制风格、格式、领域表达方式 |
| 对齐（RLHF、DPO 等） | 按人类偏好调整输出倾向 | 更有用、更少有害、更符合预期 | 影响拒答尺度与表达倾向，也带来迎合倾向 |

需要区分微调与 RAG 的适用边界，这是选型中最常被混淆的一处：

| 维度 | 微调 | RAG |
|---|---|---|
| 解决什么 | 风格、格式、领域表达习惯 | 事实、私有知识、时效信息 |
| 知识更新 | 需重新训练，周期长 | 改文档即可，分钟级生效 |
| 成本 | 训练成本加推理部署成本 | 主要是检索与额外输入 Token |
| 可解释性 | 弱，难追溯来源 | 强，可给出来源片段 |
| 典型失败 | 学到错误细节，放大幻觉 | 检索不到或检索到无关内容 |

结论：微调改“怎么说”，RAG 补“说什么”。需要频繁更新的私有事实，不应指望用微调解决。

## 2.4 三个关键参数：上下文窗口、温度、top-p

上下文窗口（context window）指一次请求可容纳的 Token 总数上限。窗口越大，可放入的资料越多，但同时带来成本上升、首字延迟增加与注意力衰减。窗口不是越大越好，合理做法是按任务确定最小必要上下文。

温度（temperature）控制采样分布的陡峭程度。接近 0 时输出更集中、更可复现；升高后低概率候选被选中的机会增加，输出更发散。

top-p（核采样）按累积概率截断候选集合。例如 top-p 为 0.9 时，只从累计概率达到 90% 的最小候选集合中采样，其余候选被排除。它与温度作用于不同环节，常配合使用。

| 任务类型 | 温度建议 | 原因 |
|---|---|---|
| 信息抽取、分类、结构化输出 | 低，接近 0 | 需要稳定、可复现、格式一致 |
| 事实问答、客服回复 | 低到中 | 需要稳定措辞，避免自由发挥 |
| 文案撰写、创意生成、头脑风暴 | 中到高 | 需要多样性，允许不同表达 |
| 多候选方案生成 | 高，并多次采样 | 主动扩大输出空间 |

一个需要说明的细节：温度设为 0 并不保证完全一致。批处理、并行计算与浮点误差会导致微小差异，在长输出与工具调用场景中可能表现为不同结果。因此不能以“温度 0”作为可复现性的保证，评估仍需多次采样。

## 2.5 常见误解

一、模型会记住与我的历史对话。不成立。单次请求不包含此前会话，跨会话记忆需要产品侧显式存储与检索。

二、上下文窗口够大，就可以把全部文档直接塞进去。不成立。成本、延迟与注意力衰减都会恶化，且窗口仍有上限。资料规模大时应走检索。

三、模型“理解”了内容，和人的理解一样。不成立。它掌握的是语言中的统计规律，不具备事实核查与逻辑验证机制。

四、提高温度会让模型更聪明。不成立。温度只改变输出的多样性，不改变知识与推理能力。

五、微调可以让模型学会最新政策。多数情况下不成立。频繁变化的事实应通过检索或工具注入。

## 2.6 判断练习

1. 一个合同信息抽取任务，输出 JSON，偶发字段缺失与格式错误。指出两个最该调整的参数或手段。
2. 一个文案生成产品，用户抱怨每次生成的内容都差不多。指出调整方向。
3. 客服助手在第 12 轮对话后开始忘记用户的订单号。给出两种改法。
4. 团队把 200 页手册全文塞入上下文回答产品咨询，成本高且答案质量不稳定。给出改进方案。

参考答案：

1. 降低温度以提升稳定性；同时用结构化输出约束（JSON schema 或函数调用）代替自然语言要求，并在解析层做校验与重试。
2. 提高温度并允许 top-p 放宽，同时提供风格、长度、角度等显式参数，必要时一次生成多个候选供选择。
3. 把订单号等关键事实抽成结构化状态并在每轮注入；或对历史做摘要压缩，保留事实、丢弃寒暄。
4. 改为检索式：分块入库，按问题召回若干片段，控制注入条数与长度；把最关键的约束放在提示词首尾。

## 2.7 小结

- 生成是逐个 Token 的概率采样，因此输出天然存在波动，长链条任务会累积偏差。
- 注意力使上下文直接影响输出，关键信息应放在首尾，片段数量要受控。
- 预训练决定能力上限，微调改表达方式，RAG 补事实，三者不可互相替代。
- 温度控制稳定性与多样性，top-p 控制候选范围，温度 0 也不保证完全可复现。
- 上下文窗口是成本、延迟与质量三者之间的权衡，不是越大越好。
