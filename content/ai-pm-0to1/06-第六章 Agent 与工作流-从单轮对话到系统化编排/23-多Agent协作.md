# 多 Agent 协作

本节讨论多 Agent 的分工方式、协作模式与状态传递，以及由此产生的失败模式。核心观点：多 Agent 的价值来自职责单一化，代价来自协调成本。

## 3.1 为什么要拆成多个 Agent

单个 Agent 承担全部任务时，会出现三个问题：

1. 提示词膨胀。售前、售后、订单、投诉的规则混在一起，约束互相干扰，遵循率下降。
2. 工具过多。工具集过大导致选择错误率上升。
3. 权限混淆。一个 Agent 同时拥有查询与退款权限，一旦被诱导，损失范围扩大。

拆分后，每个 Agent 只处理一个业务域，提示词更短、工具更少、权限更小。这是拆分的主要收益。

## 3.2 三种分工方式

| 方式 | 划分依据 | 例子 | 适用 |
|---|---|---|---|
| 按业务域 | 业务场景 | 售前、售后、订单、投诉 | 业务边界清晰、工单类型稳定 |
| 按角色 | 职能 | 规划者、执行者、审核者 | 任务复杂、需要质量把关 |
| 按技能 | 能力 | 检索、计算、写作、翻译 | 能力可复用、组合灵活 |

按业务域拆分最常见，也最容易运维，因为每个域有明确的责任人与指标。按角色拆分适合高风险流程，审核者可以对执行结果做二次检查。按技能拆分更接近工具组合，未必需要独立 Agent，用工作流节点即可。

## 3.3 四种协作模式

| 模式 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| 路由（主管分发） | 一个调度者判断意图，交给对应 Agent | 责任清晰，用户只面对一个入口 | 调度判错会导致整条链路走错 |
| 交接（handoff） | A 完成后把任务与上下文交给 B | 流程自然，适合分阶段任务 | 交接次数多时信息易丢失 |
| 并行 | 多个 Agent 同时处理不同子任务 | 缩短总耗时 | 结果合并需要仲裁规则 |
| 审核 | 执行者产出，审核者检查 | 提高质量，适合高风险 | 成本与延迟翻倍 |

实际系统常组合：主管路由，各业务 Agent 内部用并行处理子任务，高风险操作用审核 Agent 复核。

## 3.4 状态传递

多 Agent 失效的最常见原因是状态传递不完整。两个 Agent 之间只传一句自然语言描述，接收方无法确认哪些事实已核实、哪些是推测。

正确做法是维护一份共享状态，并显式传递：

| 字段 | 内容 |
|---|---|
| 任务目标 | 用户到底要解决什么 |
| 已确认事实 | 经系统查询或用户明确确认的信息，附来源 |
| 待确认信息 | 尚缺的参数与需要澄清的点 |
| 已完成动作 | 已调用的工具与结果 |
| 待办 | 下一步应做什么 |
| 风险标记 | 是否涉及资金、权限、投诉等 |

三条要求：

1. 事实与推测分开。模型推断的内容必须标记为未确认，不能与查询结果混在一起。
2. 交接结构化。用固定字段，不用自由文本，便于程序校验与日志记录。
3. 状态有版本。多 Agent 并行修改时，需要避免覆盖；冲突时以确认过的事实为准。

## 3.5 失败模式

| 失败 | 表现 | 原因 |
|---|---|---|
| 责任不清 | 用户的问题在多个 Agent 间来回转发 | 边界重叠，缺少唯一责任人 |
| 踢皮球 | 每个 Agent 都说“不是我负责” | 缺少兜底 Agent 与升级规则 |
| 信息丢失 | 后一个 Agent 重复询问已提供的信息 | 状态未传递或未结构化 |
| 重复劳动 | 多次查询同一数据 | 缺少共享状态与缓存 |
| 成本放大 | 一次请求触发十余次模型调用 | 层级过深、无预算上限 |
| 结论冲突 | 两个 Agent 给出不同答案 | 缺少仲裁规则 |

## 3.6 设计规则

1. 单一职责。每个 Agent 只负责一类任务，边界用一句话能说清。
2. 明确入口与出口。用户只面对一个入口，所有 Agent 的输出统一由出口层返回。
3. 交接显式。每次交接都传结构化状态，并记录交接原因。
4. 层级受控。最多两到三层，层数越多，错误放大与延迟越严重。
5. 有仲裁者。结论冲突时由规则或审核 Agent 决定，不能并列返回两个答案。
6. 有兜底。任何 Agent 无法处理时，统一交由兜底 Agent 或转人工。
7. 有预算。整体设定调用次数、Token 与时长上限。

## 3.7 什么时候不该拆

以下情况单 Agent 加工作流更合适：

1. 业务域只有一个，任务类型单一。
2. 请求量小，协调成本高于收益。
3. 各环节强依赖，必须顺序执行且共享大量上下文。
4. 团队缺少多 Agent 的监控与调试能力。

判断标准是：拆开后是否真的降低了单点复杂度。如果每个 Agent 仍需了解全部业务，只是把提示词复制了几份，拆分没有意义，只会增加成本与失败点。

## 3.8 判断练习

1. 售前与售后被拆成两个 Agent，用户问“买过的产品能否退”时在两个 Agent 间来回跳。指出问题与改法。
2. 一个订票流程由五个 Agent 串联，每层都重复询问出行日期。指出原因。
3. 两个 Agent 并行查询政策，给出互相矛盾的结论。给出处理方案。
4. 一个只有三类工单的小型客服，是否应拆成三个 Agent。

参考答案：

1. 边界重叠且缺少兜底与仲裁。应明确“已购商品的退换”归售后，售前仅做转交；补充统一的兜底 Agent 与升级规则。
2. 状态未结构化传递，交接只传了自然语言摘要，后序 Agent 无法确认已有信息。应建立共享状态并显式传递已确认事实。
3. 缺少仲裁规则。应指定一个审核或仲裁环节，按确认过的事实与来源优先级裁决，不接受并列返回两个答案。
4. 通常不必。业务域少、请求量有限时，单 Agent 分三条工作流分支更简单，拆分只会增加协调成本。

## 3.9 小结

- 多 Agent 的收益来自职责单一化：提示词更短、工具更少、权限更小。
- 分工可按业务域、角色、技能划分，业务域划分最常见也最易运维。
- 协作模式包括路由、交接、并行、审核，实践中常组合使用。
- 状态传递必须结构化，事实与推测分开，避免自由文本交接。
- 主要失败模式是责任不清、踢皮球、信息丢失、重复劳动、成本放大与结论冲突，需要靠单一职责、显式交接、仲裁与兜底来解决。
- 拆分是否值得，取决于是否真的降低了单点复杂度。
