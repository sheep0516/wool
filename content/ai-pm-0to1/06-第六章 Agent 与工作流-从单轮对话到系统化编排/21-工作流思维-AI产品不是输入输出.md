# 工作流思维-AI 产品不是输入输出

本节说明企业级 AI 应用的实际结构，以及为什么用单个 Prompt 做不出来。核心观点：AI 产品的形态通常是一条多节点流程，而不是一次请求得到一次响应。

## 1.1 一个真实产品的节点

以“退货处理助手”为例，用户输入一句话之后，系统实际要做的事远不止一次生成。

```
用户输入
  ↓
意图识别（退款 / 咨询 / 投诉）
  ↓
来源路由（内部知识库 / 订单系统 / 人工）
  ↓
权限校验（是否为本人订单）
  ↓
检索规则 + 查询订单 + 查询物流
  ↓
判定（是否符合条件，规则引擎）
  ↓
生成回复（附引用）
  ↓
输出校验（敏感信息、格式、一致性）
  ↓
回复 / 转人工
```

每一步都可能失败，每一步都需要单独的输入输出约定。若把整条链路塞进一个 Prompt，任何一步出错都无法定位，也无法单独替换。

企业级 AI 应用常见的节点类型：

| 节点类型 | 作用 | 实现方式 |
|---|---|---|
| 意图识别 | 判断用户要做什么 | 小模型或分类规则 |
| 路由 | 决定走哪条流程、调用哪些工具 | 规则或分类模型 |
| 检索 | 取回相关知识与资料 | RAG |
| 权限校验 | 确认可访问范围 | 确定性代码 |
| 数据查询 | 获取实时结构化数据 | 工具调用 |
| 判定 | 按规则得出结论 | 规则引擎，而非模型 |
| 生成 | 组织语言输出 | 大模型 |
| 校验 | 检查格式、来源、敏感信息 | 代码加规则 |
| 兜底 | 失败时转人工或降级 | 流程控制 |

## 1.2 为什么不能用一个 Prompt

单 Prompt 方案在原型阶段可行，进入生产后会暴露五个问题。

1. 不可控。所有逻辑藏在自然语言里，改一处可能影响其他部分。
2. 不可测。无法对单个环节做回归测试，只能整体看结果。
3. 不可观测。出错时不知道是检索、判定还是生成环节出的问题。
4. 不可优化。想降低某类错误的成本，无从下手。
5. 成本不可控。每次请求都跑完整流程，简单问题也付出最高成本。

工作流的价值正是把这些环节拆开，让每一段可以独立设计、独立测试、独立替换。

## 1.3 工作流与单轮生成的对比

| 维度 | 单轮生成 | 多节点工作流 |
|---|---|---|
| 可控性 | 低，逻辑隐含在文本里 | 高，节点边界明确 |
| 可测试性 | 只能端到端测 | 可按节点测 |
| 可观测性 | 只有一个结果 | 每步有输入输出记录 |
| 成本 | 一律按最复杂路径计费 | 可按节点选模型，简单路径低成本 |
| 开发成本 | 低 | 较高，需要编排与状态管理 |
| 适用任务 | 单步、低风险 | 多步骤、需权限与校验 |

判断标准：如果任务需要访问多个系统、需要权限控制、需要按条件分支、需要对结果做校验，就应该做成工作流。只有单轮问答、无副作用、无须溯源的场景，才适合单 Prompt。

## 1.4 节点设计的核心原则

第一，能确定性完成的交给代码。金额计算、时间窗口、权限判断、状态流转，都应写成规则，不要让模型参与。模型只处理需要理解自然语言的部分。

第二，模型节点要有明确的输入输出契约。每个节点输入什么字段、输出什么结构，应固定下来，便于替换模型与做回归。

第三，分支条件显式化。不要指望模型在生成时顺手决定走哪条路径，路由应作为独立节点，输出明确的枚举值。

第四，每个节点都要有失败出口。检索为空、查询失败、校验不通过，都应定义下一步，而不是让流程中断或让模型自由发挥。

## 1.5 编排工具的作用与边界

Dify、Coze 这类可视化编排工具，价值在于把流程结构化：节点、连线、变量、条件分支可见，调试时可以逐节点查看输入输出，同类流程可以复用为模板。

它们不能解决的部分同样要清楚：

| 工具能解决 | 工具不能解决 |
|---|---|
| 流程编排与节点复用 | 知识库内容质量 |
| 各节点的输入输出可见 | 评估集与效果标准 |
| 简单的条件分支与变量传递 | 复杂业务规则与权限体系 |
| 快速搭建与调试 | 长期运营、版本管理与成本控制 |

因此编排工具适合用来理解结构、验证链路，生产落地仍需要自己处理知识治理、权限、评估与监控。

## 1.6 工作流的六段结构

一个可复用的工作流骨架包含六段：

1. 入口：接收输入，做基础清洗与长度限制。
2. 路由：识别意图，确定流程分支与可用工具集。
3. 执行：检索、查询、调用工具，获得证据。
4. 判定：按规则得出结论，模型不参与规则判断。
5. 生成：把结论组织成用户可读的回答，附来源。
6. 出口：校验输出，成功则返回，失败则降级或转人工。

六段之外还需要横切能力：日志记录、耗时统计、成本统计、异常告警。这些能力不参与业务逻辑，但决定产品能否长期运维。

## 1.7 常见误解

一、工作流只是把 Prompt 拆成几段。不成立。拆分带来的是可控性、可测性与可观测性，不只是形式变化。

二、可视化编排工具可以直接上生产。不成立。工具解决编排，权限、评估、成本、运营仍需单独建设。

三、节点越多越专业。不成立。节点增加会提高延迟与故障点，应按必要拆分。

四、模型可以承担规则判断。不成立。规则判断应交由代码，模型只做理解与表达。

五、工作流不需要状态管理。不成立。多节点之间需要传递结构化状态，否则会出现信息丢失与重复查询。

## 1.8 判断练习

判断下列产品应做成单 Prompt 还是多节点工作流。

1. 把一段会议记录整理成纪要。
2. 客服判断用户诉求后查询订单、核对政策、给出答复。
3. 把商品描述翻译成英文。
4. 员工报销单据的合规初筛。
5. 根据一段文字生成三条朋友圈文案。

参考答案：

1. 单 Prompt。单步生成，无外部系统、无权限、无副作用。
2. 多节点工作流。涉及意图识别、权限校验、数据查询、规则判定与生成。
3. 单 Prompt。单步转换，输出可直接使用。
4. 多节点工作流。涉及票据解析、规则校验、权限与留痕，且需要可追溯。
5. 单 Prompt。纯生成任务，容错高。

## 1.9 小结

- 企业级 AI 应用通常由意图识别、路由、检索、权限校验、查询、判定、生成、校验、兜底等节点组成。
- 单 Prompt 的五个问题是不可控、不可测、不可观测、不可优化、成本不可控。
- 节点设计原则是确定性逻辑交给代码、模型节点有输入输出契约、分支显式化、每个节点有失败出口。
- 编排工具解决结构与调试，不解决知识质量、评估、权限与运营。
- 任务涉及多系统、权限、分支或校验时，应做成工作流。
