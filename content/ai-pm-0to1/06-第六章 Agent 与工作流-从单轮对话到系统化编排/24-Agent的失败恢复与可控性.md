# Agent 的失败恢复与可控性

本节讨论 Agent 的失败类型、状态追踪、重试与人工接管，以及判断某个场景应当用 Agent 还是确定性工作流。

## 4.1 失败类型

| 类型 | 表现 | 处理方向 |
|---|---|---|
| 工具失败 | 超时、限流、业务拒绝 | 重试、改写参数、降级 |
| 推理错误 | 选错工具、参数填错、忽略观测 | 校验、限制工具集、结构化输出 |
| 循环 | 重复同一动作或原地打转 | 步数上限、重复检测 |
| 超时超预算 | 步骤过多，成本或时间超限 | 预算控制、提前终止 |
| 状态丢失 | 后续步骤缺少前序信息 | 结构化状态、检查点 |
| 越权 | 调用不该调用的工具或数据 | 权限层、白名单 |

前两类是模型问题，后四类是系统问题。系统问题应当由程序解决，而不是靠提示词提醒模型。

## 4.2 状态追踪

Agent 的任务应有明确的状态，而不是一串对话记录。

| 状态 | 含义 | 下一步 |
|---|---|---|
| 待执行 | 已接收任务，未开始 | 进入循环 |
| 执行中 | 正在调用工具或生成 | 等待结果或判断 |
| 待确认 | 需要用户确认或补充信息 | 等待用户 |
| 已完成 | 目标达成 | 输出结果 |
| 失败 | 超限或无法继续 | 降级或转人工 |
| 已接管 | 人工已接手 | 由人处理 |

状态追踪需要三个机制：

1. 检查点。每完成一个关键步骤就记录状态与中间结果，失败后可从检查点恢复，避免整条链路重跑。
2. 事件日志。记录每次工具调用、参数、结果、耗时，用于排查与审计。
3. 幂等键。写操作带幂等键，恢复或重试时不重复执行。

## 4.3 重试策略

重试不是越多越好。错误应先分类，再决定是否重试。

| 错误类型 | 是否重试 | 说明 |
|---|---|---|
| 网络超时 | 可重试，需幂等保护 | 可能已成功执行，重试前先查状态 |
| 限流 | 可重试，退避等待 | 立即重试会加剧限流 |
| 参数错误 | 修正后重试一次 | 需模型或程序修正参数 |
| 业务拒绝 | 不重试 | 重试不会改变结果，应解释原因 |
| 权限拒绝 | 不重试 | 重复尝试可能触发风控 |

四条通用规则：设置最大次数（通常两到三次）；采用指数退避；区分读操作与写操作；失败后必须进入明确的降级路径，不允许模型自行编造结果。

## 4.4 人工接管

触发接管的四个条件：

1. 高风险操作。涉及资金、权限、不可逆动作。
2. 连续失败。同一环节重试若干次仍失败。
3. 低置信。模型输出不确定，或多个 Agent 结论冲突。
4. 用户主动要求。任何时刻用户都能要求转人工。

接管时不能只给人一句“用户有问题”，需要移交完整上下文：

| 移交内容 | 作用 |
|---|---|
| 任务目标 | 用户要解决什么 |
| 已确认事实 | 已查询到的数据与来源 |
| 已完成动作 | 调用过哪些工具、结果如何 |
| 待办与阻塞点 | 卡在哪一步、缺什么信息 |
| 风险标记 | 是否涉及资金、投诉、敏感数据 |

缺少这份移交清单，人工接管等于从头再来，用户体验会比直接用人工更差。

## 4.5 可控性的五个约束

| 约束 | 作用 | 典型设置 |
|---|---|---|
| 步数上限 | 防止循环与无限探索 | 单任务最多若干次工具调用 |
| 时间上限 | 控制用户等待 | 整体超时后转兜底 |
| 成本上限 | 防止费用失控 | 单次会话 Token 预算 |
| 工具白名单 | 限制可调用范围 | 按意图开放子集 |
| 输出校验 | 阻止错误或敏感内容流出 | 格式、来源、敏感信息检查 |

这五项应写在执行配置里，由程序强制执行。任何一项缺失，都意味着模型的行为没有边界。

## 4.6 什么场景适合 Agent

| 适合 Agent | 只适合确定性工作流 |
|---|---|
| 步骤数量与顺序不确定 | 步骤固定、顺序确定 |
| 需要根据中间结果调整方向 | 每步输入输出已明确 |
| 需要探索、试错、多轮查询 | 一次查询即可获得全部信息 |
| 容错较高，错误可被发现与纠正 | 错误代价高且不可逆 |
| 请求量适中，成本可承受 | 高频调用，成本敏感 |

一个实用判断顺序：

1. 步骤能否预先写死。能，则用工作流，不必上 Agent。
2. 是否需要根据观测结果改变下一步。不需要，用工作流。
3. 出错的代价是否可承受。不能承受，则把 Agent 限制在“提议”角色，执行由人或规则完成。
4. 成本是否可接受。动态路径通常意味着更高的 Token 消耗与更长的延迟。

多数企业场景的正确形态是工作流为主、Agent 为辅：固定流程由工作流控制，只在少数需要探索的节点内使用 Agent，并为其设定步数与成本上限。

## 4.7 常见误解

一、Agent 比工作流更先进。不成立。二者适配不同任务，确定性任务用 Agent 只会增加不可控性。

二、加了最大步数限制就不会出问题。不成立。还需要重复检测、成本预算与失败出口。

三、人工接管随时可以插入。不成立。接管需要上下文移交机制，否则接手的人无法继续。

四、失败就让 Agent 重试到成功。不成立。业务拒绝类错误重试无效，且可能触发风控。

五、状态记录在对话历史里就够了。不成立。对话历史会膨胀且不可结构化查询，任务状态应独立存储。

## 4.8 判断练习

1. 一个报销审批 Agent 连续三次修改参数仍未通过校验。应如何处理。
2. 用户要求转人工，但坐席只收到一句“用户咨询报销”。指出缺陷。
3. 一个查询类 Agent 单次会话调用了 14 次工具，成本异常。给出三项约束。
4. 月度对账流程，步骤固定且有明确校验规则。是否应做成 Agent。

参考答案：

1. 参数错误属于可修正类，但已达重试上限，应停止自动重试，转入待确认状态，向用户说明缺什么，或转人工。
2. 缺少上下文移交。应传递任务目标、已确认事实、已完成动作、阻塞点与风险标记。
3. 设置步数上限、单次会话成本预算、重复动作检测；同时限制工具白名单，减少无效探索。
4. 不适合。步骤固定、规则明确，应使用确定性工作流，Agent 只会引入不可控与额外成本。

## 4.9 小结

- 失败分六类，模型问题靠校验与约束解决，系统问题靠状态管理、预算与权限解决。
- 任务状态应有明确流转，配合检查点、事件日志与幂等键。
- 重试需先分类，设置次数上限与退避，写操作必须幂等。
- 人工接管需要完整上下文移交，否则等于从头开始。
- 可控性依赖五项约束：步数、时间、成本、工具白名单、输出校验。
- 步骤可预先写死、错误代价高、调用高频的场景，应使用确定性工作流而非 Agent。
