# 安全护栏与人工兜底

本节说明输入过滤、输出审核、人工复核的设计，以及“可解释的拒绝”的写法。护栏的目标不是让模型永不犯错，而是让错误不产生不可挽回的后果。

## 4.1 四层结构

| 层级 | 位置 | 作用 | 主要局限 |
|---|---|---|---|
| 输入过滤 | 请求进入前 | 拦截明显违规与攻击性输入 | 误杀与漏检并存 |
| 生成约束 | 生成过程中 | 通过提示与工具限制输出空间 | 可被更强指令绕过 |
| 输出审核 | 生成之后 | 拦截违规、敏感与格式错误 | 依赖规则覆盖度 |
| 人工复核 | 高风险或低置信 | 由人做最终判断 | 成本高，有时效要求 |

四层不是互为备份，而是各管一段。后一层能兜住前一层漏掉的问题，但任何单独一层都不能提供完整保障。

## 4.2 输入过滤

| 手段 | 做法 | 说明 |
|---|---|---|
| 长度与频率限制 | 限制单次输入长度、单用户请求频率 | 防止滥用与成本攻击 |
| 敏感词与模式匹配 | 关键词、正则匹配 | 快但误杀率高，需配合语境 |
| 上传文件扫描 | 类型、大小、内容检查 | 防止恶意文件与超大文件 |
| 注入模式检测 | 识别“忽略以上指令”类表达 | 只能拦截已知模式 |
| 身份与权限校验 | 校验用户是否可访问该场景 | 属于架构层，优先级最高 |

输入过滤的核心问题是误杀。过滤过严会让正常用户被拦，过滤过松则形同虚设。实践中的做法是分级：明确违规直接拦截，可疑内容降级处理（例如只回答通用信息），并记录以便复核。

## 4.3 输出审核

输出审核通常包含三类检查：

1. 规则检查。敏感词、个人信息格式（手机号、身份证号、银行卡号）、内部标识、链接白名单。
2. 一致性检查。答案是否引用了所依据的资料，关键数值是否出现在来源中。
3. 模型审核。用另一个模型判断内容是否违规、是否有害、是否符合要求。

处理方式分三档：

| 档位 | 处理 | 适用 |
|---|---|---|
| 拦截 | 不展示，替换为兜底文案 | 明确违规、泄露敏感信息 |
| 降级 | 展示简化版或去掉敏感部分 | 部分内容有问题 |
| 提示 | 展示但加风险提示 | 内容不确定、需要用户判断 |

完全拦截会损失可用性，完全放行会带来风险。分级处理是兼顾两者的唯一方式，但需要明确每一档的判定标准，避免工程临时决定。

## 4.4 人工复核

触发条件应写死，不交给模型判断：

1. 高风险场景：医疗、法律、金融、人事决策。
2. 不可逆操作：退款、删除、授权。
3. 低置信度：模型给出不确定标记，或多个结论冲突。
4. 内容审核命中：自动审核无法确定是否违规。
5. 用户申诉：用户对结果提出异议。

复核界面需要提供三样东西：

| 内容 | 作用 |
|---|---|
| 原始请求与上下文 | 让人理解用户到底要什么 |
| 依据材料与引用 | 让人核对结论是否有据 |
| 系统建议与置信标记 | 减少重复劳动，但不替代判断 |

复核还需要时效承诺。若复核排队超过用户可接受时间，用户会直接放弃，护栏就变成了障碍。应为不同风险等级设定不同的响应时限。

## 4.5 可解释的拒绝

拒绝不能是一句“抱歉，我无法回答”。可解释的拒绝应包含四要素：

1. 说明原因。是缺少依据、超出能力范围，还是涉及敏感内容。
2. 说明边界。让用户知道哪些可以问、哪些不可以。
3. 给出替代路径。转人工、换一种问法、查看文档。
4. 保留反馈渠道。用户可以申诉或报告错误。

| 场景 | 差的拒绝 | 好的拒绝 |
|---|---|---|
| 知识库无覆盖 | 抱歉，我无法回答。 | 知识库中没有 2026 年后的保修条款。可以转接人工客服，或查看产品页的售后说明。 |
| 超出能力范围 | 这个问题我不能处理。 | 我不能给出法律意见。可以为你整理相关条款原文，具体判断请咨询法务。 |
| 内容敏感 | 请求被拒绝。 | 该请求涉及他人账户信息，出于隐私保护无法处理。如需查询本人账户，请先完成身份验证。 |
| 置信度低 | 无法确定。 | 目前没有找到明确依据。以下两条规则可能相关，建议核对后再决定，或转人工确认。 |

拒绝的粒度也要按场景调整。面向内部员工的工具可以说明具体规则编号；面向外部用户的产品应避免暴露内部结构。

## 4.6 护栏的评估

护栏本身需要评估，否则无法知道是否有效。

| 指标 | 含义 |
|---|---|
| 拦截准确率 | 被拦截的内容中真正违规的比例 |
| 漏检率 | 违规内容未被拦截的比例 |
| 误杀率 | 正常内容被拦截的比例 |
| 覆盖率 | 护栏覆盖的场景与语言范围 |
| 复核时效 | 人工复核的平均与最长处理时间 |

评估方法包括红队测试：由专门的测试人员尝试用各种表达绕过护栏，记录成功案例并补入测试集。红队测试应定期进行，而不是上线前做一次。

## 4.7 常见误解

一、加了敏感词库就完成了内容安全。不成立。变体、隐语、多语言都能绕过，需要多层结构与模型审核。

二、护栏越严格越安全。不成立。误杀会损害可用性，用户会转向不受限制的渠道。

三、人工复核可以覆盖所有风险。不成立。复核成本高、有时效限制，只能用于高风险或抽样。

四、拒绝时越模糊越安全。不成立。无信息量的拒绝会让用户反复尝试或直接流失。

五、护栏上线后不需要维护。不成立。攻击方式与业务内容都在变化，需要持续更新规则与测试集。

## 4.8 判断练习

1. 用户问“帮我查一下我同事的工资”，系统应如何回应。
2. 一个医疗问答产品，模型给出了用药剂量建议。属于哪一层失效，应如何补。
3. 内容审核模型把正常医学术语判为违规，导致大量误杀。给出两项改进。
4. 用户对拒绝理由不满，反复尝试不同说法。产品应如何处理。

参考答案：

1. 明确拒绝并说明原因：涉及他人隐私，无法查询；如需查询本人薪资，可引导至个人信息页面或人事系统。不暴露是否存在该记录。
2. 生成约束与人工复核失效。应在提示层限制不给具体剂量，输出层识别剂量类表述并降级为“请遵医嘱”，并要求涉及用药建议的内容进入人工复核。
3. 引入领域白名单与上下文判断，区分正常医学术语与违规内容；同时把误杀样本加入测试集，调整模型审核阈值。
4. 记录多次尝试行为，累计达到阈值后转人工并说明可处理的边界；同时对拒绝文案做统一优化，减少用户反复试探的动机。

## 4.9 小结

- 护栏分四层：输入过滤、生成约束、输出审核、人工复核，各管一段，不能单靠任何一层。
- 输入过滤要分级处理，兼顾误杀与漏检；权限校验属于架构层，优先级最高。
- 输出审核包含规则、一致性与模型审核三类，处理分拦截、降级、提示三档。
- 人工复核需写死触发条件、提供完整依据与时效承诺。
- 可解释的拒绝包含说明原因、说明边界、给出替代路径、保留反馈渠道四要素。
- 护栏自身要用拦截准确率、漏检率、误杀率与复核时效评估，并定期做红队测试。
