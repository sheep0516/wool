# 作品集整合与面试表达

本节说明如何把四个项目整理成可核验的作品集，以及在面试中如何表达。核心原则：用决策与数据说明能力，不用形容词说明热情。

## 5.1 单个项目的五段结构

每个项目压缩成一页，固定五段：

| 段落 | 要回答的问题 | 篇幅 |
|---|---|---|
| 问题 | 谁的什么问题，现状如何，为什么值得做 | 三到五句 |
| 方案 | 链路是什么，关键节点如何设计 | 一张流程图加说明 |
| 技术决策 | 有哪些备选，为什么选这个，代价是什么 | 三到五条 |
| 评估结果 | 用什么指标、多少样本、达到什么水平 | 一张表 |
| 复盘 | 哪些判断错了，如何调整，还剩什么问题 | 三到五条 |

五段中，“技术决策”与“复盘”最能体现水平。方案本身可以抄，决策理由与失败经验无法抄。

## 5.2 技术决策的写法

每条决策写成“备选、选择、理由、代价”四项：

| 决策 | 写法示例 |
|---|---|
| 分块方式 | 备选固定长度与按条款切分；选择按条款；理由是制度类问题依赖条款号定位，固定长度会切断限定条件；代价是实现复杂度上升，需处理跨条款引用 |
| 是否重排 | 备选直接取前 k 条与加重排；选择先不加，实测后加；理由是先验证召回上限，避免过早增加延迟；代价是需要多跑一轮评估 |
| 拒答策略 | 备选允许模型自答与强制拒答；选择强制拒答；理由是避免掩盖知识缺口；代价是误拒率上升，需要单独监控 |

四条信息齐全的决策，能让人看出你考虑过代价。只写“我们选择了方案 A”的决策，看不出判断力。

## 5.3 评估结果的呈现

不要只写“效果良好”。给出四个要素：样本量、指标、阈值、结论。

| 指标 | 样本量 | 结果 | 阈值 | 结论 |
|---|---|---|---|---|
| 检索命中率 | 120 | 83% | 80% | 达标 |
| 引用准确率 | 120 | 91% | 90% | 达标 |
| 误拒率 | 30 | 17% | 不高于 10% | 未达标，已定位为分块过细 |
| 单次成本 | 500 次实测 | 已测算 | 预算内 | 达标 |

未达标项要写出来并说明后续处理。全部达标的报告通常意味着评估集太简单或标准定得太低。

## 5.4 作品集组件

| 组件 | 作用 | 注意 |
|---|---|---|
| PRD | 展示需求与验收能力 | 突出能力边界、评估方案、降级策略三章 |
| 知识库方案 | 展示 RAG 设计能力 | 含分块策略、元数据、更新流程 |
| Agent 方案 | 展示编排与可控性设计 | 含状态机、失败恢复、预算设置 |
| 成本测算表 | 展示商业判断 | 含单次成本、月度预算、优化记录 |
| 评估报告 | 展示评估能力 | 含样本构成、指标、失败分析 |

提交时不需要全部放上去，按岗位选择三到四件。应用层岗位优先 PRD 与评估报告；平台层岗位优先 Agent 方案与接口规范；行业岗位优先知识库方案与合规设计。

## 5.5 面试表达结构

用“背景、任务、决策、结果、复盘”五段，每段一到两分钟：

1. 背景：一句话说明业务场景与约束。
2. 任务：你负责的部分与目标指标。
3. 决策：两到三个关键技术或产品决策及理由。
4. 结果：量化结果，包含未达标项。
5. 复盘：如果重做会改什么。

常见追问与准备方向：

| 追问 | 准备什么 |
|---|---|
| 为什么不用另一种技术路线 | 备选方案的代价与实测对比 |
| 效果怎么衡量 | 评估集构成、指标定义、阈值来源 |
| 出错时怎么办 | 失败分类与兜底路径 |
| 成本多少 | 测算方法与优化前后的对比 |
| 权限怎么控制 | 检索侧过滤、身份透传、审计 |
| 如果规模扩大十倍 | 瓶颈在哪，先优化哪一层 |

## 5.6 表达的三个原则

第一，数据可解释。说“准确率 83%”时，要能说明样本量、判定标准、谁标注。说不清来源的数字，反而会成为追问的缺口。

第二，区分事实与推测。项目里哪些是实测、哪些是估算、哪些是假设，要能分开说。把估算说成实测，一旦被追问就会失去信任。

第三，保留失败。全部成功的项目不可信。说明一个判断失误以及如何修正，比罗列成果更有说服力。

## 5.7 简历写法

| 差的写法 | 好的写法 |
|---|---|
| 负责 AI 客服产品设计，效果显著 | 设计四类意图的客服流程，意图识别准确率 87%，误转率控制在 9%，单会话成本下降三成 |
| 精通 RAG 与 Agent | 主导知识库问答项目，建立 120 条评估集，检索命中率 83%，引用准确率 91% |
| 参与多个 AI 项目 | 独立完成三个项目：知识库问答、客服流程、Agent 编排，均含评估报告与成本测算 |

一条通用要求：每个数字都要能追溯到评估集或日志，不能是印象。

## 5.8 常见误解

一、作品集越多越好。不成立。三个做透的项目优于十个半成品。

二、界面漂亮就能证明能力。不成立。面试官关注决策与数据，界面只是载体。

三、只讲成功案例。不成立。缺少失败与复盘，反而显得缺乏真实经验。

四、指标越高越好。不成立。脱离样本量与判定标准的数字会被质疑，适度且可解释的数字更可信。

五、作品集只给面试用。不成立。整理过程本身就是对项目的二次复盘，常能发现遗漏的问题。

## 5.9 判断练习

1. 一个项目的引用准确率写的是 95%，但样本只有 20 条。如何改进表述。
2. 面试官问“为什么不用微调”，应如何回答。
3. 项目全部指标达标，没有任何失败。面试官会如何判断。
4. 三个项目都很小，文档量不足 50 篇，是否值得放进作品集。

参考答案：

1. 补充样本量与判定标准，或扩大样本后重新统计；若样本有限，应写明“小样本初测”，并说明置信度有限。
2. 说明知识更新频率高、需要溯源、微调成本与周期，以及实测对比结果；若有实测，给出两种方案在评估集上的差异。
3. 通常会怀疑评估集过于简单或标准过低。应主动补充未达标项与失败样本。
4. 值得。项目规模不决定说服力，决策质量与评估完整性更重要；但需说明范围收窄的理由。

## 5.10 小结

- 单个项目按问题、方案、技术决策、评估结果、复盘五段整理，一页完成。
- 技术决策写成“备选、选择、理由、代价”四项，评估结果写清样本量、指标、阈值与结论。
- 作品集按岗位选择组件，应用层重 PRD 与评估，平台层重 Agent 方案，行业层重知识库与合规。
- 面试按背景、任务、决策、结果、复盘五段表达，准备六类常见追问。
- 数据要可解释，事实与推测分开，保留失败与复盘。
