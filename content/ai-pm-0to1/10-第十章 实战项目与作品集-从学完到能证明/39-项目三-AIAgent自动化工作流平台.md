# 项目三-AI Agent 自动化工作流平台

本项目的目标是做出一个能完成多步骤任务、失败时可恢复、成本可控的编排系统。评估重点在工具调用、状态追踪与失败恢复。

## 3.1 范围定义

不要做通用平台。选两到三个真实场景，每个场景有明确的完成标准。

| 项目要素 | 建议 |
|---|---|
| 场景数量 | 2 至 3 个，例如工单分派、周报生成、资料核查 |
| 工具数量 | 每场景 3 至 6 个，单场景暴露总数不超过 10 个 |
| 步骤深度 | 3 至 6 步，便于定位问题 |
| 明确不做 | 无限自主探索、无人监督的资金操作 |

## 3.2 工具设计

| 要求 | 说明 |
|---|---|
| 命名一致 | 动词加对象，同对象用同一前缀 |
| 描述含边界 | 写明何时用、何时不用 |
| 参数精简 | 多用枚举与默认值，减少模型推算 |
| 返回统一 | 成功与失败使用同一结构，附摘要字段 |
| 错误分类 | 可重试、需补充、业务拒绝、权限拒绝、参数错误 |
| 幂等保护 | 写操作带幂等键 |

工具描述的有效性要在评估中验证：同一批任务下，模型选错工具的比例是多少。选错率高时，先改描述与工具集，不要先换模型。

## 3.3 编排结构

```
任务输入
  ↓
意图与任务识别
  ↓
计划生成（步骤、工具、依赖）→ 可人工审阅
  ↓
逐步执行（每步：校验 → 调用 → 记录 → 判断是否继续）
  ↓
状态更新（待执行 / 执行中 / 待确认 / 已完成 / 失败）
  ↓
结果校验 → 输出 / 转人工
```

流程控制放在代码里：步骤上限、超时、成本预算、终止条件。模型只负责节点内的判断与生成。

## 3.4 状态设计

共享状态应结构化，字段固定：

| 字段 | 内容 |
|---|---|
| 任务目标 | 用户要完成什么 |
| 已确认事实 | 经系统查询或用户确认的信息，附来源 |
| 待确认信息 | 缺失参数与需澄清项 |
| 已完成动作 | 调用过的工具与结果摘要 |
| 待办 | 剩余步骤 |
| 风险标记 | 是否涉及资金、权限、投诉 |

事实与推测必须分开存储。模型推断出的内容标记为未确认，不能与查询结果混用。

## 3.5 失败恢复

| 失败 | 处理 |
|---|---|
| 工具超时 | 重试两到三次，指数退避，写操作先查状态 |
| 参数错误 | 修正一次，仍失败转人工 |
| 业务拒绝 | 不重试，解释原因给替代路径 |
| 权限拒绝 | 停止调用，不暴露细节 |
| 循环 | 重复动作检测加步数上限，触发中止 |
| 状态丢失 | 从最近检查点恢复，不重跑全流程 |
| 连续失败 | 转人工并移交完整上下文 |

关键设计：检查点。每完成一步记录状态与中间结果，恢复时从检查点继续，避免重复调用与重复扣费。

## 3.6 评估方案

| 指标 | 定义 | 用途 |
|---|---|---|
| 任务成功率 | 端到端达成完成标准的比例 | 核心指标 |
| 平均步数 | 完成任务所需工具调用次数 | 衡量效率与成本 |
| 选错工具率 | 首步调用错误工具的比例 | 衡量工具设计质量 |
| 恢复成功率 | 失败后经重试或恢复完成的比例 | 衡量健壮性 |
| 单任务成本 | Token 与调用成本 | 判断能否规模化 |
| 人工接管率 | 转人工比例 | 衡量可控性 |

评估集应包含四类任务：正常任务、需多步推理的任务、工具会失败的任务、应被拒绝的任务。

## 3.7 成本控制

Agent 的成本是乘性放大，控制手段与放大机制对应：

| 放大来源 | 控制手段 |
|---|---|
| 循环轮次 | 步数上限、无新信息即中止 |
| 上下文累积 | 每步只保留结构化摘要 |
| 工具结果 | 裁剪字段，附摘要 |
| 推理文本 | 不把完整推理带入下一轮 |
| 多 Agent 交接 | 传状态，不传全量上下文 |
| 重试 | 分类重试，设次数上限 |

应设定单任务成本预算，超限时中止并转人工。

## 3.8 交付物清单

| 交付物 | 内容 |
|---|---|
| 平台 PRD | 场景清单、编排规则、状态机、验收标准 |
| 工具规范 | 每个工具的名称、描述、参数、返回、错误码 |
| Agent 方案 | 编排图、状态字段、恢复策略、预算设置 |
| 评估报告 | 成功率、步数、选错工具率、成本 |
| 成本测算 | 单任务成本、放大系数、优化记录 |

## 3.9 常见失败

| 失败 | 原因 | 改进 |
|---|---|---|
| 任务成功率低 | 计划生成错误或工具描述模糊 | 先做计划人工审阅，再优化描述 |
| 成本远超预算 | 上下文累积、重复调用 | 结构化摘要、步数上限、结果裁剪 |
| 死循环 | 无终止条件 | 重复检测、最大步数 |
| 写操作重复执行 | 无幂等键 | 加幂等键，重试前查状态 |
| 接管后无法继续 | 未移交上下文 | 固定移交字段 |

## 3.10 自检清单

1. 每个场景是否有明确的完成标准。
2. 工具描述是否写清了何时不用。
3. 是否设置了步数、时间、成本三项上限。
4. 状态是否结构化，事实与推测是否分开。
5. 写操作是否有幂等保护。
6. 接管是否携带完整上下文。

## 3.11 小结

- 项目范围应收窄到两到三个场景，每个场景有明确的完成标准。
- 工具设计决定选错率，描述要含适用边界，参数量要受控。
- 流程控制放在代码里，状态结构化，事实与推测分开。
- 失败恢复依赖检查点、幂等与分类重试，接管需要固定移交字段。
- 评估看任务成功率、平均步数、选错工具率、恢复成功率与单任务成本。
