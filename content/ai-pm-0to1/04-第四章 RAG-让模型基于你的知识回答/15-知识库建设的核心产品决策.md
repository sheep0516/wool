# 知识库建设的核心产品决策

本节讨论 RAG 项目中属于产品职责的三个决策：分块策略、知识覆盖度与精度之间的取舍、权限边界与引用设计。这三项决定知识库能否长期可用。

## 3.1 分块策略

分块不是一个技术参数，它直接决定答案质量。切分的粒度本质上是在“信息完整”与“检索精确”之间选择。

| 块大小 | 优点 | 缺点 | 典型后果 |
|---|---|---|---|
| 过小（一句或半段） | 召回归一化好，匹配精确 | 缺少上下文，指代无法解析 | 答案碎片化，模型自行补全造成错误 |
| 适中（一个完整小节） | 语义完整，可独立理解 | 可能包含无关内容 | 通用场景的常用选择 |
| 过大（整章或多节） | 上下文充足 | 噪声多，成本高，匹配度稀释 | 检索得分普遍偏低，重排难以区分 |

按文档类型给出的参考决策：

| 文档类型 | 建议 |
|---|---|
| 制度、规章、条款 | 按“条”或“款”切分，保留章节编号作为路径 |
| 产品手册、帮助文档 | 按标题层级切分，一个功能点一块 |
| 合同 | 按条款切分，保留条款号与所属章节 |
| 表格清单 | 转成结构化记录，每条记录带表头字段 |
| 会议纪要、报告 | 按议题或段落切分，附文档标题与日期 |
| 长篇小说、访谈 | 按语义边界切分，适当加大重叠 |

两个容易被忽略的细节：

第一，块内要保留标题路径。例如片段开头带上“第三章 售后管理 > 3.2 退款时限”。没有路径的片段，模型无法判断它属于哪条规则，也无法判断适用范围。

第二，表格的处理方式决定成败。按行切散会导致数字失去表头含义，模型会把“7 天”误认为其他指标。正确做法是把整张表作为一个块，或转成“字段名加值”的结构化文本。

父子块是一种常用折中：用小块参与检索以获得精确召回，命中后返回其所属的大块作为生成上下文。代价是占用更多 Token。

## 3.2 覆盖度与精度的取舍

覆盖度指知识库是否收录了回答所需的知识，以及是否及时更新。精度指检索返回的片段是否真正相关。二者方向相反：放宽召回提高覆盖但降低精度，收紧过滤提高精度但可能漏掉答案。

一个重要的诊断顺序：先确认知识是否存在，再检查检索是否命中。

| 现象 | 优先怀疑 | 检查方法 |
|---|---|---|
| 所有问题都答不上 | 知识库未建或未入库 | 直接查库中是否有该文档 |
| 某类问题答不上 | 覆盖缺口 | 用关键词在库中搜索原文 |
| 能搜到原文但检索不返回 | 分块、Embedding、查询改写 | 查看 top-k 命中与得分 |
| 返回片段相关但答非所问 | 分块粒度或重排 | 检查片段完整性 |
| 答案与文档冲突 | 版本混杂或资料本身错误 | 核对文档版本与生效时间 |

知识库运营比建库更重要。需要明确四项机制：

1. 责任人：每类知识指定维护人，避免无人更新。
2. 更新流程：新增、修订、下线的标准动作与生效时间。
3. 版本管理：同一制度保留历史版本，检索按生效时间过滤。
4. 质量抽检：定期抽样核对回答与原文一致性。

缺少这四项，知识库在上线三个月内就会开始失真。

## 3.3 权限边界

权限必须在检索侧实现，而不是在生成侧补救。原因很直接：如果无权内容进入了上下文，模型可能以摘要、改写、暗示的方式泄露，事后过滤无法完全挽回。

| 粒度 | 做法 | 成本 |
|---|---|---|
| 文档级 | 每个片段带可见范围元数据，检索时按用户身份过滤 | 低，最常用 |
| 段落级 | 敏感段落单独标记，命中时按权限剔除 | 中，需要段落级元数据 |
| 字段级 | 结构化数据按字段授权 | 高，需要与业务权限体系打通 |

三条实施要求：

1. 元数据在入库时写入，不能等到检索时推断。
2. 权限过滤发生在召回之后、组装之前，确保进入上下文的内容都已授权。
3. 多租户场景下，租户标识必须作为强制过滤条件，不能依赖查询语义。

还有一个容易忽略的泄露路径：答案摘要。即使用户无权查看原文，模型生成的摘要也可能包含敏感结论。因此权限判断要在片段层面生效，而不是只对“原文展示”做限制。

## 3.4 引用设计

引用的作用是让答案可核查，同时把事实判断的责任部分转移给用户。引用设计包含四个决策。

第一，引用粒度。文档级最粗，用户仍需自行定位；段落级或页码级更实用。制度类文档建议精确到条款号。

第二，引用与内容的一致性。模型可能引用 A 文档却使用 B 文档的内容。需要在输出层做校验：抽取答案中的关键实体与数值，回查是否出现在所引用的片段中。

第三，无引用时的行为。检索为空或全部低分时，产品应明确表示无法回答，并给出替代路径，而不是让模型凭自身知识作答。是否允许模型在无资料时回答，应在 PRD 中明确写出。

第四，引用如何呈现。默认折叠来源、点击展开原文是常见做法；高风险场景应默认展开，并要求用户确认已阅读依据。

| 场景 | 引用要求 |
|---|---|
| 内部制度问答 | 必须引用到条款，默认展开 |
| 产品帮助中心 | 引用到文档段落，折叠可展开 |
| 客服辅助 | 引用给坐席看，不直接展示给终端用户 |
| 创意生成 | 无需引用 |

## 3.5 常见误解

一、分块可以用一套参数适配所有文档。不成立。制度、手册、合同、表格的最优切分方式不同，需要按类型配置。

二、知识库建好就可以长期不管。不成立。缺少责任人与更新流程，知识会快速过期。

三、权限可以在生成后过滤。不成立。无权内容一旦进入上下文，就可能通过摘要泄露。

四、引用只是展示来源，不影响质量。不成立。引用准确性是 RAG 可信度的核心指标，错配比没有引用更糟。

五、覆盖度越高越好，宁可多收不可漏收。不成立。无关文档会稀释召回精度，并引入版本冲突。

## 3.6 判断练习

1. 一份 200 页的员工手册，问答系统经常答错“适用范围”。给出分块层面的改进。
2. 制度更新后，新旧版本同时在库中，回答出现矛盾条款。给出处理方案。
3. 客服助手在回答中暗示了用户无权查看的客户等级信息。指出权限设计的缺陷。
4. 答案正确但引用的是另一份相似文档。给出两个改进方向。

参考答案：

1. 按章节标题层级切分，每块开头保留章节路径与适用对象说明；必要时把适用范围作为元数据并参与过滤。
2. 入库时写入版本号与生效时间，检索时按当前时间过滤，历史版本仅对特定角色开放；建立下线流程。
3. 权限只在原文展示层做了限制，片段仍进入了上下文。应在召回后按片段元数据过滤，摘要类输出也要基于已授权片段生成。
4. 一是要求模型逐段标注引用并在提示词中强制对应；二是在输出层校验答案关键实体是否出现在所引片段中，不一致则重试或标注不确定。

## 3.7 小结

- 分块粒度在信息完整与检索精确之间取舍，应按文档类型配置，块内保留标题路径，表格不可切散。
- 覆盖度与精度方向相反，诊断顺序是先确认知识是否存在，再检查检索。
- 知识库需要责任人、更新流程、版本管理、质量抽检四项运营机制。
- 权限必须在检索侧按片段过滤，摘要输出同样受权限约束。
- 引用需明确粒度、校验一致性、规定无资料时的行为、设计呈现方式。
