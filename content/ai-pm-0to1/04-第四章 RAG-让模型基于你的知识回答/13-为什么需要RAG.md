# 为什么需要 RAG

本节说明模型的三个知识缺口，RAG 的基本机制，以及它能解决与不能解决的问题。目的是建立判断：什么样的产品需要 RAG，什么样的不需要。

## 1.1 模型的三个知识缺口

模型的知识来自训练语料，这带来三个结构性缺口。

| 缺口 | 表现 | 例子 |
|---|---|---|
| 私有知识缺失 | 企业内部制度、产品文档、客户资料从未出现在训练语料中 | 员工问“差旅报销上限是多少”，模型按通用印象作答 |
| 时效过期 | 知识有截止日期，此后发生的变化模型不知道 | 新政策、新价格、新版本功能 |
| 长尾知识薄弱 | 语料稀少的内容只能靠推测 | 冷门型号参数、地方性规定、内部代号 |

即便模型在训练中见过某条事实，也不能保证稳定复现。模型存储的是统计规律，不是权威台账；同一事实可能在不同表达下给出不同数值。因此涉及数字、日期、条款、编号的内容，都属于必须外部校验的范围。

## 1.2 RAG 的机制

RAG（检索增强生成）把回答流程改成两步：先在知识库中检索与问题相关的资料，再把资料作为上下文交给模型生成答案。

一句话概括：把“让模型回忆”改为“给模型资料”。

与另外两种做法对比：

| 做法 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| 依赖模型记忆 | 直接提问，模型凭训练知识回答 | 成本最低，无需建设 | 私有知识与时效信息不可用，无法溯源 |
| 全文塞入上下文 | 把文档全部放进提示词 | 实现简单，覆盖完整 | 成本高、延迟高、注意力衰减，窗口仍有上限 |
| RAG | 检索相关片段后注入 | 成本可控、可溯源、可更新、可按权限过滤 | 依赖检索质量，链路长，失败点更多 |

RAG 与传统搜索的区别在于服务对象：搜索把结果给人看，由人判断；RAG 把结果给模型用，由模型组织成答案。因此 RAG 的检索目标不是“列出相关文档”，而是“提供足以回答问题的证据”。

## 1.3 RAG 能解决什么

1. 私有知识可用。企业制度、产品手册、合同、工单记录都可以成为回答依据。
2. 时效可控。修改文档即可生效，不需要重新训练模型。
3. 可溯源。答案可以附带来源文档与段落，用户可核对。
4. 可权限控制。检索时按用户身份过滤，避免越权读取。
5. 可审计。能记录本次回答使用了哪些片段，便于问题追溯。

## 1.4 RAG 不能解决什么

| 局限 | 说明 |
|---|---|
| 推理能力 | 检索只提供资料，不提升模型的推理与计算能力 |
| 指令遵循 | 检索到的资料可能被模型忽略或误用 |
| 知识本身错误 | 文档写错了，RAG 会把错误答案说得更有依据 |
| 检索不到的内容 | 知识库没有、分块切断、表述差异过大时无法召回 |
| 跨文档聚合 | 需要统计多份文档并计算时，单次检索难以覆盖 |
| 长文档全局理解 | 摘要类任务需要覆盖全文，检索片段方式不适用 |

由此得到一条判断：RAG 改善的是知识的可得性与可溯源性，不改善模型的能力。用 RAG 去弥补推理能力不足，方向本身错误。

## 1.5 什么情况下不需要 RAG

1. 答案是稳定的通用知识，且不会随时间变化。
2. 知识量很小，可以直接写进系统提示词，维护成本低于建设检索链路。
3. 任务不需要引用来源，且对准确性要求不高，例如创意生成、头脑风暴。
4. 需要的是实时数据而非文档知识，此时应使用工具调用而不是 RAG。

判断标准可以简化为三问：知识是否私有或有时效，答案是否需要溯源，知识规模是否超过提示词可容纳的范围。三问均为否，就不必上 RAG。

## 1.6 常见误解

一、上了 RAG 就不会幻觉。不成立。RAG 减少了知识缺失型幻觉，但检索错误、资料错误、模型不按要求使用资料都会产生新的错误。

二、RAG 等于把文档丢进向量库。不成立。解析、分块、元数据、查询改写、重排、引用校验都影响最终质量，建库只是其中一步。

三、知识库越大效果越好。不成立。无关内容会稀释召回精度并推高上下文成本，覆盖与精度需要平衡。

四、RAG 可以替代微调。不成立。二者解决不同问题：RAG 补事实，微调改表达与格式。

五、RAG 的效果主要取决于模型。不成立。多数 RAG 问题出在知识库建设与检索链路，而不在生成模型。

## 1.7 判断练习

判断下列场景是否需要 RAG，并说明理由。

1. 公司内部制度问答助手。
2. 一个根据关键词生成营销口号的工具。
3. 客服查询用户当前订单的物流状态。
4. 产品手册版本差异对比助手。
5. 通用编程语法问答。

参考答案：

1. 需要。知识为私有且需溯源，制度还会更新。
2. 不需要。输出为创意内容，无固定事实依据，也不需要引用。
3. 不需要 RAG，需要工具调用。物流状态是实时结构化数据，应查询业务系统。
4. 需要。知识私有、跨版本，且需要精确引用到条款。
5. 通常不需要。属于稳定通用知识，模型已具备，错误可用通用校验兜底。

## 1.8 小结

- 模型的三个知识缺口是私有知识缺失、时效过期、长尾薄弱，且记忆本身不稳定。
- RAG 的机制是先检索再注入，把“让模型回忆”改为“给模型资料”。
- RAG 改善知识可得性与可溯源性，不改善推理与指令遵循能力。
- 知识私有、需要溯源、规模超出提示词容量时才需要 RAG；实时数据应走工具调用。
