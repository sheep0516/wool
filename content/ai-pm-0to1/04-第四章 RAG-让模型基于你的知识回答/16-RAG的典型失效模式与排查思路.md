# RAG 的典型失效模式与排查思路

本节把 RAG 的失败分成四类，给出按顺序的排查路径，并说明 RAG 不够用时应当补充什么能力。

## 4.1 四类失效

| 类别 | 表现 | 常见原因 |
|---|---|---|
| 检索不到 | 上下文里没有正确片段 | 知识不存在、表述不匹配、分块切断、过滤过严、Embedding 不适配 |
| 检索到但不用 | 片段在上下文里，答案却没用它 | 片段过多、顺序靠后、指令冲突、模型偏好自身知识 |
| 用了但答错 | 使用了片段，结论与资料不符 | 片段相互冲突、资料过期、跨片段推理错误、过度概括 |
| 引用错配 | 答案正确，标注来源不对 | 引用绑定缺失、片段相似导致错标 |

这四类的处理方式完全不同。因此排查的第一步不是改 Prompt，而是判断属于哪一类。

## 4.2 排查顺序

按以下顺序检查，每一步都能排除一类原因。

1. 知识是否存在。用原文关键词在库中直接搜索，确认文档已入库且解析文本正确。这一步能排除大量“模型不行”的误判。
2. 检索是否召回。查看该问题对应的 top-k 结果与相似度得分。若正确片段不在候选中，问题在召回侧。
3. 重排是否把正确片段排前。若在候选中但排名靠后，且最终因截断被丢弃，问题在重排或条数设置。
4. 上下文是否真的包含正确片段。检查最终注入的文本，确认没有被长度预算截掉，也没有被去重逻辑误删。
5. 模型是否引用。在上下文中显式保留片段编号，要求答案标注编号，可以直接判断是否使用。
6. 答案是否忠实。对照片段原文逐句核对，确认没有改写关键限定条件、没有混入自身知识。

要执行这套流程，日志必须记录五类信息：原始问题、改写后的查询、召回的片段与得分、最终注入的上下文、输出结果与用户反馈。缺少任何一项，排查会退化为猜测。

## 4.3 症状与处理对照

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 关键词能搜到，问答搜不到 | 查询改写偏离原意 | 关闭或弱化改写，检查改写提示词 |
| 编号、型号类问题命中差 | 纯向量检索 | 加入关键词检索，做混合召回 |
| 正确答案在候选中但排名靠后 | 得分区分度不足 | 引入重排，或调整分块粒度 |
| 片段相关但答非所问 | 块过小或缺少标题路径 | 加大块或改用父子块，补充路径 |
| 片段在上下文里但答案不用 | 条数过多、顺序靠后 | 减少条数，把高分片段置首尾 |
| 答案混入资料外内容 | 提示词未限制来源 | 强制只用所给资料，检索为空时拒答 |
| 同一问题两次答案不同 | 采样随机性、片段顺序变化 | 降低温度，固定片段排序规则 |
| 回答很快但总是套话 | 未命中却未拒答 | 设相似度阈值，低于阈值走兜底 |
| 新旧制度答案矛盾 | 版本未过滤 | 元数据加生效时间，检索时过滤 |

## 4.4 RAG 不够用的时候

RAG 只解决“知识从哪来”，以下需求需要补充其他能力。

| 需求 | 应补充 | 原因 |
|---|---|---|
| 改变语气、格式、术语习惯 | 微调或 Prompt 约束 | 属于表达方式问题，与知识无关 |
| 查询实时状态、执行操作 | 工具调用或 Agent | 需要访问业务系统，不是文档知识 |
| 大规模结构化统计 | 数据库查询 | 需要精确计算，检索片段无法保证 |
| 跨大量文档的全局总结 | 分层摘要或多轮检索 | 单次检索无法覆盖全文 |
| 多步骤任务编排 | 工作流或 Agent | 需要按顺序执行多个动作 |
| 高准确率的封闭问答 | RAG 加规则校验 | 检索提供依据，校验保证一致性 |

常见的组合形态：

1. RAG 加工具。先检索政策，再调用接口查询订单，两者结合给出判定。例如退货资格判断既需要规则也需要订单状态。
2. RAG 加工作流。检索只是流程中的一个节点，前后还有意图识别、权限校验、人工确认。
3. RAG 加微调。用微调固定输出格式与领域表达，用检索保证事实来源。

判断方法：如果失败原因是“不知道”，补 RAG；如果失败原因是“没做到”，补工具或工作流；如果失败原因是“说得不对”，补 Prompt 或微调。

## 4.5 评估的基本要求

RAG 的评估要拆成检索与生成两段，分别打分，否则无法定位问题。

| 对象 | 指标 | 说明 |
|---|---|---|
| 检索 | 命中率、召回率、排序位置 | 正确片段是否出现在 top-k 及其排名 |
| 生成 | 忠实度、完整性、引用准确率 | 答案是否依据片段、是否覆盖要点、引用是否对应 |
| 端到端 | 任务完成率、拒答正确率 | 用户是否得到可用答案，该拒答时是否拒答 |

评估集应包含四类样本：常见问题、边界问题、应当拒答的问题、以及包含诱导性表述的问题。第 8 章会展开具体构建方法。

## 4.6 常见误解

一、RAG 效果差就换更强的模型。多数情况下问题在检索，换模型只会让错误答案更流畅。

二、把召回条数调到 20 条以上就能解决漏检。条数增加会引入噪声与冲突，且推高成本，通常应在召回与重排环节解决。

三、让模型“如果资料里没有就说不知道”就能解决拒答。还需要相似度阈值与无结果分支，单靠提示词不稳定。

四、评估只看最终答案是否正确。不拆分检索与生成，无法知道该改哪一环。

五、RAG 与微调二选一。二者解决不同问题，可以同时使用。

## 4.7 判断练习

1. 用户问“发票抬头能改吗”，系统每次都回答“可以”，但制度规定开票后不可修改。判断失效类别并给出排查步骤。
2. 某型号参数问题长期命中相似型号文档。给出两项改进。
3. 上下文里明明有正确条款，答案却引用了另一条不相关条款。判断类别与改进方向。
4. 业务方要求“回答要更专业一些”，是否应该补 RAG。

参考答案：

1. 属于“用了但答错”，也可能是检索到过期或错误资料。排查顺序：确认制度文档是否入库且为最新版，检查命中片段，核对模型是否使用了该片段，最后检查提示词是否允许其凭自身知识作答。
2. 编号与型号属于精确匹配，应加入关键词检索做混合召回；同时为型号字段建立结构化过滤或元数据。
3. 引用错配。需在提示词中强制逐段标注引用编号，并在输出层校验答案关键实体是否出现在所引片段。
4. 不应。专业感属于表达方式，应通过 Prompt 约束或微调调整，RAG 只补知识，不改善表达风格。

## 4.8 小结

- 失效分四类：检索不到、检索到但不用、用了却答错、引用错配，处理方式各不相同。
- 排查顺序是查知识是否存在、查召回、查重排、查注入上下文、查是否引用、查是否忠实。
- 日志需记录问题、改写查询、召回片段与得分、注入上下文、输出与反馈。
- 失败原因是“不知道”补 RAG，“没做到”补工具或工作流，“说得不对”补 Prompt 或微调。
- 评估必须拆分检索与生成两段，否则无法定位问题。
