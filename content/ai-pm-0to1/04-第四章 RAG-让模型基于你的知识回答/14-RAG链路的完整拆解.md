# RAG 链路的完整拆解

本节把 RAG 拆成离线与在线两段，逐个环节说明作用与常见失败。理解链路的意义在于：出问题时能定位到具体环节，而不是笼统地归因为“模型不行”。

## 2.1 两段结构

| 阶段 | 触发时机 | 主要工作 | 影响 |
|---|---|---|---|
| 离线索引 | 文档入库时 | 解析、清洗、分块、增强、向量化、入库 | 决定知识能否被检索到 |
| 在线问答 | 每次请求 | 查询改写、召回、过滤、重排、组装、生成 | 决定单次回答的质量与成本 |

离线阶段的问题会在每次请求中重复出现，且难以在线修复。多数 RAG 质量问题源自离线阶段。

## 2.2 离线：文档摄入与索引

| 环节 | 做什么 | 常见失败 |
|---|---|---|
| 解析 | 从 PDF、Word、网页、表格、扫描件中提取文本与结构 | 扫描件无文字层、表格错行、图文混排顺序错乱 |
| 清洗 | 去掉页眉页脚、水印、重复内容、导航文字 | 清洗过度丢失关键信息，或清洗不足引入噪声 |
| 分块 | 把长文档切成可检索的片段 | 切断了完整语义，丢失表头与章节标题 |
| 增强 | 为片段补充标题、摘要、关键词、元数据 | 元数据缺失，导致无法过滤与溯源 |
| 向量化 | 用 Embedding 模型转为向量 | 模型与查询侧不一致，或对中文、专业术语表现差 |
| 入库 | 写入向量库并建立索引 | 增量更新缺失，删除不同步，版本混杂 |

解析是最容易被低估的环节。一份排版复杂的 PDF，如果解析后文字顺序错乱，后续分块、向量化、检索全部建立在错误文本上，再优化检索也无法补救。评估 RAG 时应先抽查解析结果文本，而不是直接看回答效果。

## 2.3 分块

分块指的是把文档切成检索的基本单位。它同时影响召回与生成：块太大，噪声多、成本高；块太小，语义不完整。

常见策略：

| 策略 | 做法 | 适用 |
|---|---|---|
| 固定长度 | 按 Token 或字符数切分，带重叠 | 结构不明显的纯文本 |
| 按结构 | 按标题、段落、表格行切分 | 有明确层级的手册、制度、合同 |
| 语义分块 | 按语义边界切分，通常借助模型判断 | 长篇叙述性文档 |
| 父子块 | 小块用于检索，命中后返回其所属大块用于生成 | 需要精确召回又要完整上下文的场景 |

几个实践要点：

1. 块内必须保留标题路径。片段脱离章节标题后，模型难以判断它属于哪条规则。
2. 表格不应按行切散。至少保证表头与数据行在同一块内，或转成结构化记录。
3. 设置适度重叠，避免边界处的句子被切断。
4. 块大小没有通用最优值，需要按文档类型与问题类型实测。

## 2.4 在线：检索与生成

| 环节 | 作用 | 常见失败 |
|---|---|---|
| 查询改写 | 补全指代、展开缩写、生成多个检索式 | 改写偏离原意，或过度扩写引入噪声 |
| 召回 | 向量检索与关键词检索并行取得候选 | 只做向量检索，编号与专有名词命中差 |
| 过滤 | 按权限、时间、文档类型筛除候选 | 过滤过严导致无结果，或元数据缺失无法过滤 |
| 重排 | 用更精细的模型对候选重新排序 | 重排模型与业务语料不匹配，反而降低排序质量 |
| 组装 | 去重、排序、按长度预算截断后注入上下文 | 条数过多导致注意力分散，或截断掉关键片段 |
| 生成 | 基于资料组织答案并标注来源 | 忽略资料、混合自身知识、引用错配 |

重排的价值在于：召回阶段追求覆盖，容易带回大量弱相关片段；重排用更高成本的模型在少量候选上做精细判断，把真正有用的片段排到前面。代价是额外延迟。

装组环节有两个决策：注入多少条、按什么顺序。条数过多会分散注意力并推高成本，通常控制在 3 至 8 条；顺序上，得分最高的放在开头或结尾更稳妥。

## 2.5 延迟与成本预算

| 环节 | 大致量级 | 说明 |
|---|---|---|
| 查询改写 | 数十到数百毫秒 | 若调用模型生成多个检索式，成本增加 |
| 向量召回 | 数十毫秒 | 取决于索引规模与过滤条件 |
| 重排 | 一百到数百毫秒 | 与候选数量成正比 |
| 生成 | 秒级，流式可改善感知 | 与输出长度和模型规模相关 |

这些数字随环境变化，只用于建立量级感。产品设计时的做法是给整条链路设一个延迟预算，再分配各环节额度；超预算时优先砍重排条数或改写次数，而不是压缩生成质量。

成本方面，主要开销来自注入的 Token 与重排调用。控制手段是限制召回条数、压缩片段长度、对高频问题做结果缓存。

## 2.6 常见误解

一、RAG 的效果主要看生成模型。不成立。检索不到正确片段时，再强的模型也只能编造。

二、分块用固定长度最省事，效果也够用。不成立。结构明确的文档按结构切分通常明显更好，固定长度会切断章节与表格。

三、召回条数越多越好。不成立。过多片段会稀释注意力、推高成本，并增加相互冲突的概率。

四、重排一定提升效果。不成立。重排模型与业务语料不匹配时可能降低排序质量，需要用评估集验证。

五、解析环节可以交给通用工具，不必检查。不成立。解析错误会传导到全链路，必须抽样核对文本。

## 2.7 判断练习

判断下列问题最可能出在哪个环节。

1. 用户问“2026 年新版的退款政策”，系统回答旧版内容。
2. 检索结果里出现的全是正确主题的文档，但答案引用的段落答非所问。
3. 扫描版合同上传后，问答完全无法命中条款。
4. 用户问“订单 A123 的售后规则”，系统检索到其他订单的规则。
5. 答案内容正确，但标注的来源文档与内容不符。

参考答案：

1. 离线更新与版本管理。新旧版本同时入库且未按生效时间过滤，或新文档未入库。
2. 召回可用但重排失效。应在重排环节检查候选排序，或调整分块粒度。
3. 解析环节。扫描件缺少文字层，需接入 OCR 并抽查文本质量。
4. 查询改写或过滤环节。编号需要关键词检索与结构化过滤，纯向量检索易混淆。
5. 生成环节的引用绑定。需要求模型逐段标注来源，并在输出层校验引用与内容一致性。

## 2.8 小结

- RAG 分离线索引与在线问答两段，离线问题会在每次请求中重复出现。
- 离线链路是解析、清洗、分块、增强、向量化、入库，解析错误会传导到全链路。
- 分块策略需匹配文档结构，块内要保留标题路径，表格不应被切散。
- 在线链路是查询改写、召回、过滤、重排、组装、生成，重排用成本换精度。
- 延迟与成本应按环节分配预算，优先砍可选的检索步骤而非生成质量。
