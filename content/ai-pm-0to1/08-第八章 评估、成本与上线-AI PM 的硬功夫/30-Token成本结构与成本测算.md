# Token 成本结构与成本测算

本节说明 AI 产品的边际成本结构、测算方法、Agent 场景的成本放大机制，以及五层成本优化体系。这一节决定产品能否规模化。

## 2.1 与传统软件的成本差异

| 维度 | 传统 SaaS | AI 产品 |
|---|---|---|
| 成本结构 | 研发与运维为主，边际成本低 | 每次请求都有推理成本 |
| 规模化影响 | 用户增加，成本增长缓慢 | 用户增加，成本近似线性增长 |
| 毛利率 | 高且稳定 | 取决于单价与调用量，早期可能为负 |
| 成本可控性 | 主要靠架构优化 | 需要产品、模型、上下文多层控制 |

这意味着 AI 产品的定价与商业模式必须建立在成本测算之上。不做测算就定价，规模越大亏得越多。

## 2.2 成本构成

| 项目 | 说明 | 是否随请求增长 |
|---|---|---|
| 输入 Token | 系统提示词、历史、检索片段、工具结果 | 是 |
| 输出 Token | 生成内容，通常单价高于输入 | 是 |
| 检索与重排 | 向量检索、重排模型调用 | 是 |
| 工具调用 | 外部接口调用、业务系统查询 | 是 |
| 离线索引 | 文档解析、向量化、入库 | 否，按批摊销 |
| 存储与监控 | 向量库、日志、看板 | 部分 |

容易漏算的三项：重试带来的重复调用、多轮对话中历史重复计费、失败请求仍然消耗的输入 Token。

## 2.3 测算方法

单次请求成本的粗略算式：

```
单次成本 = 输入 Token 数 × 输入单价
         + 输出 Token 数 × 输出单价
         + 检索与重排调用成本
         + 工具调用成本
```

月度成本还要乘上三个系数：

1. 日均请求量 × 30。
2. 平均轮次。多轮对话每次都要重发历史，成本随轮次递增。
3. 重试与失败率。失败请求同样消耗资源。

一个结构化的测算表：

| 变量 | 取值方式 |
|---|---|
| 日均请求量 | 从业务预估或历史数据取 |
| 平均输入 Token | 系统提示词 + 历史 + 检索片段，实测取均值 |
| 平均输出 Token | 实测，注意长回答场景 |
| 平均轮次 | 从真实会话统计 |
| 重试率 | 从日志统计，通常不为零 |
| 单价 | 按模型与接口类型分别取 |

测算的纪律是：用实测数据，不用主观估计；单价可能变化，结论要写成“在当前单价下”的表述；上线后每月核对实际账单与测算偏差。

## 2.4 Agent 与多 Agent 的成本放大

Agent 的成本不是线性增长，而是乘性放大。

| 机制 | 放大原因 |
|---|---|
| 循环重发 | 每一轮都要带上此前全部上下文，轮次增加则输入量二次增长 |
| 工具结果注入 | 每次调用结果都追加到上下文，后续轮次继续携带 |
| 推理文本 | 思考过程本身占用输出 Token，并进入后续上下文 |
| 多 Agent 交接 | 每个 Agent 各自携带一份上下文，重复计费 |
| 校验与重试 | 生成后再审核、失败再重生成，调用次数成倍增加 |

举例说明量级：单轮问答输入一千 Token、输出三百 Token；若改成五轮 Agent 循环，且每轮上下文累积到三千 Token，总输入可达上万 Token，成本是单轮的十倍以上，而且延迟同步上升。

控制手段与放大机制一一对应：限制轮次、裁剪工具结果、不把完整推理文本带入下一轮、用结构化状态代替全量交接、设置会话级预算。

## 2.5 五层成本优化

| 层级 | 手段 | 收益 | 风险 |
|---|---|---|---|
| 需求层 | 缩小场景、减少不必要的模型调用、能规则化就不上模型 | 最大，直接减少请求量 | 需重新评估场景价值 |
| 模型层 | 按任务路由到合适模型、简单任务用小模型、必要时才用推理模型 | 显著，单价差异大 | 路由错误会降低质量 |
| 上下文层 | 精简系统提示词、限制检索条数、裁剪工具结果、压缩历史 | 明显，直接减少输入 Token | 可能丢关键信息 |
| 缓存层 | 精确缓存相同请求、前缀缓存复用固定提示词、语义缓存近似问题 | 中等，高频重复场景收益大 | 缓存过期导致答案过时，语义缓存可能错配 |
| 交互层 | 限制输出长度、流式输出、批量合并请求 | 中等 | 输出过短影响有用性 |

优化的顺序应该是从上到下：先减少不必要的调用，再考虑换模型，最后才做工程层的压缩与缓存。反过来做，往往在低价值的地方投入大量工程。

一条纪律：每一层优化都必须回到评估集验证，成本下降但达标率跌破阈值，等于把问题转移给用户。

## 2.6 与定价的关系

成本测算的直接用途是判断商业模式是否成立。三种常见定价方式与成本的匹配关系：

| 定价方式 | 适用 | 风险 |
|---|---|---|
| 按 Token 计费 | 用量波动大、开发者客户 | 用户难以预估，可能抑制使用 |
| 按席位订阅 | 使用稳定、企业内部 | 重度用户可能亏损 |
| 按价值或结果计费 | 效果可量化 | 需要可信的计量方式 |

具体定价策略在第9章展开。这里只需记住一个判断：如果单用户月成本超过其付费，规模扩大只会扩大亏损，此时应先做成本优化或调整场景，而不是继续拉新。

## 2.7 常见误解

一、单价低就等于成本低。不成立。输出 Token 单价通常更高，轮次与重试也会成倍放大。

二、按平均请求量测算就够了。不成立。峰值、长尾请求与异常重试会显著拉高实际账单。

三、缓存一定能省钱。不成立。缓存命中率低或内容频繁变化时，维护成本可能超过收益。

四、小模型一定更划算。不成立。若达标率下降导致重试与人工介入增加，总成本可能更高。

五、成本优化是上线之后的事。不成立。立项阶段不做测算，产品形态可能从根上不成立。

## 2.8 判断练习

1. 一个客服产品日均一万次会话，平均五轮，每轮重发全部历史。指出成本问题与两种改法。
2. 单轮问答成本可接受，改成 Agent 后成本上涨十倍。列出三个放大来源。
3. 团队把所有请求都路由到旗舰模型，理由是“效果稳定”。给出改进方向与验证方式。
4. 语义缓存上线后成本下降，但用户投诉答案与问题不匹配。分析原因与处理。

参考答案：

1. 历史全量重发导致输入 Token 随轮次累积。改法：滑动窗口保留近期轮次；把关键事实抽成结构化状态每轮注入，替代原始历史。
2. 循环轮次增加导致上下文累积；工具结果持续注入；推理文本与多 Agent 交接重复携带上下文。
3. 按任务难度路由：简单意图与抽取用小模型，复杂推理用旗舰模型。验证方式是在同一评估集上分场景比较达标率与单位成本。
4. 语义缓存按相似度匹配，阈值过松导致近似但语义不同的问题命中同一答案。应提高阈值、限定缓存范围到高频稳定问题，并在结果中提示来源为缓存。

## 2.9 小结

- AI 产品的成本是边际成本，随请求量近似线性增长，定价必须以测算为基础。
- 成本由输入输出 Token、检索重排、工具调用与摊销项构成，重试、多轮与失败请求容易漏算。
- 测算要用实测数据，并保留“在当前单价下”的前提表述。
- Agent 的成本是乘性放大，来源是上下文累积、工具结果注入、推理文本与多 Agent 重复携带。
- 成本优化按需求层、模型层、上下文层、缓存层、交互层顺序推进，每层都需回归评估。
