# 监控、日志与效果观测

本节说明线上需要记录哪些信息、指标如何分层，以及效果下滑时的排查链路。没有观测能力的 AI 产品，问题只能靠用户投诉发现。

## 3.1 为什么需要观测

线上分布与评估集不同：用户的真实表述、请求频率、数据范围都超出预期。此外，模型版本、知识库内容、上游业务系统都会变化。评估集只能覆盖已知问题，未知问题只能靠线上观测发现。

## 3.2 必须记录的内容

| 类别 | 记录项 | 用途 |
|---|---|---|
| 输入 | 用户原始输入、改写后的查询 | 判断理解与改写是否偏离 |
| 检索 | 召回的片段、得分、过滤结果、最终注入内容 | 判断知识是否被找到并被使用 |
| 生成 | 输出全文、引用来源、置信标记 | 核对答案与依据 |
| 工具调用 | 工具名、参数、耗时、返回状态 | 判断执行是否成功 |
| 用户反馈 | 采纳、修改、重问、差评、转人工 | 判断真实可用性 |

每条记录还必须带元数据：请求标识、用户或租户、时间、模型版本、Prompt 版本、知识库版本、各环节耗时、Token 用量、成本。

这组字段决定了排查能否进行。缺少检索命中记录，就无法区分“没检索到”与“检索到但没用”；缺少版本号，就无法关联变更与效果波动。

## 3.3 日志的隐私与合规

记录得越全，排查越容易，但隐私风险也越大。三条处理原则：

1. 脱敏。身份证号、手机号、地址、银行卡号等在入库前脱敏或哈希。
2. 保留期限。明确各类日志保存多久，到期删除。
3. 访问控制。谁能查看原始日志、谁能导出，需有权限与审计。

用户上传的文档内容属于高敏数据，是否记录全文应根据业务与合规要求决定，通常记录摘要与引用位置即可。

## 3.4 指标分层

| 层级 | 指标 | 用途 |
|---|---|---|
| 业务 | 任务完成率、采纳率、转人工率、留存 | 判断产品是否被使用 |
| 质量 | 差评率、修正率、拒答正确率、引用准确率 | 判断回答是否可靠 |
| 系统 | 延迟 P50、P90、P99、错误率、超时率 | 判断是否可用 |
| 成本 | 单次成本、日成本、单会话成本 | 判断能否规模化 |

四层要同时看。只追业务指标会导致硬扛问题；只看系统指标会得到“跑得很快但没人用”的产品。

## 3.5 下滑排查链路

按六步执行，每一步都能缩小范围。

1. 确认现象。哪个指标下滑、从什么时候开始、影响哪些用户或场景。先排除统计口径变化。
2. 关联变更。近期是否有模型版本升级、Prompt 修改、知识库更新、上游系统发布。
3. 分环节定位。看检索命中率、工具成功率、生成质量三项，找出变化集中在哪里。
4. 归因。属于数据问题（知识缺失、格式错误）、模型问题（版本变化、拒答尺度变化）、流程问题（路由错误、超时）还是用户行为变化。
5. 处置。能回滚则回滚，不能回滚则修复并灰度验证。
6. 复盘。把新发现的失败样本加入评估集，并补充监控项。

| 症状 | 可能原因 | 验证方法 |
|---|---|---|
| 回答突然变短 | 输出限制调整、模型版本变化 | 对比变更前后的平均输出长度 |
| 拒答率上升 | 检索命中下降、阈值调整 | 查看召回得分分布 |
| 延迟上升 | 上下文变长、重排条数增加、上游变慢 | 分环节耗时对比 |
| 成本上升 | 轮次增加、重试增加、缓存失效 | 拆解 Token 来源 |
| 差评集中在某类问题 | 知识缺口或分块问题 | 抽取差评样本逐条核对 |

## 3.6 告警设计

告警的原则是少而准，避免告警疲劳。

| 级别 | 触发 | 响应 |
|---|---|---|
| 严重 | 错误率或超时率超过阈值，或核心场景完全不可用 | 立即处理，必要时回滚 |
| 重要 | 质量指标连续下滑，成本超过预算比例 | 当日排查 |
| 提示 | 单项指标轻微偏离 | 记录，观察趋势 |

两类告警必须设置：一类是绝对阈值，例如错误率超过某个比例；一类是同比变化，例如差评率相对上周上升明显。只看绝对阈值会漏掉“基线原本就高”的场景。

## 3.7 常见误解

一、有了评估集就不需要线上监控。不成立。评估集覆盖已知问题，线上会出现未知分布。

二、日志只记录输入输出即可。不成立。缺少检索命中与工具记录，无法定位失败环节。

三、指标越多越好。不成立。指标过多会失焦，应围绕四层各选少量核心指标。

四、告警越多越安全。不成立。频繁误报会让团队忽略真实告警。

五、用户反馈可以作为唯一质量来源。不成立。反馈样本有偏，主动差评的用户占比很低。

## 3.8 判断练习

1. 一个知识库问答产品差评集中在“答非所问”。给出三步排查。
2. 上线新模型版本后，转人工率一周内上升 8 个百分点。如何定位原因。
3. 日志显示检索命中正常，但答案仍无引用。判断问题环节。
4. 团队设置了二十条告警，每天收到数十条通知。如何改进。

参考答案：

1. 先抽取差评样本逐条核对；再查该问题的检索命中与注入内容；最后检查生成环节是否引用了正确片段。三步分别对应检索、注入、生成。
2. 对比新旧版本在同一评估集上的表现；按场景拆分转人工原因；检查新版模型的拒答尺度与工具调用成功率；确认是否有知识库同步变更。
3. 问题在生成与校验环节。应核对提示词是否强制引用，并检查输出层是否校验引用与内容的一致性。
4. 按四层指标收敛到少量核心告警，区分严重、重要、提示三级，合并重复项，并加入同比变化以减少误报。

## 3.9 小结

- 线上观测弥补评估集的盲区，必须记录输入、检索、生成、工具调用与用户反馈。
- 每条记录需带请求标识、版本号、耗时、Token 与成本，否则无法关联变更。
- 日志要脱敏、设保留期限、控制访问权限。
- 指标分业务、质量、系统、成本四层，需同时观察。
- 排查按确认现象、关联变更、分环节定位、归因、处置、复盘六步执行，并把新样本补入评估集。
- 告警应少而准，同时设置绝对阈值与同比变化。
