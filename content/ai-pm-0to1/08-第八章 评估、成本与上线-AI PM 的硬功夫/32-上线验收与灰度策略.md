# 上线验收与灰度策略

本节说明上线前的验收清单、模型与 Prompt 版本切换的回归方法、灰度放量与回滚机制。核心目标是让上线成为可控动作，而不是一次性赌博。

## 4.1 上线前验收清单

| 类别 | 检查项 |
|---|---|
| 功能 | 主流程可用，异常态有设计，空状态有引导 |
| 评估 | 评估集达标，指标达到阈值，结果有记录 |
| 兜底 | 各类失败均有走向，转人工通道可用 |
| 成本 | 单次成本与月度预算确认，超限策略生效 |
| 权限 | 按用户身份鉴权，敏感操作二次确认 |
| 合规 | 数据使用、生成内容标注、留痕满足要求 |
| 监控 | 日志字段齐全，核心告警可触发 |
| 运维 | 模型与 Prompt 版本可回滚，知识库可回退 |

八类中任何一类缺失，都不应全量上线。清单的作用是把“差不多可以了”变成逐项确认。

## 4.2 版本切换的回归评估

模型升级、Prompt 修改、知识库重建，都属于版本变更。每次变更都要做同一套回归。

| 步骤 | 做法 |
|---|---|
| 固定评估集 | 使用同一版本评估集，保证可比 |
| 新旧并行 | 同一批样本分别跑旧版与新版 |
| 盲评 | 标注员不知道答案来自哪一版 |
| 分场景看 | 不只看总体，拆到各意图与各文档类型 |
| 关注退化 | 重点看原本通过的样本是否变差 |
| 记录决策 | 写明采用哪一版、理由、遗留问题 |

一个常见误区是只看总体分数。总体提升可能来自某类问题的改善，同时另一类明显退化。必须分场景对比，尤其关注高风险的少数场景。

另一个误区是把新模型当作“只会更好”。版本变化可能改变拒答尺度、格式遵循、语气风格，这些都会影响产品行为。升级前必须实测，不能依据厂商说明。

## 4.3 灰度策略

灰度的四个维度：

| 维度 | 做法 | 适用 |
|---|---|---|
| 用户比例 | 按百分比逐步放量 | 通用场景 |
| 租户或部门 | 先在内部或少数客户试用 | B 端产品 |
| 场景 | 先在低风险场景启用 | 功能差异大 |
| 流量 | 按请求分流，其余走旧版 | 需要快速对比 |

放量节奏通常是：内部试用、小比例真实用户、逐步扩大、全量。每一档都要设观察期与放量条件。

观察期内要看三类指标：

1. 质量指标是否退化，尤其是差评率与拒答正确率。
2. 系统指标是否稳定，延迟与错误率是否在预期内。
3. 成本是否符合测算，单次成本是否超出预算。

放量条件应事先写死，例如“错误率低于某阈值且差评率未上升超过设定幅度”，避免凭感觉放量。

## 4.4 回滚机制

| 项目 | 要求 |
|---|---|
| 触发条件 | 严重故障、质量明显退化、成本失控、合规问题 |
| 回滚粒度 | 模型、Prompt、知识库、功能开关，应可独立回滚 |
| 回滚速度 | 分钟级完成，不依赖重新发布 |
| 回滚验证 | 回滚后核对核心指标恢复 |

三个容易忽略的点：

第一，回滚目标本身可能已经过期。旧版 Prompt 可能依赖已被修改的知识库结构，回滚前要确认旧组合仍可用。

第二，回滚需要开关，而不是重新部署。是否启用新版本应由配置控制，可以按用户或场景切换。

第三，回滚也要评估。回滚后同样要跑一遍核心指标，确认恢复，而不是假设一定恢复。

## 4.5 上线后的观察节奏

| 阶段 | 关注点 |
|---|---|
| 首日 | 错误率、超时率、转人工量、明显异常反馈 |
| 首周 | 质量指标趋势、成本是否符合测算、灰度群体差异 |
| 首月 | 任务完成率、留存、长尾失败类型、评估集补充 |

首日看稳定性，首周看质量与成本，首月看业务价值。三者的判断标准不同，不应混在一起看。

## 4.6 常见错误

一、用开发环境的小样本验证后直接全量。样本规模与真实分布都不足。

二、只做总体回归，不分场景。掩盖局部退化。

三、灰度没有放量条件。凭感觉扩大，出问题才发现。

四、回滚依赖重新发布。故障时无法在分钟级恢复。

五、上线后不补评估集。新发现的失败类型不会进入后续回归。

## 4.7 判断练习

1. 新模型在总体准确率提升 2 个百分点，但合同类问题下降 6 个百分点。是否应上线。
2. 灰度 10% 用户后，差评率未变化，但单次成本上升 30%。应如何处理。
3. 知识库重建后，旧版 Prompt 的引用格式失效。回滚时应注意什么。
4. 首日错误率正常，首周差评率缓慢上升。应优先检查哪些项。

参考答案：

1. 不应直接全量。合同类属于高风险场景，应先定位退化原因；或对合同场景保留旧版，其余场景灰度上线。
2. 先确认成本上升来源（上下文变长、重试增加或缓存失效），评估是否在预算内；若超出预算，暂停放量并优化后再继续。
3. 回滚需同时回退知识库与 Prompt 版本，确认组合一致；回滚后跑核心指标验证，不能只切换模型或只切换 Prompt。
4. 优先检查质量与变更关联：近期是否有知识库或 Prompt 变更，抽取新增差评样本核对检索命中与生成忠实度，并分场景拆解。

## 4.8 小结

- 上线前按功能、评估、兜底、成本、权限、合规、监控、运维八类逐项验收。
- 版本切换必须用固定评估集做新旧并行盲评，并分场景关注退化。
- 灰度可从用户比例、租户、场景、流量四个维度控制，放量条件应事先写死。
- 回滚要能按模型、Prompt、知识库独立回退，分钟级生效，并验证恢复。
- 上线后按首日稳定性、首周质量与成本、首月业务价值三阶段观察，新失败样本要及时补入评估集。
