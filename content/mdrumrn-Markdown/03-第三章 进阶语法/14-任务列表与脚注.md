# 任务列表与脚注：扩展语法怎么用

任务列表写成 `- [ ]` 与 `- [x]`，脚注写成 `[^1]` 加一行 `[^1]: 说明`；两者都不属于 CommonMark 标准，属于 GFM 与编辑器扩展，换个渲染器就可能退化成普通文字。写之前先确认目标平台，这是使用所有扩展语法的前提。

## 一、任务列表的写法

任务列表是在无序列表项里加一个方括号标记，括号内一个空格表示未完成，`x` 或 `X` 表示已完成：

```markdown
- [ ] 补全接口文档
- [ ] 跑通端到端测试
- [x] 完成数据库迁移
```

规则有三条：必须先是列表项，也就是以 `-`、`*` 或 `+` 开头；方括号后必须有一个空格再写文字；方括号内不能有别的字符。`[x]` 写在普通段落里不会变成复选框，只会原样显示。

## 二、支持情况与「能不能点」

「显示成复选框」和「可以点击切换」是两件事，很多平台只做到前者：

| 环境 | 显示复选框 | 能否点击 | 说明 |
| --- | --- | --- | --- |
| GitHub 仓库文件 | 是 | 否 | 只读渲染 |
| GitHub Issue、PR | 是 | 是 | 勾选会留下操作记录 |
| GitLab | 是 | Issue 内可点 | 仓库文件只读 |
| Typora | 是 | 是 | 点击会改写源文件 |
| Obsidian | 是 | 是 | 阅读视图和编辑视图都可点 |
| VS Code 预览 | 是 | 否 | 需相应扩展或内置支持 |
| 静态站点生成器 | 多数是 | 否 | 取决于主题与插件 |
| 严格 CommonMark 渲染器 | 否 | 否 | 显示为普通列表文字 |

判断方法是看使用场景：写作笔记用任务列表，读者看到的是静态图标；真正需要协作勾选时，应放进 Issue 或任务系统，而不是 Markdown 文件。合适用法集中在三类：

- 待办清单：周计划、上线检查表、代码评审前自查。
- 进度追踪：迁移清单逐项打勾，比写「已完成三成」直观。
- 阶段性文档：把「已完成」「待办」放在同一列表里，便于对照。

反过来，正式发布的文档不适合大量使用任务列表，读者会误以为能点击。发布前可以改写成「已完成」「未完成」的文字描述，或者去掉方括号只留列表。

## 三、脚注的写法

脚注由引用标记和定义行两部分组成，引用写在正文里，定义通常集中在文末：

```markdown
GitHub 的 Markdown 解析基于 GFM 扩展[^1]，并非 CommonMark 原文。

[^1]: GFM 是 GitHub 在 CommonMark 之上补充的方言，任务列表来自它，脚注则是 GitHub 后来加入的支持。
```

标签可以是数字，也可以是单词，例如 `[^note]`，数字不必连续，渲染时会按出现顺序重新编号。定义行的冒号后要有空格，内容换行时续行缩进四个空格。同一个标签可以在正文里引用多次，指向同一条定义。

## 四、脚注在导出与静态站点里的表现

| 场景 | 表现 |
| --- | --- |
| GitHub 仓库渲染 | 支持，脚注跳到页尾并带返回链接 |
| Typora 导出 PDF、Word | 支持，排在页脚或文末 |
| Pandoc 转换 | 支持，可输出到 LaTeX、HTML、docx |
| Hugo | 默认开启，基于 Goldmark 的脚注扩展 |
| Jekyll | kramdown 支持脚注 |
| 不支持的环境 | 引用与定义两行原样显示，版式很难看 |

导出环节最容易出问题的是「预览正常、导出丢失」。如果文档要交给别人用 Word 打开，先在目标格式里试导出一页确认。

脚注编号由渲染器决定，源文件里写 `[^3]` 也可能显示为 1。同一条定义被引用两次时，多数实现只生成一个脚注条目，并在条目后提供多个返回入口。合并别人写的文档时，标签重名会让引用指错位置，统一改成带前缀的标签，例如 `[^md-1]`，比纯数字更安全。脚注正文同样支持行内代码和链接，但不建议放多段内容，阅读体验会割裂。

## 五、定义列表与其它扩展

定义列表用「术语 + 冒号缩进」表示，PHP Markdown Extra、Pandoc、kramdown 和 Typora 支持：

```markdown
CommonMark
: 严格的 Markdown 标准，只规定最基础的语法。

GFM
: GitHub 的方言，在标准之上加了表格、任务列表等扩展。
```

GitHub 会把这段渲染成普通段落加冒号，Obsidian 原生也不支持。类似还有 `==高亮==`，Obsidian、Typora 认，GitHub 不认；Pandoc 的 `^上标^` 和 `~下标~` 在多数编辑器里无效，只能用 `<sup>`、`<sub>`。

## 六、跨平台写作的保守策略

| 语法 | 主要风险 | 保守替代 |
| --- | --- | --- |
| 任务列表 | 静态站点不渲染复选框 | 普通列表加「待办」 |
| 脚注 | 不支持时露出源码 | 文末「注释」小节加编号 |
| 定义列表 | 仅少数工具支持 | 加粗术语加冒号解释 |
| `==高亮==` | 多数渲染器不认 | 加粗 |
| `^上标^` | 仅 Pandoc 系支持 | 用 `<sup>` 或直接写文字 |

实用的分界线是：只在个人笔记或确定的平台内使用扩展语法；只要文章会输出到网页、PDF、邮件等多个地方，就退回 CommonMark 加 GFM 里最稳的几条，也就是表格、删除线和任务列表，脚注视平台而定。

## 速查

- 任务列表：`- [ ]` 未完成，`- [x]` 已完成。
- 方括号后必须有空格，且必须是列表项。
- 复选框能显示不等于能点击。
- 脚注引用 `[^1]`，定义写 `[^1]: 说明`。
- 脚注定义可放文末，标签可重复引用。
- 定义列表用术语加冒号缩进，支持面窄。
- 扩展语法不是标准，换渲染器可能降级。
- 多平台发布时优先 CommonMark 与 GFM。
