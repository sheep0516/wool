# 强调：加粗、斜体、删除线与行内代码

行内强调一共五种写法：`**加粗**`、`*斜体*`、`***粗斜体***`、`~~删除线~~`，以及用反引号包住的行内代码。标记必须紧贴文字，内侧不留空格，否则不生效。

## 一、五种行内标记

| 语法 | 效果 | 用途 |
| --- | --- | --- |
| `**加粗**` | 加粗 | 关键词、警告 |
| `*斜体*` | 斜体 | 术语、书名、语气 |
| `***粗斜体***` | 粗斜体 | 极强强调，少用 |
| `~~删除线~~` | 删除线 | 修订、作废内容 |
| `` `行内代码` `` | 等宽字体 | 命令、文件名、变量 |

斜体也可以写成 `_斜体_`，效果相同，但下划线在词内部不会被识别。

## 二、边界规则：标记要贴住文字

开标记后面不能紧跟空格，闭标记前面不能紧挨空格，否则这对标记会被当作普通字符。

```markdown
**加粗**、*斜体*、***粗斜体***、~~删除线~~、`code`

** 加粗 ** 与 * 斜体* 都不生效
```

渲染效果：第一行五种样式全部生效；第二行因为标记内侧有空格，星号原样显示。

相邻标记可以直接挨着，`**粗**和*斜*` 能正常渲染。需要同时加粗和倾斜时，用三个星号一次包住，比在两层标记里再套一层更稳。

## 三、中文与标点带来的坑

中文没有词间空格，强调标记通常能紧贴汉字生效，`这是**重点**内容` 可以正常渲染。但全角标点属于 Unicode 标点，紧贴标记时可能影响判定：`**"引用"**` 这类写法在部分解析器里会失效，稳妥做法是把标点放到标记外面。混合中英文时，标记两侧统一紧贴被强调的文字即可。

## 四、下划线与 `<u>`

Markdown 标准没有下划线语法。`<u>下划线</u>` 是 HTML 标签，GitHub、Obsidian、Typora 大多能渲染，但一些平台会过滤 HTML，内容粘到别处就失效。下划线在网页里还容易和链接混淆，能不用就不用。

## 五、删除线的语义与行内代码的分工

删除线在 GitHub 风格的 Markdown（GFM）里是扩展语法，严格的 CommonMark 渲染器不保证支持。它的语义是"这段内容已作废但仍保留痕迹"，用于修订记录，不是装饰。想弱化语气应当改写，而不是加删除线。

行内代码只承载一小段代码或字面量：命令、路径、变量名、配置项。多行代码要用三个反引号的代码围栏；行内代码本身包含反引号时，用两个反引号包裹，并在两端各留一个空格。

```markdown
执行 `npm run build` 后，产物在 `dist/` 目录。

用 `` ` `` 表示一个反引号本身。
```

渲染效果：命令与目录名以等宽字体呈现；第二行用双反引号包住单个反引号，文本不会被打断。

## 六、节制使用与错误对照

一段话里超过两处加粗，重点就不存在了。强调越多，读者越会跳过。斜体在中文界面里辨识度低，长段落尤其明显，术语首次出现时用一次即可。

| 错误写法 | 问题 | 正确写法 |
| --- | --- | --- |
| `** 加粗 **` | 标记内侧有空格，失效 | `**加粗**` |
| `* 斜体*` | 开标记后有空格 | `*斜体*` |
| `_snake_case_` | 词内下划线不解析 | `` `snake_case` `` |
| `**"重点"**` | 全角引号影响判定 | `**重点**` |
| 用删除线当装饰 | 语义不符 | 直接删或改写 |

## 速查

- 加粗 `**文字**`，斜体 `*文字*`。
- 粗斜体用 `***文字***`，一步到位。
- 删除线 `~~文字~~`，属 GFM 扩展。
- 行内代码用反引号包裹。
- 标记必须紧贴文字，内侧不留空格。
- 词内下划线不生效，改用反引号。
- 下划线只能用 `<u>`，且未必被支持。
- 一段最多两处强调。
