# 中英文混排与排版规范

结论：中英文混排的稳定做法只有一条主线——中文用全角标点，英文、数字、代码用半角，中文与英文或数字相邻时留一个半角空格。这些规则不是 Markdown 语法，解析器不会替你修正，只能靠写作时统一，或在发布前用工具检查。

## 一、空格：中英文、数字与单位

中文与英文之间、中文与数字之间各留一个半角空格。空格只加在“中文边界”，英文单词内部、数字内部、版本号内部不加。

```text
使用 VS Code 编辑 Markdown 文件
本库共 23 篇文章，分 5 个部分
第 17 篇讲目录与锚点
```

反例是 `使用VS Code编辑Markdown文件` 和 `共23篇文章`，读起来挤，也不利于屏幕阅读器和搜索分词。

数字与单位之间是否加空格，取决于单位和语境：公制单位、存储单位、货币代码通常加空格，如 `10 GB`、`5 kg`、`100 USD`；百分号、摄氏度符号紧贴数字，如 `50%`、`25°C`；中文量词按“中文与数字之间加空格”处理，如 `3 天`、`8 个文件`。同一篇里选一种并贯彻到底，比争论哪种更标准更重要。

版本号、文件名、命令、代码不拆空格：`v2.0`、`Node.js`、`npm run check`、`package.json`。时间写成 `2026 年 11 月 23 日`，日期内部的数字与“年、月、日”之间保留空格，全文统一。

## 二、标点：中文全角，英文半角

中文正文使用全角标点：`，。：；？！（）“”‘’《》——……`。英文句子、代码、URL、文件路径使用半角标点。判断依据是“这句话的主体语言”，不是“里面有没有英文单词”。

| 场景 | 用法 | 示例 |
| --- | --- | --- |
| 中文句子 | 全角逗号、句号 | `先备份，再修改。` |
| 中文里的英文短语 | 外层中文标点 | `使用 GitHub Pages 部署。` |
| 纯英文句子 | 半角标点 | `Run the command, then refresh.` |
| 代码与路径 | 反引号，不翻译 | `` `npm run build` `` |
| 时间、比例 | 半角冒号 | `14:30`、`3:1` |

括号：包裹中文内容用全角 `（）`，包裹纯英文、代码、URL 用半角 `()`。引号：中文引号用弯引号 `“”`，不要用英文直引号 `""` 包裹中文；界面按钮、菜单项优先用引号标出，如“点击‘设置’”；代码标识符则用反引号。

破折号用两个全角破折号 `——`，前后不加空格；表示范围用连接号 `-`，如 `2020-2025`；省略号用 `……`，不用三个英文句点。顿号 `、` 只用于中文并列词，较长的并列分句用逗号。

## 三、专有名词与大小写

专有名词按官方写法，不按中文习惯改写。常见的固定形式如下：

| 错误写法 | 正确写法 | 说明 |
| --- | --- | --- |
| Github | GitHub | 中间大写 H |
| Javascript | JavaScript | 两个词合成，S 大写 |
| Node.JS、nodejs | Node.js | 保留点和大小写 |
| Vscode、vs code | VS Code | 两个词，VS 大写 |
| MacOS | macOS | 首字母小写 |
| Wifi | Wi-Fi | 连字符不能省 |
| Html、Css | HTML、CSS | 缩写全大写 |
| Pdf、Api | PDF、API | 缩写全大写 |
| Iphone | iPhone | 首字母小写 |
| Springboot | Spring Boot | 两个词分开 |

同一篇里只保留一种叫法。首次出现可以写“静态站点生成器（SSG）”，之后统一用缩写或统一用中文，不要来回切换。

## 四、段落、句子与列表

一段只讲一个意思，控制在 2 到 4 句；句子超过 40 字就找逗号或分号拆开。段落之间空一行，不用两个全角空格做首行缩进，也不用 `<br>` 手动换行。

列表项保持平行结构：都以动词开头，或都是名词短语。短条目不加句末标点；条目本身是完整句子时，统一加句号，或统一用分号、最后一条用句号。不要一条加标点、一条不加。

标题不加句末标点，长度控制在一行内。表格单元格用短名词短语，不加句号；同一列的量纲、单位、格式保持一致。

## 五、十条可执行规范与改前改后

- 中文与英文之间加一个半角空格。
- 中文与数字之间加一个半角空格。
- 数字与公制单位之间加空格，百分号、摄氏度紧贴。
- 中文正文用全角标点，英文和代码用半角。
- 中文引号用 `“”`，不用 `""`。
- 破折号用 `——`，省略号用 `……`。
- 专有名词按官方大小写书写。
- 一段只讲一个意思，长句拆短。
- 列表、表格、标题的标点风格全篇统一。
- 代码、命令、文件名用反引号，不翻译。

| 改前 | 改后 |
| --- | --- |
| `用vscode打开md文件` | `用 VS Code 打开 md 文件` |
| `共23篇文章` | `共 23 篇文章` |
| `下载一个10GB的文件` | `下载一个 10 GB 的文件` |
| `成功率50%` | `成功率 50%` |
| `温度25°C` | `温度 25°C` |
| `这是github的仓库,很好用.` | `这是 GitHub 的仓库，很好用。` |
| `使用"设置"里的选项` | `使用“设置”里的选项` |
| `Node.JS 和 javascript` | `Node.js 和 JavaScript` |
| `第一步:安装依赖` | `第一步：安装依赖` |
| `2026年11月23日` | `2026 年 11 月 23 日` |

## 六、这些是约定，不是语法

Markdown 解析器只负责识别结构，不会替你把半角逗号换成全角，也不会在中文和英文之间补空格。渲染出来的结果忠实于原文，所以排版质量完全取决于写作习惯。

可以借助工具做检查，但要先确认规则：部分编辑器插件、textlint 一类的中文排版规则能标出空格和标点问题，需要额外安装与配置；Prettier 主要处理代码格式和换行，不会系统性地补中英文空格。工具只能兜底，不能替代统一约定。

真正有效的是把规则写进自己的模板：新建文章时套用同一套标点、空格和标题格式，发布前扫一遍。个人笔记以一致为先，团队协作以团队规范为先，不必在不同标准之间反复摇摆。
