# 静态站点与内容检查

结论：Markdown 变成网站只需要三步——解析成 HTML、套上模板、写成静态文件；剩下的工作是把目录约定固定下来，并在每次发布前做一次内容体检。生成器只是加速器，真正决定站点长期可用的是路径规则和检查机制。

## 一、从 Markdown 到网页的链路

| 阶段 | 输入 | 输出 | 常见做法 |
| --- | --- | --- | --- |
| 解析 | `.md` 源文件 | HTML 片段与标题结构 | Markdown 解析器，如 markdown-it |
| 套模板 | HTML 片段、站点配置 | 完整页面 | 模板引擎或框架布局 |
| 生成 | 页面数据 | 每篇一个 HTML 文件 | 静态导出脚本 |
| 托管 | 静态文件 | 可访问的网址 | GitHub Pages 等静态托管 |

解析阶段把标题、列表、代码块、表格转成 HTML，同时收集标题生成目录与锚点；套模板阶段补上导航、侧边栏、样式和页脚；生成阶段把每个 URL 写成一个 `index.html`；托管阶段只负责按路径返回文件。静态站点没有数据库和服务器逻辑，所有页面在发布前就已经是成品。

这也意味着两件事：第一，源文件里的相对路径必须在生成时正确转换，否则图片和站内链接会 404；第二，任何内容错误都不会在运行时暴露，只能在生成前检查。

## 二、常见方案对比

| 方案 | 适合 | 优点 | 代价 |
| --- | --- | --- | --- |
| Hugo | 内容多、追求构建速度 | 单二进制、构建快、主题多 | 要学模板语法和目录约定 |
| VitePress | 文档站、Vue 生态 | 开发体验好，Markdown 可嵌组件 | 深度定制需要 Vue 知识 |
| GitHub Pages 加自建脚本 | 想完全控制渲染与检查 | 无额外服务，规则自己定 | 解析、路由、搜索都要自己维护 |
| 本地预览服务 | 写作阶段 | 保存即刷新，反馈最快 | 只负责预览，不负责上线 |

本仓库是后两种的组合：本地用 Node 服务实时读取 Markdown 并渲染，发布时用自建脚本导出静态页，再交给 GitHub Pages 托管。写作时看到的是实时渲染，线上看到的是提前生成的副本，两套并行、互不影响。

## 三、目录即路由

这类站点通常不写路由表，文件路径就是 URL。约定越简单，越不容易出错。

| 磁盘上的位置 | 含义 | 页面或地址 |
| --- | --- | --- |
| `content/库名/` | 一个知识库 | `/kb/库名/` |
| `content/库名/01-第一章/` | 一个章节 | 章节不单独占 URL |
| `content/库名/01-第一章/01-文章.md` | 一篇文章 | `/kb/库名/01-文章/` |
| `content/库名/_meta.md` | 库的元信息 | 首页卡片与库概览 |
| `content/库名/01-第一章/assets/` | 本章图片 | 由文章相对路径引用 |

要点有四条：

- 文件夹等于知识库，子文件夹等于章节，`.md` 文件等于文章。
- 文章 URL 是扁平的 `/kb/库/文件名`，章节层级不进入地址；文件名直接成为地址的一段。
- 文件名前的 `01-`、`02-` 用于排序；它仍会出现在 URL 里，改名等于改地址。
- `_meta.md` 用 front matter 管库的标题、简介、分类和排序，正文作为库概述；引用块里的内容不渲染，可以写给自己看。

`_meta.md` 的最小写法：

```markdown
---
title: Markdown语言入门
description: 从语法到发布与维护的参考笔记。
category: Markdown学习
order: 1
---

本库按五个部分组织，每篇独立成文。
```

## 四、内容体检查什么

静态站点最危险的不是报错，而是静默失败：图片路径写错，页面只是少一张图；站内链接写错，点进去才是 404。体检要覆盖四类问题。

| 问题 | 页面表现 | 常见原因 | 处理 |
| --- | --- | --- | --- |
| 缺失图片 | 破图或空白 | 路径拼错、图片不在 `assets/`、大小写不一致 | 按提示把图片放到正确目录并改路径 |
| 失效链接 | 点击后 404 或停在文首 | 库名、文件名、锚点写错，标题改名 | 改成现有路径，锚点按标题重新生成 |
| 孤儿图片 | 页面上看不出来 | 图片已不再被任何文章引用 | 删除，或补回引用 |
| 缺少 `_meta.md` | 首页没有这个库 | 新建库时漏了元信息文件 | 补上 front matter |

体检脚本还需要跳过代码块里的示例，否则文章里写的 `![](图片地址)` 会被误判成真实引用。本仓库的检查命令是 `npm run check`，也可以双击 `check.bat`；它只读不写，发现问题时返回非零退出码，方便接进自动发布。

```bash
npm run check
```

## 五、本地预览、体检与发布

| 阶段 | 动作 | 结果 |
| --- | --- | --- |
| 写作 | 改 Markdown 并保存 | 本地页面自动刷新 |
| 体检 | 运行内容检查 | 列出缺失图片、失效链接、孤儿图片、缺元信息 |
| 提交 | 提交并推送 | 触发自动构建 |
| 发布 | 生成静态页并上传 | 线上地址更新 |

在本仓库里，推送后会自动做三件事：先跑体检，有问题直接失败；再执行静态导出；最后发布到 GitHub Pages。体检失败会挡住坏版本，避免破图和坏链上线。

## 六、一条最小上线路径

- 在 `content/` 下新建库文件夹，放入 `_meta.md`，写清标题、简介、分类。
- 在库里新建章节目录，再放入第一篇 `.md`，第一行写一级标题。
- 图片放进本章 `assets/`，正文用 `./assets/图片名.png` 引用。
- 本地启动预览，确认页面、图片、站内链接都能打开。
- 运行 `npm run check`，直到没有报错。
- 提交并推送到托管平台，开启 Pages 自动部署，等待构建完成。
- 打开线上地址，抽查首页、库概览、一篇文章和一张图片。

这套路径不依赖任何特定生成器：换成 Hugo 或 VitePress，变的只是预览和构建命令，目录约定和体检思路不变。

## 检查清单

- [ ] 每个知识库都有 `_meta.md`，front matter 字段完整
- [ ] 文章都放在章节文件夹内，文件名带排序前缀
- [ ] 图片位于本章 `assets/`，引用使用相对路径
- [ ] `npm run check` 通过，没有缺失图片和失效链接
- [ ] 没有无人引用的孤儿图片
- [ ] 站内链接的锚点与目标标题一致
- [ ] 本地预览确认页面、导航、图片正常
- [ ] 推送后构建成功，线上抽查通过
