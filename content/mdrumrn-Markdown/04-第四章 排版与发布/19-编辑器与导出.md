# 编辑器与导出：Typora、VS Code 与格式转换

结论：写作工具和导出工具分开选。编辑器负责输入、预览、大纲和图片管理，导出负责把同一份 Markdown 变成 HTML、PDF、Word 或 PPT。没有一款工具在三件事上都最好，稳定流程比工具本身更值钱。

## 一、三类工具对比

| 维度 | Typora | VS Code 加插件 | Obsidian |
| --- | --- | --- | --- |
| 预览 | 所见即所得，输入即排版 | 分栏预览，需要插件增强 | 实时预览，编辑与阅读可切换 |
| 大纲 | 内置大纲面板 | 内置大纲视图，插件可增强 | 内置大纲，可折叠 |
| 图片处理 | 支持粘贴图片并复制到指定目录 | 需图片粘贴插件或手动放入 `assets/` | 附件目录可配置，粘贴自动保存 |
| 导出 | 内置 PDF、HTML，其他格式常依赖 Pandoc | 依赖插件或外部 Pandoc | 内置 PDF，其他格式依赖插件或 Pandoc |
| 成本 | 付费，有试用 | 免费 | 个人使用免费，商用需看授权 |

上表按常见能力概括，具体功能随版本和插件变化，以当前安装的版本为准。

## 二、各自适合的写作场景

- Typora：单篇长文、报告、需要边写边看最终排版、最后交付 PDF 的场景。它的强项是“写的时候就像成品”。
- VS Code：技术笔记、代码示例多、需要和 Git、终端、项目文件同屏的场景。它本质是代码编辑器，Markdown 只是其中一种语言。
- Obsidian：长期积累、双向链接、卡片笔记、需要把几百篇笔记连成网络的场景。它更像知识库，不只是编辑器。

如果只写这个仓库的文章，VS Code 足够：文件就在项目里，改完保存，本地服务自动刷新。若经常导出排版精美的 PDF，Typora 更省事。

## 三、必备配置

自动保存：VS Code 在设置里把 `files.autoSave` 设为 `onFocusChange`，切走窗口即保存；Typora 在偏好设置里开启自动保存；Obsidian 默认即时写入。

图片位置：统一放在文章所在章节的 `assets/` 目录，Markdown 里写相对路径 `./assets/图片名.png`。Typora 可在图片设置里选择“复制到指定目录”；VS Code 需要 Paste Image 一类插件，把粘贴路径指到当前文件的 `assets/`；Obsidian 在“文件与链接”里把附件默认位置设为当前文件夹下的 `assets`。

换行行为：Markdown 里单个换行不等于换段，分段必须空一行。编辑器的“自动换行”只影响显示，不影响文件内容，建议打开，避免长行横向滚动。不要用行尾两个空格制造硬换行，也不要靠 `<br>` 控制间距。

编码统一用 UTF-8，换行符统一即可。VS Code 的一份最小配置：

```json
{
  "files.autoSave": "onFocusChange",
  "files.encoding": "utf8",
  "editor.wordWrap": "on",
  "markdown.preview.fontSize": 16
}
```

## 四、导出格式与工具

| 目标 | 常见做法 | 注意 |
| --- | --- | --- |
| HTML | 编辑器导出，或 Pandoc 加 `--standalone` | 样式要靠 CSS，默认是无样式的裸 HTML |
| PDF | 编辑器内置导出，或 Markdown PDF 插件，或 Pandoc 加 LaTeX 引擎 | 中文字体必须显式配置 |
| Word | Pandoc 输出 `.docx`，用参考文档控制样式 | 复杂表格和公式可能变形 |
| PPT | Marp 一类工具，或 Pandoc 生成 `.pptx` | 需要按页拆分，排版控制有限 |

Pandoc 是通用转换器，一份源文件可以输出多种格式。两条最常用的命令：

```bash
pandoc note.md -o note.html --standalone --css style.css
pandoc note.md -o note.docx
```

渲染效果：第一条生成带外部样式的独立 HTML，第二条生成 Word 文档。PDF 需要额外的 PDF 引擎和中文字体配置，命令更长，建议先固定一份模板再复用。

## 五、导出样式与常见问题

HTML 的样式全在 CSS：正文字体、行高、最大宽度、代码块配色。把下面这段存成 `style.css`，导出时引用即可。

```css
body {
  max-width: 760px;
  margin: 2rem auto;
  font-family: "Source Han Sans SC", "Microsoft YaHei", sans-serif;
  line-height: 1.75;
}

@media print {
  @page { margin: 18mm; }
  h2, h3 { page-break-after: avoid; }
  pre, table { page-break-inside: avoid; }
}
```

渲染效果：屏幕上正文居中、最宽 760 像素；打印或导出 PDF 时页边距 18 毫米，标题不落在页底，代码块和表格尽量不跨页。

PDF 还要处理字体：优先使用系统已安装的中文字体，导出时嵌入；字体缺失会变成方框。页边距通过 `@page` 或导出面板设置，分页用 `page-break-*` 控制。Word 的样式通过一份参考 `.docx` 预设，PPT 通过模板预设，改模板比逐页调格式省力。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 图片裂开或空白 | 相对路径失效、图片没随文件移动、大小写不一致 | 图片统一放 `assets/`，导出时保留目录结构，或把图片内嵌进 HTML |
| 中文变成方框 | PDF 引擎没有可用的中文字体 | 指定中文字体并嵌入，或换支持中文的导出模板 |
| 代码没有高亮 | 导出器未启用高亮主题 | 选择带高亮主题的模板，Pandoc 可指定 `--highlight-style` |
| 公式显示为原文 | 目标格式不支持 MathJax 或 KaTeX | HTML 导出启用 MathJax，PDF 用 LaTeX 引擎 |
| 表格错位 | 列太多、单元格内容过长 | 精简列数，长内容改为列表 |
| 标题孤零零在页底 | 没有分页控制 | 用 CSS 的 `page-break-after: avoid` |

## 六、一套稳定的导出流程

- 源文件只保留一份，图片放在固定的 `assets/`，不引用站外图。
- 先在编辑器预览一遍，确认标题、表格、代码块、公式都正常。
- 把导出命令写进脚本，固定输出目录和样式文件，不每次手调。
- 导出后打开成品，重点抽查图片、中文字体、代码高亮、公式和分页。
- 成品和源文件分开放，源文件进版本控制，成品按需分发。
