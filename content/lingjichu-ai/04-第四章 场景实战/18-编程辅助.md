# 编程辅助：读代码、写代码与调试

模型在编程上最稳的用法，是把它当加速器而不是决策者：样板代码、报错解释、测试补全、正则与 SQL 这类边界清楚的任务可以放心交给它；架构选型、安全逻辑、精确版本兼容这类要担责任的事，最终判断必须由人做。

## 一、什么交给模型，什么自己扛

| 适合交给模型 | 不适合交给模型 |
| --- | --- |
| 样板代码与目录脚手架 | 架构与技术选型 |
| 解释报错与堆栈 | 安全敏感逻辑（鉴权、加密、支付） |
| 补单元测试与边界用例 | 未公开的内部 API 用法 |
| 写正则、写 SQL | 依赖精确版本的兼容性问题 |
| 给重构建议 | 影响面不明的全局改动 |
| 语言或框架间翻译 | 需要业务权衡的取舍 |

判断标准很简单：错了能不能被测试或文档立刻发现。能，就交给模型；不能，就自己来。越靠近「正确性只能靠人负责」的环节，越不能交出去。代码翻译也要小心：模型翻完，语义等价需要你逐行对照，尤其是异常处理和边界。

## 二、读代码：先要结构地图

读陌生代码别一上来就问细节。先要一张结构地图：

- 这个模块解决什么问题，入口在哪。
- 主要文件各负责什么，调用关系如何。
- 数据从哪进、从哪出，经过哪些层。

拿到地图后，再逐块深入读关键函数和数据流。地图错了，后面所有细节理解都会跟着错，所以地图本身要你对照文件树和入口函数核实。一个有效的做法是让模型先输出模块清单和调用链，你逐项确认后再让它解释某一处，避免一次性要全量分析。结构地图可以要求模型用三行说清：入口函数、核心数据流、外部依赖。三行说不清，说明它也没读懂。调用链里跨服务、跨进程的地方最容易看错，单独标出来。

## 三、调试四步

调试不是问「为什么报错」，而是走一个能收敛的循环：

1. 最小复现：把问题缩到最少代码、最短输入，确认它仍然失败。
2. 提出假设：列出两到三个可能原因，按可能性排序。
3. 验证假设：对每个假设设计一条能证伪的检查，加日志、断点或最小改动。
4. 修复：只改被验证成立的那一处，改完立刻回归测试。

跳过最小复现，你会在无关代码里绕圈；跳过证伪，你会把「碰巧好了」当成修好了。四步里最容易被省略的是第三步，它恰恰决定了修复是否可靠。每次只验证一个假设，同时改多处会让你分不清是哪一处起了作用。

## 四、提问要给足的上下文

模型答得差，多半是问得少。下面五样缺一不可：

- 语言与版本：如 Python 3.11、Node 20，版本不同行为可能不同。
- 错误全文：完整堆栈，不要只截最后一行。
- 输入与期望输出：实际得到什么，期望得到什么。
- 已试过的方案：避免它重复你已经排除的路。
- 相关代码：能复现问题的最小片段。

上下文越完整，模型越可能直接命中，而不是给你一堆泛泛的排查建议。如果能贴出能直接跑的最小脚本，比贴一整段业务代码更有效，模型不必猜测上下文。

## 五、必须自己验证的环节与调试提示词

模型给的修复只是候选，三件事必须自己过一遍：

- 跑测试：至少跑相关单测和一次全量回归。
- 查文档：确认用到的 API 在你这个版本里确实存在且行为一致。
- 看边界：空值、超长输入、并发、异常路径都要过一遍。

修复后把根因和验证方法写进提交说明，下次同类问题能直接查。

一段可直接复制的调试提示词：

```text
我在用【语言与版本】，遇到下面的问题。

错误全文：
【粘贴完整堆栈】

相关代码：
【粘贴最小复现片段】

实际结果：【……】
期望结果：【……】
我已试过：【列出已排除的方案】

请先复述你理解的问题，再列出 2 到 3 个可能原因并按可能性排序；对每个原因给出一条能证伪的检查方法。
不要直接给最终修复，等我确认假设后再改。
```

## 检查清单

- [ ] 任务边界清楚，错了能被测试或文档发现
- [ ] 读陌生代码前先拿到了结构地图并核实过
- [ ] 调试先做了最小复现
- [ ] 假设都设计了证伪检查，没有直接改代码
- [ ] 提问给足了版本、错误全文、输入输出和已试方案
- [ ] 修复后跑了相关测试与回归
- [ ] 查过文档，确认 API 在当前版本可用
- [ ] 检查过空值、超长输入、异常路径等边界
