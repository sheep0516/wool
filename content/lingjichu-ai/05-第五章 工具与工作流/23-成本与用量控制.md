# 成本、延迟与用量控制

一次调用的成本主要来自 token 数量，延迟主要来自输出长度和工具往返。控制成本不是省到极致，而是把钱花在影响结果的地方：粗活用小模型、长上下文先压缩、重复前缀走缓存，事实核查与关键验收不能省。

## 一、成本构成

- 输入 token：系统提示、上下文材料、检索结果、历史对话。
- 输出 token：模型生成的全部内容，通常单价更高。
- 缓存：命中缓存的重复前缀往往更便宜，适合固定系统提示。
- 工具调用：检索、外部接口可能单独计费，按次累计。
- 重试：失败重跑等于重复付费，隐性成本容易被忽略。

记账时不要只看单次价格，要把一次任务的调用次数、重试次数、检索费用一起算进去。

同样一段话，放在系统提示、检索材料还是历史对话里，计费方式可能不同；优先把固定内容放在前缀以便缓存。

## 二、为什么输出更贵、长输出更慢

输出是逐 token 生成的，每一步都要计算，所以单价通常高于输入，生成长度也直接决定耗时。输入可以并行处理，输出只能一个接一个地出。

长输出还有连带成本：它会进入下一轮的上下文，抬高后续输入的 token 数。工具往返增加的是等待时间，不增加生成长度，两者要分开看。

所以「先想清楚要什么再问」比「多轮修补」更省：多轮对话里每一轮都要带上历史，越聊越贵。

## 三、控制手段

| 手段 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| 压缩上下文 | 只放相关片段，历史对话做摘要 | 降低输入成本与延迟 | 可能丢失细节 |
| 分级选模型 | 简单任务用便宜模型 | 显著降低成本 | 需判断任务难度 |
| 批处理 | 合并同类请求一次处理 | 减少重复开销 | 单次错误影响面大 |
| 缓存前缀 | 固定系统提示与示例放在最前 | 降低输入成本 | 仅对重复前缀有效 |
| 限制输出长度 | 明确字数与格式上限 | 降低输出成本与延迟 | 可能截断内容 |

这些手段有先后：先砍输出，再压输入，最后才考虑换模型。换模型影响质量，属于成本更高的一步。

## 四、延迟的组成

一次响应的等待分三段：首字延迟，包含排队与预填充；生成速度，通常按每秒 token 计；工具往返，包含网络请求与执行时间。

优化顺序也按这三段来：先缩短输出，首字更快到达；再减少工具往返次数，把能合并的查询合并；最后才考虑小模型，因为小模型快但可能要多轮才答对。

## 五、质量与成本的平衡

粗活交给小模型：分类、抽取字段、格式化、初筛、简单改写。难活交给强模型：推理、方案设计、长文分析、代码架构。

一个实用的组合是用大模型定标准、写提示词，用小模型做量大的初加工，再把结果交回大模型抽检。这样既控制了成本，又保留了质量下限。

一个常见误区是全程用最强的模型。多数日常任务并不需要顶级推理，长期下来这部分浪费最大。

## 六、个人用量怎么估算

按任务记一次账：任务名、所用模型、输入与输出的量级、调用次数、耗时、是否满意。连续记一周，就能看出哪类任务最费钱。

估算不需要精确到分，量级对就够了。比如「每天 20 次总结，每次输入约 3000 字、输出约 500 字」，据此判断是否值得换成更便宜的模型或加缓存。

如果某个任务每次都要多轮才满意，先修提示词或模板，往往比换模型更省钱。

一张可执行的优化清单：

```text
按优先级从高到低：
1. 缩短输出：能 200 字说清就别写 800 字
2. 压缩输入：只给相关材料，历史对话做摘要
3. 分级路由：分类、抽取、格式化交给小模型
4. 缓存固定前缀：系统提示与示例放在最前
5. 合并批处理：同类小任务一次提交
6. 监控重试：失败重跑要计数并分析原因
```

不能为省成本而省略的部分：事实核查、关键结论的二次验证、对外内容的最终人审。这些环节省下的钱，往往抵不过一次错误的代价。
