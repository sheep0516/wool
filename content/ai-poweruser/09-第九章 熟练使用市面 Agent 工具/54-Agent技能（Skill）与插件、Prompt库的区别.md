# Agent 技能（Skill）与插件、Prompt 库的区别

本节说明 Skill 是什么、由什么组成、如何调用，以及它与 Prompt 库、插件、MCP、Agent 的边界。

## 8.1 什么是 Skill

Skill 是给 Agent 预置的一套"能力包"：一个文件夹，里面有一份说明文档，写清在什么情况下该怎么做，以及可选附带的脚本、模板和参考资料。Agent 在运行时按需读取，不需要使用者每次重新粘贴提示词。

与提示词模板相比，Skill 多出三样东西：

1. 触发描述。写清"什么时候用、什么时候不用"，模型据此判断是否加载。
2. 可执行步骤。不只是输出格式，还包含按顺序执行的操作和判断分支。
3. 附带资源。脚本、模板、示例、参考文档可以随 Skill 一起分发。

一个典型的 Skill 目录：

```
my-skill/
├── SKILL.md          # 必需：名称、触发描述、步骤说明
├── scripts/          # 可选：可执行脚本
├── templates/        # 可选：输出模板
└── references/       # 可选：参考文档、示例
```

`SKILL.md` 开头通常是一段元数据，写明名称和描述；正文写步骤、判断规则、输出要求。描述字段决定了模型是否会加载这个 Skill，因此写作质量直接影响可用性。

## 8.2 为什么需要它

1. 减少重复输入。同一套流程不用每次粘贴。
2. 分层加载。模型先只看到名称和描述，确认相关后才读正文和资源，节省上下文。
3. 可分发。整个文件夹可以复制给同事，或放进版本库管理。
4. 可组合。一个任务可以同时加载多个 Skill，例如"写周报"和"公司文风"。

它解决的是"同一类任务反复交代、步骤容易漏、经验无法传递"的问题。

## 8.3 与其他形态的区别

| 形态 | 本质 | 触发方式 | 适合 |
|---|---|---|---|
| Prompt 库 | 人工挑选的模板文本 | 人复制粘贴 | 个人日常写作与分析 |
| Skill | 带说明与资源的能力包 | 模型按描述自动判断加载 | 多步骤、需复用、需分发 |
| 插件 | 包装好的外部服务 | 模型按工具描述调用 | 获取数据、执行动作 |
| MCP | 工具接入的协议 | 客户端连接服务器 | 标准化接入本地或远程工具 |
| Agent | 自主编排的执行体 | 用户发起任务 | 开放式、多步决策 |

关键差别在"谁来判断是否使用"：

- Prompt 库由人判断，人决定复制哪一段。
- Skill 由模型判断，模型根据描述决定是否加载。
- 插件与 MCP 由模型判断是否调用，但执行的是外部程序，会改变外部状态。
- Agent 不只是用能力，还自己决定步骤顺序和何时停止。

容易混淆的两组：

1. Skill 与 Prompt 库。前者能自动触发并携带脚本，后者只是文本。把 Prompt 存成文件不叫 Skill，缺少触发描述和资源，模型不会主动使用。
2. Skill 与插件。Skill 主要提供"怎么做"的程序性知识，工具提供"能做什么"的执行能力。一个 Skill 可以调用工具，但工具本身不是 Skill。

## 8.4 使用现成的 Skill

常见步骤：

1. 确认客户端的 Skill 存放位置，通常在用户目录或项目目录下的固定文件夹。
2. 把 Skill 文件夹整体放入，保持目录结构不变。
3. 重启或刷新客户端，让模型重新读取可用列表。
4. 用一句会触发该 Skill 的话测试，观察是否被加载。
5. 检查输出是否符合 Skill 说明中的步骤与格式。

判断是否真的加载了 Skill，看两点：输出是否遵循了 Skill 中的特定步骤；客户端日志或提示中是否显示了 Skill 名称。如果输出与普通回答没有区别，通常是描述没有匹配上，或目录位置不对。

注意安全边界：第三方 Skill 可能包含脚本。安装前查看 `SKILL.md` 与脚本内容，确认它会读写哪些文件、访问哪些网络地址。来源不明的 Skill 不要直接放入含敏感数据的目录。

## 8.5 写一个自己的 Skill

基本顺序：

1. 选定场景。只做一件重复发生、步骤稳定的事，例如"把会议记录整理成待办"。
2. 写描述。说明做什么、什么时候用、什么时候不用。这一段决定能否被触发。
3. 写步骤。按执行顺序列出动作、判断条件、需要的输入、输出格式。
4. 写失败处理。资料缺失、格式异常、工具失败时该怎么做。
5. 附资源。把模板、示例、术语表放进 `templates/` 或 `references/`。
6. 测试。用会触发和不该触发的两类请求各试几次。
7. 迭代。把失败案例补进说明，而不是只在对话里修。

描述字段的写法要点：

- 用任务中真实出现的词，包含用户可能说的同义说法。
- 写清适用条件，例如"当用户提供会议转写文本并要求生成待办时"。
- 写清排除条件，例如"仅讨论日程安排时不要使用"。
- 避免过宽，例如"处理文档相关的一切任务"会导致误触发。

步骤部分的写法要点：

- 一条一个动作，给出顺序。
- 需要的信息缺失时先追问，不要猜测。
- 输出格式固定，字段写清必填与空值规则。
- 涉及写入、发送、删除时，明确要求先确认再执行。

## 8.6 常见失败

1. 描述过泛。任何问题都会触发，导致该用的没用，不该用的乱用。
2. 描述过窄。只写了内部术语，用户换一种说法就匹配不上。
3. 正文过长。把整本手册塞进步骤，模型只执行前面几条。
4. 只写格式不写步骤。结果仍是普通对话，只是换了个格式。
5. 依赖缺失。脚本需要特定环境或库，换一台机器就跑不通。
6. 未声明副作用。Skill 中调用写操作却没有确认环节，误改数据。
7. 与知识库混用。把大量资料塞进 Skill，而不是放进知识库按需检索。

最后一条最常见：Skill 适合放"怎么做"，知识库适合放"依据什么"。两者混在一起，既拖慢加载，又降低检索质量。

## 8.7 自测

1. Skill 与 Prompt 库最关键的区别是什么？
2. 一个 Skill 至少需要哪两部分，缺一不可？
3. 为什么 Skill 的描述要同时写"何时用"和"何时不用"？
4. 什么内容应该放知识库，而不是塞进 Skill？

参考答案：

1. 是否由模型根据描述自动判断加载，以及是否携带脚本与资源。
2. 描述字段和正文步骤；无描述无法触发，无步骤等同于普通提示词。
3. 只写"何时用"容易误触发，边界条件决定模型能否正确判断。
4. 事实性资料、文档原文、大篇幅参考内容放知识库；程序性做法、判断顺序放 Skill。

## 8.8 小结

- Skill 是一个带说明文档、可附脚本与资源的能力包，由模型根据描述按需加载。
- 它与 Prompt 库的差别在自动触发与附带资源，与插件的差别在提供"怎么做"而非"能做什么"。
- 使用现成 Skill 要注意目录位置、触发测试和脚本安全。
- 自建 Skill 的关键是写清描述、步骤、失败处理和输出格式，并把资料放进知识库而不是正文。
- 常见失败是描述过泛或过窄、正文过长、只写格式不写步骤、依赖缺失和副作用未声明。
