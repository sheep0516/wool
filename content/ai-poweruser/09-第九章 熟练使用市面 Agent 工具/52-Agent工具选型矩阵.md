# Agent 工具选型矩阵

本节给出一套可执行的选型维度、评分方法和场景对照表。

## 6.1 选型维度

| 维度 | 关注点 |
|---|---|
| 任务复杂度 | 单轮问答、多步执行、跨系统操作 |
| 数据敏感度 | 公开、内部、机密、个人敏感 |
| 预算 | 订阅、按量、自托管硬件与运维 |
| 发布渠道 | 网页、API、社交平台、企业应用 |
| 维护成本 | 配置、升级、故障排查 |
| 团队规模 | 个人、小组、组织 |
| 集成需求 | 需要连接哪些系统与数据源 |
| 可迁移性 | 配置与数据能否导出 |

维度不宜过多。个人使用选 4 到 5 个，团队使用选 6 到 7 个。

## 6.2 评分方法

每个维度按 1 到 5 分打分，并写一句理由：

```
任务复杂度：4（需要多步检索与生成）
数据敏感度：5（含客户合同，不能出内网）
预算：2（个人付费，月预算有限）
发布渠道：3（主要在网页与聊天工具中使用）
维护成本：2（没有运维时间）
```

评分的作用是把模糊的"哪个好"变成可比较的条件。

## 6.3 场景对照

| 场景 | 建议工具类型 | 理由 |
|---|---|---|
| 个人写作与资料问答 | 自定义助手 | 配置低、资料固定 |
| 对外客服机器人 | Agent 平台 | 需要知识库、渠道发布和日志 |
| 企业内部知识问答 | 自托管 Agent 平台或企业协作助手 | 数据不能出内网，权限复杂 |
| 表单到表格的自动流转 | 工作流平台 | 步骤固定、需要稳定执行 |
| 跨系统数据同步 | 工作流平台或自建脚本 | 需要接口编排与幂等 |
| 代码修改与调试 | 编程 Agent | 需要读写代码与执行命令 |
| 一次性研究任务 | 通用 Agent 或对话模型 | 无需固定流程 |

## 6.4 工具能力对照表

建议维护一张表，记录每个工具能做什么、不能做什么：

| 工具 | 类型 | 知识库 | 工具调用 | 工作流 | 发布渠道 | 数据边界 | 成本 | 备注 |
|---|---|---|---|---|---|---|---|---|
| 工具A | 自定义助手 | 有 | 平台内置 | 无 | 链接 | 云端 | 订阅 | 适合个人 |
| 工具B | Agent 平台 | 有 | 插件 | 有 | 网页/API | 可自托管 | 按量 | 适合内部 |
| 工具C | 工作流平台 | 无 | API | 强 | 无 | 可自托管 | 按任务 | 适合流程 |

表格的价值在于对比，而不是记录产品介绍。每一项都应与自己的任务相关。

## 6.5 决策顺序

1. 先排除不满足硬条件的工具。数据不能出内网、必须支持某渠道、必须能导出。
2. 在剩余工具中比较任务覆盖度。能否完成主要场景，而不是只看演示。
3. 比较维护成本。没有运维能力时，自托管方案即使能力更强也不合适。
4. 比较成本。按实际调用量估算月支出，而不是只看标价。
5. 最后看体验。界面、响应速度、调试便利性属于加分项，不是决定项。

## 6.6 常见错误

1. 先选工具，再找用途。结果是工具功能很多，实际只用了一小部分。
2. 只看能力，不看维护。自托管方案上线后无人维护，逐渐失效。
3. 忽略迁移成本。配置和数据无法导出，换工具时全部重来。
4. 用个人工具处理组织数据。合规责任由个人承担。
5. 同时使用过多平台。排查问题时需要在多个系统间切换。
6. 不做评分，凭印象选择。换人后无法解释为什么选这个工具。

## 6.7 小结

- 选型维度包括任务复杂度、数据敏感度、预算、发布渠道、维护成本、团队规模、集成需求和可迁移性。
- 评分用 1 到 5 分并写理由，把模糊判断变成可比较条件。
- 场景对照表可以快速确定工具类型，再在同类中比较具体产品。
- 工具能力对照表记录知识库、工具调用、工作流、渠道、数据边界和成本。
- 决策顺序是先排除硬条件，再比覆盖度、维护、成本和体验。
- 常见错误是先选工具再找用途、忽略维护与迁移、用个人工具处理组织数据。
