# 多模型对照使用

本节说明如何让不同模型分工，以及用"红队提问"发现单一模型容易漏掉的问题。

## 4.1 为什么要用多个模型

单一模型有系统性偏差：格式偏好、论证习惯、对某类问题的过度自信、对某些观点的顺从。换一个模型，偏差通常不同。多模型对照的目的不是找"最强模型"，而是利用差异发现错误。

常见分工：

| 角色 | 任务 |
|---|---|
| 起草 | 生成初稿、方案、分析框架 |
| 评审 | 按清单挑错，指出遗漏与矛盾 |
| 红队 | 主动寻找反例、漏洞和失败条件 |
| 检索 | 查资料、核对事实、给出来源 |

一个模型可以承担多个角色，但起草与评审最好由不同模型完成，否则容易共享同一套盲区。

## 4.2 起草与评审流程

基本流程：

1. 模型 A 起草，按明确的结构和约束输出。
2. 模型 B 按评审清单检查，不重写，只列问题。
3. 人工判断哪些问题成立。
4. 模型 A 根据确认的问题修订。
5. 必要时再让模型 B 复核修订稿。

评审提示词示例：

```
以下是一份[文档类型]。请只做评审，不要重写。
检查项：
1. 事实与数字是否有依据
2. 论证是否存在跳跃
3. 是否有前后矛盾
4. 是否遗漏了必要的限定条件
5. 结构与格式是否符合要求
输出表格：位置、问题类型、原文、问题说明、严重程度。
```

关键约束是"只评审不重写"。一旦允许重写，评审模型会直接给出一版新稿，原稿的问题就被掩盖了。

## 4.3 红队提问

红队的目标是主动构造反对意见，而不是确认原方案合理。

常用提问方式：

- 这个结论在什么条件下不成立？
- 最可能失败的原因是什么？
- 如果关键假设是错的，后果是什么？
- 有哪些反例或相反的证据？
- 对手或批评者会怎么反驳？
- 这个方案最薄弱的环节在哪里？
- 如果预算减半、时间减半，哪里会先崩？

红队输出应区分"事实性反驳"和"观点性反驳"。前者需要证据，后者只需要逻辑自洽。两者都要记录，但处理方式不同。

## 4.4 对比方法

多模型对比要注意条件一致：

1. 同一输入。材料、提示词、参数完全相同。
2. 同一评分标准。事先定义维度与分值。
3. 盲评。评分时不看模型名称。
4. 多次执行。生成式输出有波动，单次结果不足以判断。
5. 记录差异。重点记录分歧点，而不是综合分。

分歧点往往最有价值：两个模型给出不同事实、不同结论、不同风险判断的地方，就是需要人工核查的地方。

## 4.5 注意事项

1. 评审模型也会犯错。它可能编造问题，也可能漏掉真正的问题。
2. 同源模型不算独立验证。同一厂商、同一底座的不同版本，偏差往往相似。
3. 成本会翻倍。每次对照至少多一次调用，长文档场景更明显。
4. 不要无限循环。起草与评审来回超过两轮仍无收敛，应转人工判断。
5. 明确裁决者。多模型给出不同意见时，需要一个明确的判断标准或人，而不是继续让模型互相辩论。

## 4.6 适用场景

适合多模型对照：

- 对外发布的文档、报告、方案。
- 高风险决策的分析材料。
- 事实核查，尤其是数字、引用、条款。
- 代码审查，一个生成，另一个找边界问题。
- 需要发现盲区的头脑风暴。

不适合：

- 低风险的日常改写、格式转换。
- 时间紧迫、只需一个可用初稿。
- 成本敏感的高频批量任务。

## 4.7 小结

- 多模型对照利用不同模型的偏差差异，目的是发现错误，不是找最强模型。
- 常见分工：起草、评审、红队、检索；起草与评审最好由不同模型完成。
- 评审要"只评审不重写"，否则会掩盖原稿问题。
- 红队提问主动构造反例、失败条件和反对意见。
- 对比要同输入、同标准、盲评、多次执行，并重点记录分歧。
- 评审模型也会犯错，同源模型不算独立验证，循环要有上限。
