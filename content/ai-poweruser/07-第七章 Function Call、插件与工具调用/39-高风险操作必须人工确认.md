# 高风险操作必须人工确认

本节说明哪些操作属于高风险、为什么要把建议与执行分开，以及确认机制如何设计。

## 5.1 高风险操作清单

| 操作 | 风险 |
|---|---|
| 发送邮件、消息 | 误发、发错人、内容未经审阅 |
| 付款、转账、下单 | 资金损失、重复支付 |
| 删除或修改数据 | 数据不可恢复、影响他人 |
| 提交表单、申报 | 法律责任、不可撤回 |
| 对外发布内容 | 声誉风险、合规问题 |
| 修改权限、授权 | 安全边界被破坏 |
| 调用产生费用的接口 | 费用失控 |
| 操作生产环境 | 服务中断、影响用户 |

判断标准不是操作是否"看起来危险"，而是后果是否不可逆、是否影响他人、是否涉及资金或法律。

## 5.2 建议与执行分离

核心原则：AI 给建议，人做决定；AI 生成草稿，人执行。

| 阶段 | 负责 | 产出 |
|---|---|---|
| 建议 | AI | 方案、草稿、待执行操作清单 |
| 审核 | 人 | 确认、修改、拒绝 |
| 执行 | 系统或人 | 实际操作 |
| 记录 | 系统 | 日志、版本、回执 |

分离的目的不是降低效率，而是把不可逆动作留在人的控制之下。自动化可以加速建议和准备，但不能替代最终确认。

## 5.3 确认机制的设计

1. 展示实际影响。用自然语言说明"会发生什么"，而不是只显示参数。
2. 明确对象与范围。收件人、金额、文件、时间都要列出。
3. 默认不执行。需要主动点击确认，而不是默认勾选。
4. 二次确认。资金、删除、对外发布类操作要求再次确认。
5. 草稿模式。先保存为草稿，人工检查后再发送。
6. 限额。单笔金额、单次数量、每日总量设置上限。
7. 可撤销。至少在短时间内支持撤回。
8. 双人复核。高风险操作要求第二人确认。

## 5.4 风险分级

| 等级 | 示例 | 处理方式 |
|---|---|---|
| 低 | 读取文件、查询数据、生成草稿 | 可直接执行，保留日志 |
| 中 | 修改内部记录、创建日程 | 执行前展示变更，可撤销 |
| 高 | 对外发消息、提交表单、发布内容 | 人工逐项确认 |
| 极高 | 付款、删除数据、权限变更、生产操作 | 二次确认 + 双人复核 + 限额 |

分级应写进 Agent 的配置和提示词，而不是靠模型自行判断。

## 5.5 提示词层面的约束

```
以下操作必须先获得人工确认，不得直接执行：
发送任何对外消息、付款或下单、删除或覆盖数据、提交表单、发布内容、修改权限。

执行前，输出：
1. 操作类型
2. 影响对象与范围
3. 具体内容或参数
4. 不可逆的后果
5. 等待用户输入"确认执行"后再调用工具
```

提示词约束只是第一层。真正的保障在运行时权限和确认界面，不能只依赖模型遵守指令。

## 5.6 常见错误

1. 为了省事，把发送、提交类操作设为自动执行。
2. 确认界面只显示 JSON，用户看不懂实际影响。
3. 批量操作只确认一次，后续条目自动执行。
4. 没有限额，一次误操作造成大范围影响。
5. 没有撤销机制，发现问题时已经无法挽回。
6. 权限过大，Agent 能访问远超任务所需的数据。
7. 日志缺失，事后无法确认谁执行了什么。

## 5.7 小结

- 高风险操作包括对外发送、资金、删除、提交、发布和权限变更。
- 核心原则是建议与执行分离：AI 出方案和草稿，人做最终确认。
- 确认机制要展示实际影响、默认不执行、二次确认、支持草稿、限额、可撤销和双人复核。
- 风险按低、中、高、极高分级，处理方式写进配置与提示词。
- 提示词约束只是第一层，运行时权限和确认界面才是主要保障。
