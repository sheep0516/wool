# 工具失败与兜底

本节说明工具调用常见的失败类型、重试原则，以及失败时如何给出可执行的下一步。

## 4.1 常见失败类型

| 类型 | 表现 | 原因 |
|---|---|---|
| 超时 | 长时间无返回 | 网络、上游服务慢、查询过重 |
| 参数错误 | 返回参数校验失败 | 类型、格式、枚举值不符合定义 |
| 权限不足 | 返回 401/403 | 未授权、范围不够、密钥失效 |
| 返回为空 | 结果为空列表或 null | 确实不存在、查询条件过窄 |
| 格式不符 | 返回结构不是预期格式 | 接口变更、错误页被当作数据 |
| 工具不存在 | 调用失败，找不到工具 | 名称拼错、未启用、版本不匹配 |
| 速率限制 | 返回 429 | 调用过于频繁 |
| 部分成功 | 批量操作中部分失败 | 个别条目校验不通过 |

失败不一定会被模型正确识别。模型可能把错误信息当作正常结果，继续生成看似合理的回答。

## 4.2 兜底原则

1. 明确失败，不要编造。工具失败时，应说明失败原因，而不是用常识补写结果。
2. 重试有上限。同一调用最多重试 2 到 3 次，避免循环。
3. 区分可重试与不可重试。超时、限流可以重试；参数错误、权限不足重试无意义。
4. 提供降级方案。例如搜索失败时改用其他来源，或明确告知无法获取。
5. 提供可执行下一步。告诉用户需要补充什么信息、联系谁、或改用哪种方式。
6. 保留现场。记录工具名、参数、错误码和返回内容，便于排查。

## 4.3 重试策略

| 情况 | 是否重试 | 处理 |
|---|---|---|
| 超时 | 可以 | 间隔后重试，最多 2 到 3 次 |
| 限流 | 可以 | 退避等待，降低频率 |
| 参数错误 | 不可以 | 修正参数或追问用户 |
| 权限不足 | 不可以 | 提示申请权限或更换账号 |
| 返回为空 | 谨慎 | 放宽条件重查一次，仍为空则报告 |
| 写操作超时 | 不可以盲目重试 | 先确认是否已执行，避免重复提交 |

写操作的重试尤其危险。付款、发邮件、提交表单在超时后可能已经成功，直接重试会造成重复。应先查询状态，再决定是否重试。

## 4.4 失败时的提示词要求

在系统提示中加入失败处理规则：

```
工具调用失败时，输出：
1. 调用了哪个工具，使用了什么参数
2. 失败类型与错误信息
3. 是否已重试，重试结果
4. 建议的下一步：需要用户补充什么，或改用哪种方式
不要用常识猜测工具本应返回的结果。
```

这条规则的价值在于，把失败从"沉默"变成"可见"，避免模型用编造内容掩盖问题。

## 4.5 日志与可观测性

每次调用至少记录：

| 字段 | 内容 |
|---|---|
| 时间 | 调用开始与结束 |
| 工具 | 名称与版本 |
| 参数 | 完整参数，敏感字段脱敏 |
| 结果 | 返回内容或错误码 |
| 耗时 | 用于发现慢调用 |
| 重试 | 次数与原因 |
| 操作者 | 用户或任务标识 |

日志的作用是事后追查。没有日志时，失败只能靠用户描述，排查效率很低。

## 4.6 常见错误

1. 失败后不报告，直接生成一个"看起来合理"的答案。
2. 对所有失败统一重试，包括参数错误和权限不足。
3. 写操作超时后直接重试，造成重复提交。
4. 返回为空时，模型自行补写"暂无数据"之外的内容。
5. 没有调用上限，多个工具循环调用，费用失控。
6. 错误信息直接抛给用户，没有转成可执行的建议。

## 4.7 小结

- 常见失败包括超时、参数错误、权限不足、返回为空、格式不符、限流和部分成功。
- 兜底原则是明确失败、限制重试、区分可重试性、提供降级与下一步。
- 写操作超时不能盲目重试，应先确认是否已执行。
- 提示词应要求模型报告工具、参数、错误和建议，不得用常识补写结果。
- 日志记录时间、工具、参数、结果、耗时和重试，是排查的基础。
- 最常见的错误是把失败伪装成正常回答。
