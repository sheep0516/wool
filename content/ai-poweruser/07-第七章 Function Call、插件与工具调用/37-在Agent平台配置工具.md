# 在 Agent 平台配置工具

本节说明如何在平台上描述工具、设置必填项与权限、加入确认步骤。

## 3.1 配置的四个部分

| 部分 | 内容 |
|---|---|
| 工具描述 | 名称、用途、适用与不适用场景 |
| 参数定义 | 字段、类型、必填、默认值、取值范围、示例 |
| 返回说明 | 返回字段、格式、错误码 |
| 权限与确认 | 可访问范围、是否需要人工确认、调用上限 |

这四部分决定了模型能否正确调用、调用是否安全。

## 3.2 如何描述工具用途

好的描述回答三个问题：做什么、什么时候用、什么时候不用。

示例：

```
工具名称：查询订单状态
用途：根据订单号查询当前状态、支付情况和物流节点。
何时使用：用户询问某个订单是否发货、是否付款、到哪了。
何时不要使用：用户没有提供订单号；用户询问的是退款政策而不是具体订单。
参数：
- order_id：字符串，必填，格式为 12 位数字。
返回：status、paid、tracking_no、updated_at。
错误：ORDER_NOT_FOUND、PERMISSION_DENIED、TIMEOUT。
副作用：只读，不修改任何数据。
```

反例：

```
工具名称：订单工具
用途：处理订单相关的事情。
```

后者没有边界、没有参数说明，模型只能猜。

## 3.3 参数定义要点

1. 必填与选填分开。必填项缺失时，模型应先追问，而不是填默认值。
2. 类型明确。字符串、数字、布尔、枚举，不要用"任意"。
3. 取值范围明确。例如状态只能是 pending、paid、shipped、closed。
4. 格式明确。日期用 YYYY-MM-DD，金额用元并保留两位小数。
5. 给出示例。一个正确参数示例，能显著降低格式错误。
6. 默认值谨慎。涉及写操作时，不要设置危险默认值。

## 3.4 必填项与追问

必填项缺失时，应让模型先追问，而不是自行补全。

提示词写法：

```
调用工具前，检查所有必填参数是否齐全。
缺失时，先向用户询问，不要猜测或用默认值代替。
如果用户无法提供，说明该操作无法继续，并列出需要的信息。
```

这条规则可以避免模型用编造的订单号、日期或邮箱地址去调用工具。

## 3.5 权限设置

1. 最小权限。只开放完成当前任务所需的数据范围。
2. 读写分离。读工具默认开放，写工具单独授权。
3. 范围限制。文件工具限制目录，数据库工具限制表与字段。
4. 速率限制。限制单位时间调用次数，防止误循环和费用失控。
5. 调用上限。多步任务设置最大步数。
6. 日志记录。记录调用时间、参数、结果、操作者。
7. 密钥隔离。密钥存在运行时的安全配置中，不进入模型上下文。

## 3.6 确认步骤

对写操作和对外操作，设置确认环节：

- 调用前展示将要执行的操作与参数，由用户确认。
- 支持"仅生成草稿，不执行"的模式。
- 高风险操作要求二次确认，或由第二人复核。
- 确认信息使用自然语言描述，而不是只显示 JSON。
- 提供撤销或回滚方式，至少在短时间内可撤销。

示例确认文案：

```
即将向 3 位客户发送邮件，主题为"续费提醒"，正文见下方。
收件人：a@example.com、b@example.com、c@example.com
发送时间：立即
[确认发送] [仅保存草稿] [取消]
```

## 3.7 常见配置错误

1. 描述只写名称，没有用途和边界。
2. 参数没有类型和取值范围，模型传入非法值。
3. 必填项缺失时允许使用默认值，导致操作对象错误。
4. 写工具与读工具使用同一权限，误改数据。
5. 没有调用上限，多步任务陷入循环。
6. 确认信息只显示技术参数，用户无法判断实际影响。
7. 密钥写入提示词或工具描述，随上下文泄露。

## 3.8 小结

- 工具配置包括描述、参数、返回、权限与确认四部分。
- 描述要写清做什么、何时用、何时不用。
- 参数要明确必填、类型、范围、格式和示例。
- 必填项缺失时应追问，不要用默认值或猜测补全。
- 权限遵循最小权限、读写分离、范围限制、速率限制和日志记录。
- 写操作与对外操作必须设置确认步骤，并提供草稿模式与撤销方式。
