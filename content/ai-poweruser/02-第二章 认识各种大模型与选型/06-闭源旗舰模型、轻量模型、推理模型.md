# 闭源旗舰模型、轻量模型、推理模型

本节按能力定位把模型分为三档，说明各档的适用任务与代价，以及"最强模型不等于最适合模型"的原因。

## 1.1 三种定位

### 闭源旗舰模型

由厂商训练并提供服务，权重不公开，只能通过网页、订阅或 API 使用。特点是综合能力最强，覆盖写作、分析、代码、多模态等任务；代价是价格较高、延迟较大、版本由厂商控制。

### 轻量模型

参数量较小，强调速度与成本。多数可以通过 API 调用，部分可以在本地或端侧运行。能力集中在常见任务：分类、抽取、改写、简短问答、格式转换。

### 推理模型

在回答前先生成较长的内部推理过程，再给出结论。适合数学、逻辑、代码调试、复杂规划等需要多步推导的任务。代价是延迟明显增加、token 消耗更高，简单任务上未必比普通模型更好。

三类不是替代关系，而是分层。实际使用中常按任务难度路由。

## 1.2 能力与代价对比

| 维度 | 闭源旗舰 | 轻量模型 | 推理模型 |
|---|---|---|---|
| 综合能力 | 强 | 中，常见任务够用 | 强，复杂推理更稳 |
| 延迟 | 中到高 | 低 | 高 |
| 单次成本 | 高 | 低 | 高，推理 token 计入 |
| 长上下文 | 通常较好 | 有限 | 通常较好 |
| 稳定性 | 较好 | 受任务复杂度影响 | 较好，但输出更长 |
| 适合任务 | 复杂写作、分析、多模态 | 分类、抽取、改写、路由 | 数学、代码、规划、多步判断 |
| 不适合任务 | 高频简单调用 | 复杂推理、长文分析 | 简单问答、实时交互 |

## 1.3 什么任务需要强模型

以下情况优先使用旗舰或推理模型：

- 任务没有明确步骤，需要模型自己规划。
- 输出需要综合多份材料，存在冲突信息。
- 涉及代码修改、逻辑推演、数学计算。
- 输出会直接对外，错误代价较高。
- 需要处理长文档、多模态输入。

以下情况轻量模型通常足够：

- 固定格式的分类、打标签、路由。
- 从结构清晰的文本中抽取字段。
- 短文本改写、翻译、润色。
- 高频、低风险的批量处理。
- 对延迟敏感的交互场景。

判断方法：先用轻量模型跑一批真实样本，统计失败率。失败率可接受就用轻量模型；不可接受再升级。

## 1.4 最强模型不等于最适合模型

选择模型时不只看能力排名，还要考虑以下因素：

1. 成本。高频任务用旗舰模型，费用会随调用量线性增长；轻量模型可能只有几分之一。
2. 延迟。对话式产品中，等待时间直接影响可用性；推理模型在简单问题上会显得过慢。
3. 过度能力。简单任务用强模型，未必更准，还可能因为"想得太多"而偏离格式要求。
4. 风格与稳定性。不同模型的表达风格不同，面向用户的场景需要匹配，而不是只看分数。
5. 隐私与合规。部分数据不能离开内网，此时本地开源模型可能比最强闭源模型更合适。
6. 版本可控性。闭源模型会静默升级，行为可能变化；对稳定性要求高的场景需要固定版本或做回归测试。

## 1.5 路由思路

常见的成本控制方式是分层路由：

1. 默认用轻量模型处理。
2. 增加校验环节：格式校验、置信度判断、规则检查。
3. 校验不通过时，升级到旗舰或推理模型重试。
4. 高风险任务直接走强模型，并保留人工确认。

这种结构的收益在于，大部分请求由低成本模型完成，只有困难样本进入高成本路径。

## 1.6 小结

- 模型按定位分三档：闭源旗舰、轻量、推理。
- 复杂规划、代码、数学、多模态优先用强模型；固定格式、高频低风险任务用轻量模型。
- 推理模型的代价是延迟与 token 消耗，不适合简单任务。
- 选型要看成本、延迟、风格、隐私和版本稳定性，而不只看能力排名。
- 分层路由是兼顾质量与成本的常用做法。
