# 主流工作流工具

本节按定位比较常见工作流工具，并说明低代码与无代码的选择依据。

## 4.1 工具定位

| 工具 | 定位 | 优势 | 局限 |
|---|---|---|---|
| Zapier | 面向非技术用户的 SaaS 集成 | 应用覆盖广、上手快 | 复杂分支能力弱、费用随任务增长 |
| Make | 可视化流程编排 | 分支与数据处理灵活、价格适中 | 学习曲线较陡、调试不够直观 |
| n8n | 开源、可自托管的工作流平台 | 灵活、可私有部署、可写代码节点 | 需要部署与维护、对技术能力有要求 |
| 扣子/Coze | 对话机器人与轻量 Agent 平台 | 知识库、插件、发布渠道整合 | 复杂流程编排能力有限、平台绑定 |
| Dify | LLM 应用开发平台 | 支持 RAG、Agent、工作流、可自托管 | 配置项多、需要一定理解成本 |

定位差异的核心是三类能力：应用连接、流程编排、模型与知识库整合。选工具前先明确自己主要缺哪一类。

## 4.2 低代码与无代码

| 维度 | 无代码 | 低代码 |
|---|---|---|
| 使用门槛 | 低，拖拽配置 | 中，需要理解数据结构与少量代码 |
| 灵活度 | 受平台功能限制 | 可插入代码、调用自定义接口 |
| 复杂分支 | 支持有限 | 支持较好 |
| 维护 | 平台升级可能影响流程 | 自行维护，可控性更强 |
| 适合 | 简单连接、轻量自动化 | 多分支、需要定制处理 |

判断方法：

- 流程只有三五步、以应用连接为主，用无代码。
- 需要复杂分支、数据清洗、自定义接口，用低代码。
- 数据不能出内网，优先选自托管方案。

## 4.3 选型维度

1. 应用覆盖。常用工具是否已有现成连接器。
2. 流程复杂度。是否支持分支、循环、错误处理、人工确认。
3. 数据边界。是否支持私有部署、是否能关闭日志留存。
4. 成本。按任务数、执行次数还是按席位计费，超出后的价格。
5. 可观测性。是否提供执行历史、每步输入输出、失败重试。
6. 迁移成本。流程能否导出，是否被平台专有格式锁定。
7. 维护负担。版本升级、接口变更时，谁来修。

## 4.4 组合使用

实际场景中常需要组合：

- 用 n8n 或 Make 做流程编排。
- 用 Dify 或扣子做模型、知识库与对话入口。
- 用 Zapier 连接少量不支持 API 的应用。
- 用自建脚本处理平台不支持的定制逻辑。

组合的代价是排查变复杂。每增加一个平台，就多一处可能失败的地方。能用一条流程解决的，不要拆成三个平台。

## 4.5 常见误区

1. 只看模板数量。模板多不代表适合自己的场景，复杂流程仍需自己搭。
2. 忽略执行成本。按任务计费的工具，在高频场景下费用可能远超预期。
3. 把平台当数据库。长期数据存在平台内，迁移时难以导出。
4. 低估维护。接口变更、授权过期、版本升级都会导致流程中断。
5. 一开始就上复杂平台。简单任务用轻量工具即可，复杂平台的学习成本可能高于收益。

## 4.6 小结

- Zapier 适合轻量连接，Make 适合可视化分支，n8n 适合自托管与定制，扣子适合对话机器人，Dify 适合 LLM 应用。
- 无代码适合简单连接，低代码适合复杂分支与定制处理。
- 选型看应用覆盖、流程复杂度、数据边界、成本、可观测性和迁移成本。
- 组合平台会增加排查难度，能用一条流程解决的不要拆分。
- 常见误区是只看模板、忽略执行成本、把平台当数据库和低估维护。
