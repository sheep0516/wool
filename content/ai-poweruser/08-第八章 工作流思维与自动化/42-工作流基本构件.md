# 工作流基本构件

本节说明工作流的常见构件，以及状态如何在步骤之间传递。

## 2.1 常见构件

| 构件 | 作用 | 例子 |
|---|---|---|
| 触发器 | 决定流程何时开始 | 定时、收到邮件、表单提交、手动运行 |
| 节点 | 执行具体动作 | 调用模型、读写文件、发请求、发通知 |
| 变量 | 保存中间结果 | 分类标签、摘要、文件路径 |
| 条件分支 | 根据结果走不同路径 | 若为投诉则转人工，否则自动回复 |
| 循环 | 对列表逐项处理 | 批量处理 100 封邮件 |
| 人工确认 | 暂停等待人操作 | 发送前审批、金额超限确认 |
| 错误处理 | 捕获失败并采取措施 | 重试、告警、转人工、跳过 |
| 输出 | 交付结果 | 写入表格、发消息、归档文件 |

不需要一次用全。简单流程可能只有触发器、两个节点和一个输出。

## 2.2 状态传递

工作流与对话最大的差别之一，是状态需要显式传递。

两种方式：

- 隐式上下文：把上一步的输出直接拼进下一步的提示词。简单，但容易超出上下文，也难以追踪。
- 显式变量：把关键结果存为字段，例如 `category`、`summary`、`file_id`，下一步按字段引用。清晰，便于调试和重跑。

推荐做法：

1. 每一步明确列出输入字段和输出字段。
2. 只传必要字段，不要把整段原文一路带着走。
3. 关键字段做格式校验，例如枚举、日期、金额。
4. 保存中间结果，失败时可以从中断处重跑。

## 2.3 一个简单流程

```
触发器：每天 9:00
节点1：读取指定文件夹中的新文件
节点2：调用模型生成摘要
节点3：条件分支
    - 若摘要包含"紧急"，发送提醒
    - 否则写入汇总表
节点4：归档原文件
输出：汇总表 + 提醒消息
```

这个流程包含触发器、节点、变量、条件分支和输出，没有循环和人工确认，属于最小可用结构。

## 2.4 设计要点

1. 单一职责。每个节点只做一件事，便于替换和排查。
2. 输入输出明确。每个节点写清需要什么、产出什么。
3. 可重跑。同一步骤重复执行不应产生重复副作用。
4. 幂等。写操作要能识别"已经处理过"，避免重复发送或重复入库。
5. 显式状态。不要依赖模型"记得"上一步，关键信息存为变量。
6. 有限循环。设置最大次数，避免死循环。
7. 可观测。每步记录输入、输出、耗时和结果。

## 2.5 常见问题

| 问题 | 后果 |
|---|---|
| 节点职责过多 | 出错时无法定位，替换困难 |
| 全部靠上下文传递 | 超出窗口，信息丢失 |
| 变量缺少校验 | 脏数据流入下游 |
| 没有幂等标记 | 重试导致重复发送 |
| 循环无上限 | 费用与资源失控 |
| 中间结果不保存 | 失败后只能从头重跑 |

## 2.6 小结

- 工作流由触发器、节点、变量、条件分支、循环、人工确认、错误处理和输出组成。
- 状态传递推荐使用显式变量，只传必要字段，并做格式校验。
- 每个节点应单一职责，输入输出明确，可重跑且幂等。
- 循环要设上限，中间结果要保存，执行过程要可观测。
- 常见问题是节点过重、上下文传递、缺少校验、重复副作用和死循环。
