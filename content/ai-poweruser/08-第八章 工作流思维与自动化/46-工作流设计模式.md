# 工作流设计模式

本节说明常见的设计模式、各自的适用场景与风险，以及从小闭环扩展的顺序。

## 6.1 常见模式

| 模式 | 结构 | 适用 | 风险 |
|---|---|---|---|
| 串行 | 步骤依次执行 | 有明确先后依赖 | 单点失败会阻断后续 |
| 并行 | 多个步骤同时执行 | 步骤互不依赖，追求速度 | 汇总复杂，部分失败难处理 |
| 路由 | 按条件选择分支 | 不同类型走不同处理 | 分类错误导致走错路径 |
| 评审 | 一个生成，另一个检查 | 质量要求高 | 成本翻倍，评审也可能出错 |
| 人工在环 | 关键节点暂停等人确认 | 高风险操作 | 依赖人的响应速度 |
| 批处理 | 对列表逐项处理 | 批量任务 | 部分失败、重复处理 |
| 补偿 | 失败后执行反向操作 | 涉及状态变更 | 补偿逻辑本身可能失败 |

模式可以组合。例如"路由 + 人工在环 + 补偿"，用于邮件处理：分类后高风险邮件转人工，发送失败时执行补偿。

## 6.2 串行与并行

串行适合有依赖关系的步骤：

```
读取文件 → 解析 → 摘要 → 写入表格
```

并行适合独立步骤：

```
同时执行：查资料A、查资料B、查资料C → 汇总
```

并行的注意点：

- 汇总节点要能处理部分失败，而不是要求全部成功。
- 并行步骤的结果要有统一格式，否则汇总困难。
- 并发数要限制，避免触发限流。

## 6.3 路由

路由根据分类结果选择路径：

```
分类节点 → 投诉 → 人工处理
        → 咨询 → 自动回复草稿
        → 垃圾 → 归档
```

路由的关键是分类规则。规则模糊时，错误分类会被后续步骤放大。建议：

1. 分类标签有明确定义和示例。
2. 允许"不确定"类别，转入人工。
3. 记录分类依据，便于复查。
4. 定期抽检分类准确率。

## 6.4 评审与人工在环

评审模式用于质量要求高的输出：

```
模型A生成 → 模型B按清单检查 → 人工裁决 → 定稿
```

人工在环用于高风险动作：

```
生成草稿 → 暂停 → 人确认 → 执行 → 记录
```

注意点：

- 评审模型也会出错，不能完全替代人工。
- 人工确认界面要展示实际影响，而不是技术参数。
- 暂停时间不宜过长，否则状态过期，需要重新校验。

## 6.5 批处理与补偿

批处理要处理三个问题：

1. 部分失败。记录失败项，单独重跑，不要整批回滚。
2. 重复处理。用唯一标识标记已处理项。
3. 顺序与限流。控制并发，避免上游限流。

补偿用于状态变更失败后的回滚：

```
扣款成功 → 后续步骤失败 → 执行退款
```

补偿逻辑必须幂等，并能识别"是否已经补偿过"。

## 6.6 从小闭环开始

第一个工作流不要追求覆盖全部场景。建议：

1. 选一个高频、规则清晰的单场景。
2. 控制在三到五步。
3. 先手动触发，确认结果稳定后再改定时触发。
4. 先只读，确认无误后再加入写操作。
5. 先人工确认每个关键节点，稳定后再逐步放开。
6. 加入日志和失败告警，再考虑扩展。

扩展顺序：

```
单步手动 → 多步手动 → 定时触发 → 自动写操作 → 高风险人工确认 → 多分支与并行
```

每一步都应在上一阶段稳定运行后再推进。

## 6.7 反模式

1. 过度自动化。把需要判断的步骤也自动化，导致错误无人发现。
2. 全自动高风险。付款、发布、删除没有人工确认。
3. 步骤强耦合。一个节点做太多事，无法定位和替换。
4. 没有日志。失败后只能靠猜。
5. 无上限循环。费用和资源失控。
6. 一次建太大。流程覆盖十几个场景，任何一处变更都影响全局。
7. 忽略人工成本。人工确认点太多，流程实际跑不动。

## 6.8 小结

- 常见模式有串行、并行、路由、评审、人工在环、批处理和补偿。
- 串行适合有依赖的步骤，并行适合独立步骤，路由依赖分类规则。
- 评审与人工在环用于质量和高风险场景，但不能完全替代人的判断。
- 批处理要处理部分失败、重复处理和限流；补偿要幂等。
- 从小闭环开始，按"手动、定时、写操作、人工确认、复杂分支"的顺序扩展。
- 常见反模式是过度自动化、全自动高风险、步骤耦合和无日志。
