# Few-shot 示例法

本节说明示例数量与适用场景的关系，以及示例质量为什么比数量更重要。

## 3.1 什么是 Few-shot

Few-shot 指在 Prompt 中给出若干"输入—输出"示例，让模型模仿示例的格式、风格和判断标准。不给示例称为 zero-shot，给一个称为 one-shot，给多个称为 few-shot。

示例的作用不是教模型新知识，而是定义任务边界：什么算合格输出、字段怎么填、边界样本怎么处理。

## 3.2 不同示例数量的适用场景

| 示例数 | 适用场景 | 局限 |
|---|---|---|
| 0 个 | 任务简单、格式要求宽松、模型熟悉该任务 | 输出格式与风格不稳定 |
| 1 个 | 需要统一格式或风格，任务结构单一 | 无法展示边界情况 |
| 2 个 | 需要展示对比，例如正例与反例、两种分类 | 覆盖仍然有限 |
| 3 个及以上 | 分类边界多、字段多、需要覆盖不同情况 | 占用上下文，收益递减 |

经验上，格式统一用 1 个示例即可；分类和抽取通常需要 2 到 5 个，且要覆盖边界样本。超过 5 个后，新增示例带来的提升有限，反而挤占材料空间。

## 3.3 一个示例适合什么

适合：

- 固定输出格式，例如固定的表格列、JSON 字段。
- 固定写作风格，例如语气、长度、段落结构。
- 简单的转换任务，例如统一日期格式。

不适合：

- 需要判断边界的情况，一个示例无法说明"什么不算"。
- 存在多种合法输出的任务。

示例写法：

```
示例输入：……
示例输出：……
现在处理以下输入：……
```

## 3.4 两个示例适合什么

两个示例的典型用法是"正例 + 反例"，或"两类并列"。

正反例写法：

```
正例：输入包含明确金额与日期，输出为结构化字段。
反例：输入只有模糊描述，输出应为"信息不足"，而不是猜测。
```

这种写法能显著降低模型在边界样本上的过度推断。另一类用法是展示两种不同类别，让模型理解分类维度。

## 3.5 三个及以上示例适合什么

适合：

- 多类别分类，需要覆盖每一类的典型样本。
- 字段较多的抽取任务，需要展示不同版式。
- 输出风格有细微差别，需要多个样本才能体现。

放置示例时注意：

1. 覆盖边界，而不是只放容易的样本。
2. 各类别数量尽量均衡，避免模型偏向出现次数多的类别。
3. 示例顺序有影响，把最典型的放在前面。
4. 总长度控制在上下文可承受范围内。

## 3.6 示例质量比数量重要

高质量示例的特征：

- 真实：来自实际任务，而不是编造的完美样本。
- 格式一致：输入输出结构完全统一。
- 覆盖边界：包含容易出错的样本，并展示正确处理方式。
- 简短：去掉与任务无关的内容。
- 无错误：示例本身的事实、格式必须正确，否则模型会学到错误模式。
- 标注清楚：说明为什么这样输出，尤其是反例。

低质量示例的典型问题：

- 示例彼此矛盾，模型无法判断哪个标准优先。
- 示例过长，挤占真正的输入材料。
- 示例只覆盖简单情况，遇到边界样本仍然出错。
- 示例包含错误，模型把它当作标准答案模仿。

## 3.7 常见失败情况

1. 过拟合示例格式。模型机械复制示例的结构，即使输入不适用。
2. 示例偏差。所有示例都是同一种写法，模型无法处理其他情况。
3. 示例与指令冲突。指令要求简洁，示例却很冗长，模型会优先模仿示例。
4. 上下文超限。示例太多导致材料被截断。
5. 示例泄露敏感信息。真实案例中的姓名、电话、金额未脱敏。

## 3.8 小结

- Few-shot 的作用是定义任务边界，不是教新知识。
- 一个示例适合统一格式与风格；两个示例适合正反对比；三个以上适合多类别与多版式。
- 示例质量取决于真实性、边界覆盖、格式一致和正确性。
- 示例数量超过一定规模后收益递减，并会挤占输入空间。
- 示例与指令冲突时，模型往往优先模仿示例，需要提前检查一致性。
