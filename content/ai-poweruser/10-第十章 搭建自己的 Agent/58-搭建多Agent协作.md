# 搭建多 Agent 协作

本节说明多 Agent 的分工方式、状态传递、冲突处理，以及如何避免职责混乱。

## 4.1 为什么需要多 Agent

单个 Agent 承担所有职责时，会遇到三个问题：

1. 指令过长。检索、分析、写作、审核的规则堆在一起，模型只遵守一部分。
2. 上下文污染。检索到的大量材料挤占写作所需的上下文。
3. 难以定位。输出质量下降时，无法判断是检索、分析还是写作环节的问题。

多 Agent 的价值在于职责分离：每个 Agent 只做一件事，输入输出明确，可以单独测试和替换。

代价是调用次数增加、延迟变长、状态传递复杂。

## 4.2 常见分工

| 角色 | 职责 | 输出 |
|---|---|---|
| 检索 | 找资料、核对来源 | 资料清单与原文片段 |
| 分析 | 对比、归纳、找矛盾 | 结构化分析结果 |
| 写作 | 组织成文 | 初稿 |
| 审核 | 按清单检查 | 问题列表 |

分工依据是任务的天然阶段，而不是人为切分。检索与分析可以合并，写作与审核通常应分开，否则审核会受写作思路影响。

## 4.3 协作模式

1. 串行。检索 → 分析 → 写作 → 审核，逐段传递。
2. 评审。一个生成，另一个按清单检查，人工裁决。
3. 辩论。两个 Agent 给出不同方案，由第三个或人做判断。
4. 主管调度。一个调度 Agent 决定调用哪个子 Agent、按什么顺序。

个人使用通常串行加评审即可。辩论与主管调度的成本较高，适合高价值、高不确定性的任务。

## 4.4 状态传递

三种方式：

- 结构化字段。每个 Agent 输出固定字段，下一个 Agent 按字段读取。最稳定。
- 共享黑板。所有 Agent 读写同一份文档或状态对象。灵活，但容易冲突。
- 消息传递。Agent 之间直接发消息。适合对话式协作，难以审计。

推荐优先使用结构化字段，并约定：

1. 字段名、类型、必填项。
2. 空值与缺失的处理方式。
3. 引用的格式，例如文件名加页码。
4. 中间结果的保存位置，便于重跑。

## 4.5 冲突处理

多个 Agent 给出不同结论时，需要明确的裁决规则：

| 冲突类型 | 处理 |
|---|---|
| 事实冲突 | 以原始来源为准，找不到来源则标注不确定 |
| 分析冲突 | 列出两种结论及依据，由人判断 |
| 风格冲突 | 以写作规范为准，不以 Agent 偏好为准 |
| 审核冲突 | 审核意见优先于写作意见，除非审核理由不成立 |

不要让 Agent 互相辩论到收敛。多数情况下，争论会放大措辞差异，而不是解决事实问题。设置轮次上限，超过后转人工。

## 4.6 避免一个 Agent 什么都干

1. 职责单一。每个 Agent 只负责一个阶段。
2. 输入输出契约。明确每个 Agent 需要什么、产出什么。
3. 不共享全部上下文。只传必要字段，避免污染。
4. 可单独测试。每个 Agent 应有自己的测试用例。
5. 可替换。更换模型或提示词时，不影响其他环节。

常见反例是"万能助手"：一个 Agent 同时检索、分析、写作、审核，指令长达数千字，结果每一步都不稳定。

## 4.7 成本与延迟

多 Agent 的代价：

- 调用次数成倍增加，成本上升。
- 串行执行导致延迟累积。
- 状态传递出错时，排查跨多个环节。

控制方式：

1. 只在高价值任务上使用多 Agent。
2. 能合并的环节合并，例如检索与分析。
3. 并行执行独立环节。
4. 设置总步数上限。
5. 记录每个环节的输入输出与耗时。

## 4.8 小结

- 多 Agent 的价值是职责分离、上下文隔离和可替换，代价是成本与复杂度。
- 常见分工是检索、分析、写作、审核，写作与审核通常应分开。
- 协作模式有串行、评审、辩论和主管调度，个人使用串行加评审即可。
- 状态传递优先使用结构化字段，约定字段、空值、引用格式和保存位置。
- 冲突按事实、分析、风格、审核分类处理，设置轮次上限后转人工。
- 避免万能助手，保持职责单一、契约明确、可单独测试与替换。
