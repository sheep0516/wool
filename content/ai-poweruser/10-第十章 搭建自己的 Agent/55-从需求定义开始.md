# 从需求定义开始

本节说明搭建 Agent 前应先写清什么，以及如何定义任务闭环和成功标准。

## 1.1 先写需求，再选工具

常见的错误顺序是：先看到一个 Agent 平台，再想办法用它做点什么。结果是功能堆了很多，实际问题没有解决。

正确的顺序是：先写清任务，再判断需不需要 Agent，最后才选工具。

需求定义要回答四个问题：

1. 用户是谁。自己、同事、客户，还是某个系统。
2. 任务是什么。从什么输入，经过什么处理，得到什么输出。
3. 什么时候触发。手动发起、定时、事件驱动。
4. 什么算成功。准确性、速度、格式、成本，哪一项是硬指标。

## 1.2 任务闭环

一个完整的任务闭环包含四段：

```
输入 → 处理 → 输出 → 反馈
```

每一段都要写清：

| 环节 | 需要明确 |
|---|---|
| 输入 | 来源、格式、频率、质量 |
| 处理 | 步骤、判断规则、需要的资料与工具 |
| 输出 | 格式、交付对象、存放位置 |
| 反馈 | 谁来验收、失败如何回流、如何改进 |

只写"做一个问答助手"不算闭环，因为没有说明输入从哪来、输出给谁、错了怎么办。

## 1.3 边界：不做什么

需求文档中应明确写出不做什么，例如：

- 不回答知识库之外的问题，直接说无法确认。
- 不执行付款、发布、删除等操作。
- 不处理含个人信息的材料。
- 不替代专业判断，只提供整理与建议。

边界的作用是防止范围蔓延，也为测试提供依据。没有边界的 Agent，会在使用中不断被加入新要求，最后无法维护。

## 1.4 一页需求文档

搭建前用一页纸写清以下内容：

```
名称：
目标用户：
使用场景：
输入：来源、格式、频率
处理：主要步骤、需要的资料与工具
输出：格式、交付方式
成功标准：准确性、完整性、格式、速度、成本
失败处理：失败时如何提示、转人工还是重试
数据边界：哪些数据可以处理，哪些不能
不做什么：
```

这一页纸决定了后面的组件配置、测试用例和验收标准。

## 1.5 判断是否真的需要 Agent

写完需求后，先判断任务是否复杂到需要 Agent：

- 只需要一次生成、没有外部资料、没有多步操作，用单提示词即可。
- 步骤固定、不需要临场判断，用工作流即可。
- 需要多步判断、调用工具、根据结果决定下一步，才需要 Agent。

很多被称为"Agent"的需求，实际只是一个配置好的提示词或一条固定流程。用更简单的形式实现，维护成本更低。

## 1.6 小结

- 先写需求，再判断是否需要 Agent，最后选工具。
- 需求定义回答四个问题：用户、任务、触发方式、成功标准。
- 任务闭环包含输入、处理、输出、反馈四段，每段都要写清。
- 明确写出不做什么，防止范围蔓延，并为测试提供依据。
- 用一页需求文档固定目标、边界、成功标准和失败处理。
- 单提示词或工作流能解决的任务，不必做成 Agent。
