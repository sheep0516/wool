# 发布与接入

本节说明发布渠道的选择、发布前检查项，以及接入后的权限与反馈设计。

## 6.1 常见发布渠道

| 渠道 | 适合 | 限制 |
|---|---|---|
| 网页 | 对外展示、内部试用 | 需要处理登录与访问控制 |
| 微信 | 面向个人用户、轻量服务 | 平台审核、消息格式限制 |
| 飞书、钉钉、企业微信 | 组织内使用 | 依赖组织权限体系 |
| API | 接入自有系统、自动化 | 需要鉴权、限流、计费 |
| 内部工具 | 团队内部使用 | 需要部署与维护 |

选择渠道的依据是用户在哪里、以什么方式使用，而不是哪个渠道更流行。

## 6.2 发布前检查

1. 权限。谁能访问，是否需要登录，是否能限制到指定群组或部门。
2. 数据边界。知识库中是否有不应对外的内容。
3. 日志。是否记录对话、调用与错误，保留多久。
4. 反馈入口。用户能否报告问题，反馈流向谁。
5. 限流。单用户与全局的调用上限，防止滥用。
6. 成本。发布后的预估用量与费用上限。
7. 兜底。服务不可用时的提示，是否有人工渠道。
8. 合规。是否需要备案、隐私政策、数据说明。

## 6.3 权限设计

1. 最小可见范围。先小范围试用，再扩大。
2. 按角色区分。管理者、普通用户、外部访客的权限不同。
3. 数据隔离。不同用户或项目的数据不互相检索。
4. 写操作确认。通过 Agent 执行的操作需二次确认。
5. 可撤销。分享链接、访问授权可以随时收回。
6. 离职回收。人员变动时及时移除权限。

## 6.4 日志与反馈

日志至少包含：

- 时间、用户标识、会话标识
- 输入摘要、输出摘要
- 调用的工具与参数
- 错误与失败原因
- 耗时与 token 用量

反馈入口至少支持：

- 对回答标记"有用/无用"
- 提交问题描述与期望结果
- 关联原始对话，便于复现
- 反馈进入待处理列表，有明确负责人

没有反馈入口的 Agent，只能靠使用者自己发现问题，迭代速度很慢。

## 6.5 灰度与回滚

1. 先内部试用。找 3 到 5 个真实用户，运行一到两周。
2. 小范围发布。限制访问人数或部门。
3. 观察指标。成功率、反馈率、失败类型、成本。
4. 逐步扩大。指标稳定后再开放更多用户。
5. 保留回滚。新版本出问题时，能切回旧版本。

## 6.6 常见问题

1. 直接公开，没有小范围验证。
2. 知识库包含内部资料，发布后对外可见。
3. 没有限流，被大量调用导致费用失控。
4. 日志缺失，用户报告问题后无法复现。
5. 没有反馈入口，问题只能靠口口相传。
6. 权限过宽，外部用户能访问内部数据。
7. 发布后无人维护，知识库逐渐过期。

## 6.7 小结

- 发布渠道按用户所在位置选择：网页、社交平台、企业协作工具、API 或内部工具。
- 发布前检查权限、数据边界、日志、反馈、限流、成本、兜底和合规。
- 权限遵循最小范围、角色区分、数据隔离、写操作确认、可撤销和离职回收。
- 日志记录输入输出、工具调用、错误和用量；反馈入口要能关联原始对话。
- 发布采用灰度方式，保留回滚能力。
- 常见问题是直接公开、数据越界、无限流、无日志和无反馈。
