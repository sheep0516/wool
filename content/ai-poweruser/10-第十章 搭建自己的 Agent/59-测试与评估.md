# 测试与评估

本节说明如何建立测试集、选择评估指标，以及如何进行回归测试。

## 5.1 测试集的构成

建议准备 20 条真实问题，覆盖五类：

| 类型 | 数量 | 目的 |
|---|---|---|
| 常规问题 | 8 到 10 条 | 检验基本可用性 |
| 边界问题 | 3 到 4 条 | 检验模糊输入、超范围输入 |
| 无答案问题 | 3 条 | 检验是否会编造 |
| 对抗问题 | 2 到 3 条 | 检验注入、诱导、越权请求 |
| 格式问题 | 2 到 3 条 | 检验输出结构是否稳定 |

问题应来自真实使用场景，而不是网上找的通用题目。每条问题记录预期结果或判断标准。

## 5.2 评估指标

| 指标 | 说明 | 测量方式 |
|---|---|---|
| 准确性 | 事实、数字、结论是否正确 | 对照标准答案 |
| 完整性 | 是否覆盖必要信息 | 检查清单 |
| 格式遵循 | 是否符合指定结构 | 程序校验 |
| 拒答能力 | 无依据时是否明确说明 | 无答案问题测试 |
| 引用质量 | 来源是否可核对 | 打开链接或核对页码 |
| 成本 | 单次调用的 token 与费用 | 平台统计 |
| 延迟 | 首字与总耗时 | 计时 |
| 稳定性 | 多次执行结果是否一致 | 重复 3 次 |

不需要每项都量化。根据任务性质选 4 到 5 项作为主要指标。

## 5.3 评估方法

1. 通过/不通过。适合格式转换、字段抽取。
2. 分级评分。1 到 5 分，需事先定义各分值标准。
3. 成对比较。两个版本输出并排，判断哪个更好。
4. 人工评审。由使用者按实际可用性判断。

评分时应隐藏版本信息，避免先入为主。多人评分时先统一标准。

## 5.4 测试记录

每条测试记录以下内容：

| 字段 | 内容 |
|---|---|
| 日期 | 测试时间 |
| 版本 | Agent 版本、模型版本 |
| 问题 | 输入原文 |
| 预期 | 期望的输出或判断标准 |
| 实际 | 实际输出 |
| 结果 | 通过/不通过、得分 |
| 问题类型 | 事实、格式、拒答、越权等 |
| 备注 | 原因分析 |

记录积累下来，就是回归测试的基础。

## 5.5 回归测试

每次修改指令、知识库、工具或模型后，重跑测试集。

重点观察：

1. 原本通过的问题是否仍然通过。
2. 修改针对的问题是否解决。
3. 是否引入新的失败。
4. 成本与延迟是否明显变化。

不做回归测试，容易出现"修好一个、坏掉两个"。

## 5.6 常见问题

1. 测试题太少，无法覆盖边界。
2. 只用简单问题，测试结果过于乐观。
3. 没有无答案问题，无法发现编造行为。
4. 只看输出内容，不看成本与延迟。
5. 修改后不回归，问题反复出现。
6. 评分标准模糊，不同人打分差异大。
7. 测试集长期不更新，与真实使用脱节。

## 5.7 小结

- 测试集建议 20 条，覆盖常规、边界、无答案、对抗和格式五类。
- 主要指标是准确性、完整性、格式遵循、拒答能力、引用质量、成本、延迟和稳定性。
- 评估可用通过/不通过、分级评分、成对比较和人工评审。
- 每条测试记录版本、输入、预期、实际、结果和问题类型。
- 每次修改后做回归测试，观察是否修复问题、是否引入新问题。
- 常见问题是题目太少、过于简单、缺少无答案样本和不做回归。
