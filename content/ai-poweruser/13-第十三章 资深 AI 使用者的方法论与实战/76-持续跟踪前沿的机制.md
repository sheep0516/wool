# 持续跟踪前沿的机制

本节说明如何用固定机制跟踪模型与工具变化，避免被信息流带着走。

## 3.1 固定时间与固定流程

每周留出 30 到 60 分钟，按同一流程执行：

1. 查看本周值得关注的更新，最多 3 条。
2. 选 1 条与自己的任务相关的变化。
3. 用固定测试集跑一次对比。
4. 记录结论：是否影响现有用法，是否需要调整。
5. 更新个人工具表与场景表。

固定时间的目的是把跟踪变成习惯，而不是刷到哪算哪。

## 3.2 信息源管理

| 来源 | 用途 | 注意 |
|---|---|---|
| 官方文档与更新日志 | 确认功能、价格、条款变化 | 最可靠，优先看 |
| 模型与工具官方公告 | 新版本、能力变化 | 注意发布日期与适用范围 |
| 少量高质量技术博客 | 理解机制与用法 | 区分实测与宣传 |
| 社区讨论 | 发现实际问题 | 噪声多，需交叉验证 |
| 自己的测试集 | 判断对自己的影响 | 最直接 |

信息源不宜多。订阅十几个频道，实际读不完，还会被标题带偏。保留三到五个稳定来源即可。

## 3.3 技术变化到场景的翻译

看到一个新功能时，按四步翻译：

```
变化是什么 → 影响哪一层能力 → 对应我的哪个任务 → 是否需要行动
```

示例：

```
变化：某模型上下文长度提升。
能力层：长文档处理。
我的任务：合同审阅、课程讲义整理。
行动：用测试集重跑长文档任务，比较准确率与成本。
```

没有完成这一步，跟踪就只是知道了新闻，不会改变实际工作。

## 3.4 测试方法

不需要完整评估，做最小对比即可：

1. 从固定测试集中选 5 条与变化相关的题目。
2. 新旧版本各跑一次，记录输出与耗时。
3. 重点看：原本失败的是否修复，原本通过的是否退化。
4. 记录成本变化。
5. 结论写入技术变化日志。

只有通过测试的变化，才进入日常使用。

## 3.5 技术变化日志

每条记录包含：

| 字段 | 内容 |
|---|---|
| 日期 | 发现时间 |
| 变化 | 新模型、新功能、价格或条款调整 |
| 来源 | 官方链接 |
| 影响能力层 | 语言、检索、文档、流程、代码 |
| 相关任务 | 自己工作流中的具体任务 |
| 测试结果 | 通过/不通过、成本变化 |
| 行动 | 采纳、观望、忽略 |
| 复核时间 | 何时再看一次 |

日志的作用是避免重复测试，也避免遗忘之前判断过的结论。

## 3.6 不追每个新工具

工具更新速度快，逐个尝试会消耗大量时间。判断是否值得测试：

1. 是否解决现有工具的明确缺陷。
2. 是否与自己的高频任务直接相关。
3. 是否有可信的实测数据，而不只是宣传。
4. 迁移成本是否可接受。
5. 数据边界是否符合要求。

五个条件中多数不满足时，记录后跳过即可。

## 3.7 小结

- 每周固定 30 到 60 分钟，按固定流程跟踪更新。
- 信息源保留三到五个稳定来源，优先官方文档与更新日志。
- 用"变化、能力层、我的任务、是否行动"四步翻译技术变化。
- 测试只需 5 条相关题目，比较新旧版本的修复与退化。
- 技术变化日志记录日期、变化、影响、测试结果、行动和复核时间。
- 不追每个新工具，只在解决明确缺陷、与高频任务相关且迁移成本可接受时测试。
