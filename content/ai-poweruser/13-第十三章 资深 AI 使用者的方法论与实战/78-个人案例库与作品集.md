# 个人案例库与作品集

本节说明如何记录案例、整理作品集，并形成可展示的能力证明。

## 5.1 案例库字段

每个案例至少记录：

| 字段 | 内容 |
|---|---|
| 名称 | 一句话说明做了什么 |
| 背景 | 什么场景，解决什么问题 |
| 任务 | 目标与成功标准 |
| 工具 | 模型、平台、插件、版本 |
| 提示词或流程 | 关键模板或工作流结构 |
| 结果 | 产出与效果，尽量量化 |
| 失败点 | 出过什么问题，如何发现 |
| 改进 | 改了什么，效果如何 |
| 成本 | 时间、费用、人工复核 |
| 日期 | 完成时间 |

字段不必全部填写，但背景、做法、失败点和改进建议保留。

## 5.2 组织方式

按用途分类，比按工具分类更稳定：

```
案例库/
├── 写作/
├── 分析/
├── 自动化/
├── 知识库/
└── 教学/
```

每个案例一个文件，文件名用"场景 + 结果"，例如"会议纪要转待办-节省每周2小时.md"。

文件内保留原始提示词、输入样例（脱敏）和输出样例，便于复现。

## 5.3 作品集

作品集不是案例库的全部，而是挑选出的代表案例。建议选 3 到 5 个，覆盖不同能力：

1. 一个知识库或问答类项目。
2. 一个写作或内容生产项目。
3. 一个自动化或工作流项目。
4. 一个 Agent 或多 Agent 项目。
5. 一个失败复盘，说明边界与改进。

每个作品包含：

- 问题与背景
- 做法与工具
- 前后对比，尽量有数据
- 失败与改进
- 可展示的产出片段

失败复盘放在作品集中，比只展示成功更能说明能力边界。

## 5.4 脱敏

对外展示前必须处理：

1. 姓名、电话、邮箱、地址。
2. 客户名称、项目代号、合同金额。
3. 内部系统截图、链接、账号。
4. 未公开的产品信息与业务数据。
5. 提示词中的密钥、内部地址。

替换为占位符，或改写为虚构示例。保留结构与方法，去掉可识别的信息。

## 5.5 定期更新

1. 每月新增一到两个案例。
2. 每季度检查旧案例，标注过时的模型与工具。
3. 删除无法复现或已被替代的案例。
4. 更新作品集，替换更有代表性的项目。
5. 记录案例带来的实际收益，例如节省的时间、减少的错误。

案例库的价值在于持续积累，而不是一次写完。

## 5.6 常见问题

1. 只记录成功案例，没有失败与边界。
2. 只存提示词，没有背景与输入要求，无法复现。
3. 结果没有量化，无法说明效果。
4. 案例未脱敏，对外展示时泄露信息。
5. 长期不更新，内容与当前工具脱节。
6. 案例太多但没有整理，找不出代表性作品。

## 5.7 小结

- 案例库记录背景、任务、工具、提示词或流程、结果、失败点、改进和成本。
- 按用途分类，文件名体现场景与结果，保留可复现的输入输出样例。
- 作品集挑选 3 到 5 个代表案例，覆盖知识库、写作、自动化、Agent 和失败复盘。
- 对外展示前脱敏，去掉姓名、客户、金额、内部链接与密钥。
- 每月新增、每季度检查、定期替换作品集。
- 常见问题是只记成功、缺背景、结果未量化、未脱敏和不更新。
